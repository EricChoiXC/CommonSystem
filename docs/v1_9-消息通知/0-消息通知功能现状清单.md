# 消息通知功能现状清单

> 依据：当前仓库代码实测（后端 `com.eric.base.sys.notify`、前端 `frontend/src/views/notify` 等），
> 设计基线见 [docs/设计文档/sys/notify/通知待办核心业务.md](../设计文档/sys/notify/通知待办核心业务.md)、
> [docs/设计文档/sys/notify/通知待办表结构.md](../设计文档/sys/notify/通知待办表结构.md)。
> 本文件只描述**已实现**的功能与实现方案；v1.9 新规划（如推送外部消息通知）见同目录 `1-推送外部消息通知.md`。

## 1. 模块定位

当前「消息通知」= **通知待办模块（notify）**：站内待办/待阅的发送、接收、办理（已办/星标/删除），
以及基于 **SSE 长连接** 的实时推送（页面气泡 + 浏览器桌面通知 + 铃铛未读红点）。
不含邮件、短信、企业微信/钉钉等外部推送通道。

| 项 | 值 |
| --- | --- |
| 后端根包 | `com.eric.base.sys.notify` |
| 接口根路径 | `/backend/sys/notify/**` |
| 数据表 | `sys_notify_todo`（主表）、`sys_notify_todo_target`（接收人表，一对多） |
| 实时通道 | SSE（`EventSource`，文本事件流） |
| 管理权限 | `SYS_NOTIFY_ADMIN`（普通操作登录即可，数据按本人过滤） |

### 2.4 关键业务规则

- **发送**：标题、待办类型、来源模块（必须为合法 MODEL_KEY）、接收人必填；接收人列表去重跳空；来源模块展示时经 `ModelCacheService` 翻译为中文，未知 key 回退原值。
- **数据隔离**：我的待办只查本人 `field_user_id` 且未删除；单条操作前校验记录归属（`requireOwnNotDeleted`）。
- **默认值**：我的列表待办类型默认「待办」、是否办结默认「未办」（均无"全部"）；排序白名单 `receiveTime`/`createTime`，默认降序。
- **自动转已办**：
  - 待阅类型：点击详情（`load`）时自动转已办；
  - 待办类型：后端内部服务 `autoDoneByModel(modelName, modelId, userId)`，由各业务在触发点调用（按来源模块+文档id 找到待办后将该用户未办记录置已办）。
- **删除**：一律软删除，仅置 `field_is_del` 并记录删除时间，主表记录不删。

### 2.5 SSE 实时推送链路

```text
send() 写库成功 ──发布 NotifySendEvent
  → NotifySseEventListener（@TransactionalEventListener AFTER_COMMIT + @Async("notifySseExecutor")）
    → SseEmitterManager.sendToUser(userId, "new-todo", json)   // 仅在线用户
```

| 项 | 值 |
| --- | --- |
| 订阅凭证 | EventSource 不支持自定义请求头，登录 token 经 URL query `?token=` 传递，`LoginSessionService.resolve` 解析 |
| 事件名 | `connected`（连上）、`heartbeat`（30 秒心跳）、`new-todo`（新待办） |
| 推送数据 | `{ todoId, todoName, notifyType, modelName, modelId, url, receiveTime }` |
| 超时/重连 | 连接 30 分钟超时；断线由前端 EventSource 内置自动重连 |
| 连接规则 | 同一用户重复订阅时关闭旧连接只留最新；推送失败自动清理连接 |
| 可靠性 | 事务提交后才推送；推送异步且失败不影响主业务事务；离线用户不推送（靠列表兜底） |
| 线程池 | `notifySseExecutor`（core 2 / max 4 / queue 500，`common/config/AsyncConfig`） |
| 部署限制 | 连接表在 JVM 内存（`ConcurrentHashMap`），**仅支持单实例**；多实例需升级 Redis Pub/Sub 桥接 |

### 3.1 页面功能项

**我的待办（MyTodoView）**
- 筛选区：待办类型（默认待办，无"全部"）、来源模块、是否星标（不限/是/否）、是否办结（默认未办，无"全部"）、标题（2 栅栏宽）、接收时间范围（限年月日，2 栅栏宽）。
- 排序区：仅接收时间，默认降序。
- 按钮区：查询；批量已办/批量转未办（按当前"是否办结"筛选互斥显隐）、批量星标、批量删除（均有选中禁用与二次确认）。
- 列表列：复选框、标题、来源模块、接收时间、是否星标、操作（详情/已办-未办/星标/删除，固定右侧）。
- 详情弹窗：标题（整行）、发送人姓名、接收时间、内容（整行）；有 `fieldUrl` 时提供「前往处理」按钮。
- 联动：进入页面重置未读红点；`watch` notifyStore.version 收到新推送自动刷新列表；支持路由 query（类型/时间范围，供首页统计卡片跳转带条件）。

**待办管理（TodoManageView，后台）**
- 筛选区：待办类型、来源模块、标题（2 栅栏宽）、创建时间范围；排序仅创建时间。
- 列表列：标题、来源模块、创建时间、接收人数、已办人数；无复选框与操作按钮。

**发送待办（TodoSendView）**
- 表单：标题、待办类型、来源模块（下拉=modelOptions）、接收人（多选）、内容（多行文本非必填，整行）。
- 提交成功后关闭标签并返回 `/notify`。

### 3.2 全局通知交互（HomeView）

| 触发 | 行为 |
| --- | --- |
| SSE 收到 `new-todo` | ① 浏览器桌面通知（已授权时，标题=新待办/新待阅，正文=标题）；② 页内 `ElNotification` 气泡（点击跳 `/todo`）；③ `notifyStore.increment()` 红点 +1 并触发列表刷新 |
| 页面挂载 | 请求一次 `Notification.requestPermission()` |
| 顶栏铃铛 | `el-badge` 显示未读数（0 隐藏），点击跳 `/todo` |
| 进入 `/todo` | `notifyStore.reset()` 清零未读 |

## 4. 业务集成点（notify 的消费方）

| 调用方 | 用法 |
| --- | --- |
| 日程 `SysCalendarMainService` | 创建/更新团队日程时 `send()` 给接收人发**待阅**通知（标题「{创建人}向您发起了一个新日程，请确认。」，来源模块 `SYS-CALENDAR`，链接 `/calendar/detail/{id}`，不给自己发） |
| 日程删除 / 日程自动删除任务（`SysCalendarAutoDeleteTask`） | 团队日程删除后按接收人逐个 `autoDoneByModel("SYS-CALENDAR", ...)` 自动转已办 |

## 5. 权限与配置

- 权限码：`SYS_NOTIFY_ADMIN`（待办管理员，见 `properties/sys/notify/roles.yml` 的 `ROLE_LIST`+`ROLE_MAP`，启动时增量同步 `sys_org_auth`）；`SYS_ADMIN` 由 `BaseResolver` 统一放行。
- 我的待办类动作与 SSE 订阅：登录且启用即可，不做权限码校验。
- 码值：待办类型 `notify_type`、是否 `yes_no` 由 dict 模块提供（`src/utils/dict.js`）。
- 接口文档：springdoc 注解已同步（`@Tag` + `@Operation`，`@Operation.description` 以「鉴权动作 …」开头）；SSE 端点标注 `@SecurityRequirements`（不走 `X-Login-Token` 头）。

## 7. 现状约束与扩展注意点

1. SSE 连接表在内存中，重启/多实例即失效；扩展外部推送或集群部署时需先改造 `SseEmitterManager`。
2. 未读红点是纯前端会话状态：登录后从 0 开始，刷新页面归零，收一条 +1；如需准确未读数需新增后端「未读计数」接口。
3. `sys_notify_todo` 主表无更新/删除业务入口（XML 保留了 update/deleteById 供基础层），管理端只能查看。
4. 软删除记录永久保留，目前无清理策略；数据量大时需考虑归档。
5. `field_model_name` 依赖 `model:name:map` 缓存翻译，历史数据中未知 key 回退显示原值。
