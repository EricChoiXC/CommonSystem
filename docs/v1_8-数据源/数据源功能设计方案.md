# 数据源功能设计方案（v1.8）

- 数据源是一份**可复用的取数配置元数据**，三元组为：**查询接口**（背后的查询能力）、**查询条件**（固定注入的条件）、**返回字段**（结果投影白名单）。
- 本文以【日程】模块为贯穿示例：
  - 默认数据源【日程列表】：由开发以代码（Provider）形式随日程模块提供，不可改删；
  - 自定义数据源【用户日程】：由管理人员配置，挂在日程查询能力上，固定注入「我创建的」条件，并自选返回字段。
- 模块 key 为 `datasource`，包 `com.eric.base.sys.datasource`，表 `sys_datasource`，权限码 `SYS_DATASOURCE_ADMIN`。
- 与既有规划的关系：属新增公共能力，`docs/预期开发顺序.md` 与四大系统模块文档暂未收录「数据源」章节，实现时需按 AGENTS.md「文档体系」同批补需求/UI/API/数据库四份文档。

## 0. 需求还原与关键裁决

### 0.1 需求还原

| 需求点 | 落地语义 |
| --- | --- |
| 后端提供【日程查询】接口 | 既有 `POST /backend/sys/calendar/list`（`SysCalendarMainController#list`），本文不改动其对外契约 |
| 默认数据源【日程列表】由代码提供 | 日程模块新增 `SysCalendarDatasourceProvider`，注册默认数据源编码 `calendar.list` |
| 自定义数据源【用户日程】由管理人员配置 | 新增 `sys_datasource` 表 + 数据源管理页；【用户日程】= 目标能力 `calendar.list` + 固定条件「我创建的」+ 自选返回字段 |
| 「我创建的」固定条件 | 条件 `fieldCreatorId = ${CURRENT_USER_ID}`，执行期由数据源模块解析运行时变量后注入 |
| 数据源信息 = 查询接口 / 查询条件 / 返回字段 | 自定义数据源落库三列：`field_target`（查询能力编码，间接指向接口）、`field_conditions`（JSON 固定条件）、`field_fields`（JSON 返回字段白名单） |

### 0.2 命名裁决

| 项 | 定稿 | 说明 |
| --- | --- | --- |
| 包路径 / 模块 key | `com.eric.base.sys.datasource` / `datasource` | 对齐 `Sys{模块}` 规范 |
| 表名 | `sys_datasource` | 自定义数据源单表（默认数据源不入库） |
| 权限码 | `SYS_DATASOURCE_ADMIN` | 数据源管理（配置自定义数据源），同步 `properties/sys/datasource/roles.yml` |
| MODEL_KEY | `SYS-DATASOURCE` | 对齐 `SYS-CALENDAR` / `SYS-NOTIFY` 风格 |
| Provider 接口 | `SysDatasourceProvider` | 各模块注册「目标查询能力 + 默认数据源」的 SPI |
| 统一执行入口 | `POST /backend/sys/datasource/query` | 消费方按 `code` 取数，前端不落配置拼条件 |

### 0.3 关键设计决策（ADR 摘要）

| # | 决策 | 理由 |
| --- | --- | --- |
| A1 | **执行必须统一走后端**，前端只按 `code` 调 `/query`，不读取配置自行拼条件调目标接口 | 固定条件（如「我创建的」）必须服务端强制；若前端可拿配置自己调 `/sys/calendar/list`，固定条件可被绕过，字段投影也失去意义 |
| A2 | 自定义数据源**不能任填接口路径**，只能挂到 Provider 暴露的「目标查询能力」编码上 | 接口白名单由代码声明，防止任意接口/任意条件被接入（SQL 注入面、越权面）；落库的是能力编码而非裸 URL |
| A3 | 默认数据源用**代码 Provider 注册**而非 yml（对比先例 `numberRule.yml` + `SysNumberModelCacheService`） | 编号接入项是纯元数据（name/modelName/modelField），yml 够用；数据源需要**可执行逻辑**（真正的查询）与**目标鉴权器引用**，只能由代码承载。字段定义等元数据随 Provider 声明，经 `options`/`targets` 接口暴露给前端 |
| A4 | 返回字段投影复用 `common/utils/FieldProjector`（白名单反射投影为 `Map`） | 既有工具已含属性名格式校验（防 `getClass` 类拼接）与 null 跳过语义；数据源执行结果天然是「动态列」，`List<Map<String,Object>>` 是合理形态，不逐数据源建 VO |
| A5 | 「我创建的」在日程侧通过 `SysCalendarQuery` 增加 `fieldCreatorId` + Mapper 可选条件实现，**数据源执行沿用日程既有数据边界**（本人创建或本人接收），`fieldCreatorId` 是在此边界内**收紧** | 不放宽原接口数据边界；`selectCalendarList` 的 `(creator=userId OR receiver=userId)` 固定段保留，用户日程是其子集，语义安全且改动最小 |
| A6 | 执行鉴权两段式：`sys.datasource.query`（登录即可）→ **委托目标 action 鉴权**（如 `sys.calendar.list` → `CalendarResolver`） | 「能通过用户日程取数」的前提是「有日程列表权限」；委托走既有 `AuthorizationHelper.authorize(resolver, context)`，不改 resolver 契约 |
| A7 | 用户 ID 类条件字段声明 `literalAllowed=false`，**仅接受运行时变量** | 防止固定条件或调用方条件写死他人 ID 越权取数（如 `fieldCreatorId=zhangsan`） |

## 1. 现状分析（代码事实）

以日程模块为例，现有取数链路：

```text
POST /backend/sys/calendar/list
  → SysCalendarMainController#list
      authorize(new AuthorizationContext(ACTION_LIST))          // CalendarResolver：登录且启用
  → SysCalendarMainService#list(query, userId, pages, sortField, sortOrder)
  → SysCalendarMainDao#selectCalendarList / selectCalendarCount
  → SysCalendarMainMapper.xml#selectCalendarList
      WHERE (m.field_creator_id = #{userId} OR p.field_person_id = #{userId})   -- 固定数据边界
      + 可选条件 fieldName / fieldType / fieldAccept / fieldStartTimeStart|End
  → BaseResponse：data = List<SysCalendarVo>，metadata.total = 总数
```

| 事实/约束 | 出处 |
| --- | --- |
| 条件对象 `SysCalendarQuery`：fieldName / fieldType / fieldAccept / fieldStartTimeStart|End / year / month，无 `fieldCreatorId` | `sys/calendar/request/SysCalendarQuery.java` |
| 数据边界（本人创建 OR 本人接收）写死在 Service/Mapper | `SysCalendarMainMapper.xml#selectCalendarList` |
| 返回字段 `SysCalendarVo`：fieldId/fieldName/fieldType/fieldStartTime/fieldEndTime/fieldContent/fieldCreatorId/fieldCreateTime/fieldUpdateTime(+persons) | `sys/calendar/response/SysCalendarVo.java` |
| 字段白名单投影为 Map 的工具已存在 | `common/utils/FieldProjector#project(source, visibleFields)` |
| 跨模块统一鉴权入口已存在（复杂 Controller 先例） | `common/resolver/AuthorizationHelper#authorize(BaseResolver, AuthorizationContext)` |
| JSON 列 + 固定结构 DO 的先例 | `sys_number_rule.field_rule`（`SysNumberRuleConfigDo`）、`SysProcessTemplateNodeConfigDo` |
| 启动任务统一追加于 `SysStartupTask#run`（本方案经 Spring 注入收集 Provider，无需新增启动任务） | `sys/task/SysStartupTask.java` |
| 列表请求统一 `{ body, pages: { pageNo, pageSize, needPage } }`，总数走 `metadata.total` | `docs/开发规范.md` 三 |

## 2. 概念模型

### 2.1 三元组与两类数据源

```text
数据源 DataSource
├─ 查询接口 target   → 目标查询能力编码（如 calendar.list），由 Provider 声明 action + 接口路径
├─ 查询条件 conditions → List<{ key, op, value }>，value 支持 ${运行时变量}；执行期固定条件覆盖调用方条件
└─ 返回字段 fields    → List<字段名>；空 = 目标能力默认全字段；执行期经 FieldProjector 投影
```

| | 默认数据源（CODE） | 自定义数据源（CUSTOM） |
| --- | --- | --- |
| 提供方 | 开发，随模块代码发布 | 管理人员（`SYS_DATASOURCE_ADMIN`），管理页配置 |
| 注册位置 | Spring Bean（`SysDatasourceProvider` 实现），由 `SysDatasourceRegistry` 收集 | `sys_datasource` 表 |
| 示例 | 【日程列表】`calendar.list`，无条件、全字段 | 【用户日程】`calendar.my-created`：target=calendar.list + 固定条件「我创建的」+ 自选字段 |
| 可改性 | 不可改删（与代码同生命周期） | 列表/新建/编辑/启停/删除 |
| 编码规则 | `{模块}.{能力}`，如 `calendar.list` | 管理员维护，Service 层查重全局唯一 |

### 2.2 目标查询能力（Provider）

`SysDatasourceProvider` 是数据源模块对业务模块开放的 SPI，一份实现同时回答四件事：

1. **我是谁**：能力编码 / 名称 / 对应接口（action + 路径），供 `targets` 下拉与展示；
2. **能查什么**：条件字段定义（key、标签、类型、允许的操作符、是否允许字面量、是否可排序）；
3. **返回什么**：结果字段定义（key、标签、类型），是默认全字段与投影白名单的母集；
4. **怎么查 / 怎么鉴权**：`query(ctx)` 执行 + `getTargetResolver()` 供执行期委托目标 action 鉴权。

### 2.3 运行时变量与条件模型

条件统一建模为 `{ key, op, value }`，操作符枚举 `SysDatasourceOp`：`EQ / NE / LIKE / GT / GE / LT / LE / IN`。
运行时变量枚举 `SysDatasourceVar`，执行期由数据源模块解析：

| 变量 | 语义 | 示例 |
| --- | --- | --- |
| `${CURRENT_USER_ID}` | 当前登录人 ID | 「我创建的」=`fieldCreatorId EQ ${CURRENT_USER_ID}` |
| `${CURRENT_DATE}` | 当天 `yyyy-MM-dd` | 「本周日程」可组合 `GE ${CURRENT_DATE}` |
| `${CURRENT_DATETIME}` | 当前时间 `yyyy-MM-dd HH:mm:ss` | 「进行中」类条件 |

【用户日程】的固定条件落库 JSON：

```json
[ { "key": "fieldCreatorId", "op": "EQ", "value": "${CURRENT_USER_ID}" } ]
```

返回字段落库 JSON（不配 = 默认全字段）：

```json
[ "fieldId", "fieldName", "fieldStartTime", "fieldEndTime", "fieldType" ]
```

## 3. 总体架构与执行流程

### 3.1 架构图

```text
消费方（页面/通用组件）
   │  POST /backend/sys/datasource/query  { code, body(调用方条件), pages, sortField, sortOrder }
   ▼
SysDatasourceController ── authorize(sys.datasource.query)          ← DatasourceResolver：登录即可
   ▼
SysDatasourceService#execute(code, ...)
   ├─ ① 解析数据源：code 命中 Registry 默认数据源，否则查 sys_datasource（CUSTOM，须启用）
   ├─ ② 委托鉴权：AuthorizationHelper.authorize(provider.getTargetResolver(),
   │            new AuthorizationContext(provider.getTargetAction()))   ← 如 sys.calendar.list → CalendarResolver
   ├─ ③ 条件合并：解析固定条件变量 → 校验 key ∈ Provider 条件白名单、op 合法、
   │            字面量限制（literalAllowed=false 只收变量）→ 固定条件覆盖调用方同名条件
   ├─ ④ 执行查询：provider.query(conditions, pages, sortField, sortOrder) → rows + total
   │            （日程 Provider → SysCalendarMainService / Dao → selectCalendarList，数据边界不变）
   ├─ ⑤ 字段投影：FieldProjector.project(row, fields) → List<Map<String,Object>>
   └─ ⑥ BaseResponse：data = 行列表，metadata = { total, fields }（fields 回传实际输出列，供渲染表头）

配置面（管理人员）：GET targets（能力 + 条件/字段定义）→ 管理页配置 → save/update/enable/delete → sys_datasource
读取面（消费方）  ：GET options（默认 + 自定义启用，含 code/name/fields）→ 下拉 / 组件渲染
```

### 3.2 以【用户日程】为例的执行时序

```text
前端某列表组件（code = "calendar.my-created"，用户输入标题过滤 "周报"，第 1 页 20 条）
  → POST /backend/sys/datasource/query
      { "code": "calendar.my-created",
        "body": { "fieldName": "周报" },
        "pages": { "pageNo": 1, "pageSize": 20, "needPage": true },
        "sortField": "startTime", "sortOrder": "desc" }
  → 数据源模块：
      sys_datasource 命中 CUSTOM 行 → target=calendar.list → SysCalendarDatasourceProvider
      委托鉴权 sys.calendar.list（登录即可 → 放行）
      固定条件 fieldCreatorId=${CURRENT_USER_ID} 解析为当前用户 ID（覆盖调用方同名条件）
      合并调用方条件 fieldName=周报 → SysCalendarQuery{ fieldName, fieldCreatorId }
      SysCalendarMainService.list(...)（沿用「本人创建 OR 本人接收」边界，再收紧 creator=我）
      FieldProjector 按 [fieldId, fieldName, fieldStartTime, fieldEndTime, fieldType] 投影
  → 响应 { data: [ {...5 列} ], metadata: { total, fields: [...5 列] } }
```

索引：

| 表 | 索引 | 用途 |
| --- | --- | --- |
| `sys_datasource` | `UNIQUE KEY uk_datasource_code (field_code)` | 编码全局唯一（默认数据源不入库，编码空间共用） |
| `sys_datasource` | `KEY idx_datasource_target (field_target)` | 按目标能力检索数据源、目标能力下线前的影响面检查 |

说明：

- 默认数据源**不落库**，仅存在于 `SysDatasourceRegistry` 进程内缓存；`field_code` 查重时须同时排除默认数据源编码，避免自定义数据源伪装默认源。
- `field_conditions` / `field_fields` 对齐 `sys_number_rule.field_rule` 先例：存储态与列表响应为原文 JSON 字符串（模型字段 `Object`），load 响应与 save/update 请求体为解析后的对象，禁止手工拼串。
- `field_target` 保存后锁定（同 `sys_number_rule.field_model_id` D3 先例）：改目标会使既有条件/字段白名单悬空。

## 5. 接口设计

统一前缀 `/backend/sys/datasource`；请求体 `{ body, pages: { pageNo, pageSize, needPage } }`，总数经 `metadata.total`；响应统一 `BaseResponse`。

### 5.1 接口清单

| 接口 | 方法 | 鉴权动作 | 鉴权口径 |
| --- | --- | --- | --- |
| `/list` | POST | `sys.datasource.list` | `SYS_DATASOURCE_ADMIN`（自定义数据源管理列表，分页） |
| `/load?fieldId=` | GET | `sys.datasource.load` | `SYS_DATASOURCE_ADMIN` |
| `/save` | POST | `sys.datasource.save` | `SYS_DATASOURCE_ADMIN` |
| `/update` | PATCH | `sys.datasource.update` | `SYS_DATASOURCE_ADMIN` |
| `/enable` | PATCH | `sys.datasource.enable` | `SYS_DATASOURCE_ADMIN`（请求体 `{ fieldId, fieldEnable }`） |
| `/delete?fieldId=` | DELETE | `sys.datasource.delete` | `SYS_DATASOURCE_ADMIN` |
| `/options` | GET | `sys.datasource.options` | 登录即可（数据源下拉：默认数据源 + 启用的自定义数据源，含解析后返回字段定义） |
| `/targets` | GET | `sys.datasource.targets` | 登录即可（目标查询能力清单 + 条件/返回字段定义，配置表单数据源；管理菜单入口仅对管理员展示） |
| `/query` | POST | `sys.datasource.query` | 登录即可 + **执行期委托目标 action 鉴权**（见 §5.2） |

权限码 `SYS_DATASOURCE_ADMIN` 增补进 `properties/sys/datasource/roles.yml`（`ROLE_LIST` + `ROLE_MAP`，随库 `sys_org_auth` 由既有启动任务增量同步）。

### 5.2 执行期鉴权委托

`DatasourceResolver` 只管数据源模块自身 action（管理分支 `hasAnyRole(SYS_DATASOURCE_ADMIN)`，options/targets/query 分支 `resolveLoggedIn()`；`SYS_ADMIN` 由 `BaseResolver` 自动放行，不重复列举）。
**目标接口的鉴权不省略**：`SysDatasourceService#execute` 在查询前调用

```java
authorizationHelper.authorize(provider.getTargetResolver(),
        new AuthorizationContext(provider.getTargetAction()));
```

未登录抛 `UNAUTHORIZED`、无权限抛 `FORBIDDEN`，拒绝事件照常进入安全审计。日程示例中即等价于 `CalendarResolver#resolve(sys.calendar.list)`。

### 5.3 `/query` 请求与响应契约

```jsonc
// 请求体
{
  "code": "calendar.my-created",                       // 数据源编码（默认或自定义）
  "body": { "fieldName": "周报", "fieldType": "PERSONAL" },  // 调用方过滤条件（固定条件同名覆盖之）
  "pages": { "pageNo": 1, "pageSize": 20, "needPage": true },
  "sortField": "startTime", "sortOrder": "desc"        // 须 ∈ Provider 可排序字段白名单
}

// 响应（BaseResponse）
{
  "code": "SUCCESS",
  "data": [ { "fieldId": "...", "fieldName": "周报例会", "fieldStartTime": "...", "fieldEndTime": "...", "fieldType": "PERSONAL" } ],
  "metadata": { "total": 3, "fields": ["fieldId", "fieldName", "fieldStartTime", "fieldEndTime", "fieldType"] }
}
```

错误语义（新增异常码，风格对齐 `CRM_NUMBER_*`）：

| 码 | 场景 |
| --- | --- |
| `CS_DATASOURCE_NOT_FOUND` | code 不存在或自定义数据源已停用 |
| `CS_DATASOURCE_TARGET_INVALID` | 自定义数据源挂接的目标能力编码不在 Registry（Provider 下线残留） |
| `CS_DATASOURCE_CONDITION_INVALID` | 条件 key 不在白名单 / op 不支持 / 字面量被禁止 / 值类型非法 |
| `CS_DATASOURCE_FIELD_INVALID` | 返回字段白名单含目标能力不存在的字段 |
| `CS_DATASOURCE_CODE_DUPLICATED` | 保存时编码与既有（含默认数据源）重复 |

## 6. 安全设计

1. **执行收口（A1）**：前端只持有 `code` 与可用的字段/条件定义（`options` 返回），不返回固定条件原文给非管理员——固定条件属于服务端强制语义，不是可协商参数。
2. **能力白名单（A2）**：`field_target` 只能取 Registry 中存在的能力编码；save 时校验，启动时对失效 target 输出 WARN（对齐 `SysNumberModelCacheService#warnInvalidModelIds` 先例）。
3. **条件白名单（A7）**：`key` 必须命中 Provider `conditionFields`；`op` 在字段声明范围内；`literalAllowed=false` 的字段只接受运行时变量值（`fieldCreatorId` 即此类），字面量一律拒绝。
4. **固定条件不可覆盖**：合并策略为固定条件优先，调用方 `body` 中同名 key 直接丢弃。
5. **投影安全（A4）**：复用 `FieldProjector`——属性名正则 `[a-z][a-zA-Z0-9]*` 天然排除 `class` 等系统方法；白名单还须经 Provider `resultFields` 校验（`CS_DATASOURCE_FIELD_INVALID`），未命中字段不输出。
6. **排序白名单**：`sortField` 必须命中 Provider 声明的可排序字段（由 `conditionFields`/`resultFields` 的 `sortable` 标记汇总），非法值回退目标能力默认排序，不进入 SQL 拼接。
7. **数据边界不放宽（A5）**：目标能力的固定数据边界（日程：本人创建 OR 本人接收）在 Mapper 固定段保留；数据源条件只允许在边界内收紧。

## 9. 范围边界与后续演进

**v1.8 范围内**：列表型（可分页、可单条件排序）查询数据源；默认数据源（Provider）+ 自定义数据源（单表 JSON）；统一执行入口与两段鉴权。

**明确不做（后续演进）**：

| 演进项 | 说明 |
| --- | --- |
| 跨数据源关联/join | 涉及执行计划与权限叠加，先不做 |
| 写类数据源 | 数据源只读，写操作仍走各模块 save/update/delete |
| SQL 直配数据源 | 安全面过大，永久排除；取数一律经 Provider 代码 |
| 外系统 HTTP（REST）数据源 | 可在 `SysDatasourceProvider` 之外增加 `RestDatasourceProvider` 类型，属 v1.9+ 议题（对应 `预期开发顺序.md` 的集成接口中心 1.6） |
| 数据源试运行/预览接口 | 管理页「预览」可复用 `/query`（管理员预判），暂不单设接口 |
| 与字段级可见性结合 | `FieldProjector` 同源；`docs/字段级可见性设计方案.md` 落地后，数据源投影可叠加按角色可见性 |

**待确认（TBD，实现前须裁决）**：

1. 码值/枚举字段的翻译（如 `fieldType` PERSONAL/TEAM → 显示名）由数据源统一翻译输出，还是消费方按码值模块自行翻译？建议：消费方翻译（保持数据源「纯投影」语义），待 UI 文档确认。
2. 默认数据源是否允许被自定义数据源引用为目标（当前设计：是，Provider 能力即目标）；若未来默认数据源携带固定条件，需明确「固定条件叠加」合并顺序。
3. 自定义数据源的可见范围（当前设计：全员可用启用的数据源；是否需要按角色限制消费，待需求补充）。
