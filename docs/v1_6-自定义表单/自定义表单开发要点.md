# 企业级 OA 系统：动态表单功能开发步骤

对于一套基于 **Spring Boot + Vue 的企业级 OA / BPM 系统**，建议将动态表单设计成一个独立的基础模块，而不是简单地做成一个表单设计器。

动态表单的核心目标是：

1. 管理员可以通过拖拽组件设计表单。
2. 表单可以配置字段属性、校验规则和联动规则。
3. 支持明细表、子表、多级嵌套表格。
4. 支持动态显隐、条件显隐、字段联动。
5. 支持 JavaScript 响应函数或自定义代码块。
6. 表单能够接入 BPM 流程，支持不同节点设置不同表单权限。
7. 表单定义可以发布、版本管理、回滚。
8. 后端能够动态解析、校验和保存表单数据。

我建议按照 **表单引擎 + 表单渲染器 + 规则引擎 + 数据引擎 + BPM 适配层** 五个部分进行开发。

## 一、整体架构设计

**① 表单设计器 Form Designer**

拖拽组件 · 属性配置 · 规则配置 · 预览 · 发布

**② 表单渲染器**

组件解析 · 数据绑定 · 表单展示

**③ 规则引擎**

显隐 · 联动 · 校验 · 响应函数

**④ 数据引擎**

数据模型 · 保存 · 查询 · 校验

**⑤ BPM 适配层**

流程权限 · 节点表单 · 审批数据

**Spring Boot 后端服务 + 数据库**

## 二、具体开发步骤

建议按照以下顺序实施。

### 第 1 步：建立表单组件体系

首先确定表单设计器支持哪些组件，组件应采用统一注册机制。

| 组件分类  | 具体组件            |
| ----- | --------------- |
| 基础输入  | 单行文本、多行文本、数字、密码 |
| 选择组件  | 下拉框、单选、多选、开关    |
| 日期组件  | 日期、时间、日期范围      |
| 人员组件  | 员工、部门、岗位、角色     |
| 数据组件  | 数据选择器、关联数据、自动编号 |
| 高级组件  | 富文本、附件、图片、地图    |
| 布局组件  | 分组、栅格、标签页、折叠面板  |
| 明细组件  | 明细表、子表、嵌套明细表    |
| 自定义组件 | 自定义 Vue 组件      |

**重点：组件必须具备统一的元数据定义。**

例如：

```
{
  type: "input",
  name: "input",
  label: "单行文本",
  category: "basic",
  icon: "edit",
  defaultProps: {
    placeholder: "请输入",
    required: false,
    disabled: false,
    readonly: false,
    clearable: true,
    maxlength: 200
  }
}
```

每个组件还应提供：

- 设计器配置面板。
- 运行时 Vue 组件。
- 属性定义。
- 默认值生成器。
- 数据类型定义。
- 校验器。
- 数据序列化和反序列化方法。

### 第 2 步：开发表单设计器

表单设计器建议分成三个区域：

| 区域     | 功能            |
| ------ | ------------- |
| 左侧组件栏  | 拖拽表单组件        |
| 中间设计画布 | 组件布局、排序、复制、删除 |
| 右侧属性面板 | 配置组件属性和规则     |

需要实现的功能：

1. 组件拖拽。
2. 组件排序。
3. 组件复制、删除。
4. 属性编辑。
5. 布局调整。
6. 撤销、重做。
7. 表单预览。
8. JSON 配置导入导出。

这里最重要的是：**设计器最终输出统一的 JSON Schema，而不是直接生成 Vue 页面代码。**

例如：

```
{
  "formId": "purchase_form",
  "formName": "采购申请表",
  "version": 1,
  "fields": [
    {
      "field": "applicant",
      "type": "input",
      "label": "申请人",
      "required": true
    },
    {
      "field": "amount",
      "type": "number",
      "label": "采购金额",
      "required": true
    },
    {
      "field": "reason",
      "type": "textarea",
      "label": "采购原因",
      "required": true
    }
  ]
}
```

### 第 3 步：开发动态表单渲染器

这是整个系统的核心。

设计器负责生成 JSON，渲染器负责根据 JSON 动态生成 Vue 组件。

建议采用组件注册表：

```
const componentRegistry = {
  input: InputWidget,
  number: NumberWidget,
  select: SelectWidget,
  date: DateWidget,
  textarea: TextareaWidget,
  employee: EmployeeWidget,
  department: DepartmentWidget,
  detailTable: DetailTableWidget
};
```

渲染器根据字段类型加载组件：

```
<component
  :is="componentRegistry[field.type]"
  v-model="formData[field.field]"
  v-bind="field.props"
/>
```

实际开发还需要补充：

- 字段初始化。
- 默认值处理。
- 字段数据绑定。
- 组件事件统一分发。
- 表单重置。
- 数据回显。
- 组件级权限。
- 动态组件加载。

建议将渲染器设计成独立 Vue 模块，设计器预览、普通表单填写、BPM 审批页面都复用同一套渲染器。

### 第 4 步：开发动态规则引擎

这是动态表单区别于普通表单的关键。

建议将规则分成四类：

**1. 动态显隐规则**

根据其他字段的值决定当前字段是否显示。

示例：采购金额大于 10000 时，显示总经理审批说明。

---

**2. 字段联动规则**

一个字段变化后，自动更新其他字段。

示例：选择部门后，自动加载该部门负责人。

---

**3. 动态校验规则**

根据条件动态修改必填、范围、正则等校验规则。

示例：选择付款方式为转账时，银行账号必填。

---

**4. 自定义响应函数**

用户通过 JavaScript 编写复杂的业务响应逻辑。

示例：金额变化时，自动计算税额和总金额。

建议统一规则数据结构：

```
{
  "ruleId": "rule_001",
  "event": "change",
  "triggerField": "paymentType",
  "condition": {
    "operator": "equal",
    "value": "transfer"
  },
  "actions": [
    {
      "type": "setRequired",
      "target": "bankAccount",
      "value": true
    },
    {
      "type": "show",
      "target": "bankAccount"
    }
  ]
}
```

规则引擎应当提供统一接口：

```
ruleEngine.register(rule);
ruleEngine.execute(event, formData);
ruleEngine.validate(formData);
```

特别注意：不要把规则直接写死在各个 Vue 组件中，否则后续会难以维护。

### 第 5 步：开发明细表组件

明细表是 OA、ERP、BPM 中非常重要的组件。

例如采购申请：

| 商品名称 | 数量 | 单价   | 金额    |
| ---- | -- | ---- | ----- |
| 电脑   | 2  | 5000 | 10000 |
| 显示器  | 2  | 1000 | 2000  |

需要支持：

- 增加、删除行。
- 行内编辑。
- 行内动态显隐。
- 行内字段联动。
- 行内动态校验。
- 自动计算。
- 合计、平均值等统计。
- 批量导入。
- 子表嵌套。
- 行级权限控制。

数据结构建议：

```
{
  "purchaseDetails": [
    {
      "productName": "电脑",
      "quantity": 2,
      "price": 5000,
      "amount": 10000
    }
  ]
}
```

明细表应该被视为一种特殊的容器组件，内部可以继续使用普通字段组件和规则引擎。

### 第 6 步：开发表单数据管理

表单数据建议与表单定义分离。

主要包括：

- 表单定义。
- 表单版本。
- 表单实例数据。
- 表单附件。
- 表单操作记录。

建议第一阶段采用 JSON 数据存储，便于快速支持不同表单结构。

例如：

```
{
  "formId": "purchase_form",
  "formVersion": 1,
  "businessId": "PUR20260001",
  "data": {
    "applicant": "张三",
    "amount": 12000,
    "reason": "办公设备采购"
  }
}
```

后续如果需要复杂的统计、报表、数据分析，可以增加结构化业务数据映射层，而不是一开始就为每个动态表单创建独立数据库表。

### 第 7 步：开发 BPM 集成

动态表单与 BPM 应当通过适配层连接，而不是互相依赖。

需要支持以下能力：

| 功能     | 说明           |
| ------ | ------------ |
| 流程绑定表单 | 流程定义关联表单版本   |
| 节点字段权限 | 不同节点配置字段读写权限 |
| 节点显隐   | 不同审批节点展示不同字段 |
| 节点必填   | 不同节点设置不同必填项  |
| 审批意见   | 支持独立审批意见组件   |
| 数据回显   | 审批时读取原始表单数据  |
| 流程结束   | 归档表单数据       |

建议字段权限采用：

```
{
  "nodeId": "manager_approval",
  "fieldPermissions": {
    "applicant": "readonly",
    "amount": "readonly",
    "reason": "readonly",
    "approvalComment": "editable"
  }
}
```

这里要特别注意：前端隐藏字段不等于后端禁止访问。字段权限必须在后端提交、读取和审批接口中再次校验。

### 第 8 步：开发表单版本管理

企业级系统必须考虑表单修改后，历史业务数据如何处理。

建议采用不可变版本机制：

```
采购申请表
├── V1.0（已停用）
├── V1.1（已停用）
└── V2.0（当前版本）
```

核心原则：

1. 每次发布产生一个新版本。
2. 已经创建的流程实例继续使用原来的表单版本。
3. 新创建的流程实例使用最新发布版本。
4. 不允许直接修改已经发布的历史版本。
5. 支持版本回滚，但回滚实际是重新发布一个历史版本的副本。

建议将以下信息绑定：

```
流程定义
   └── 表单定义 ID
        └── 表单版本 ID
             └── 表单实例
                  └── 表单数据
```

### 第 9 步：开发后端接口

建议将动态表单独立为一个 Spring Boot 业务模块。

接口可以按照以下方式规划：

| 模块   | 接口                       | 用途     |
| ---- | ------------------------ | ------ |
| 表单管理 | POST /forms              | 创建表单   |
| 表单管理 | PUT /forms/              | 修改草稿   |
| 表单管理 | GET /forms/              | 获取表单   |
| 表单管理 | POST /forms//publish     | 发布表单   |
| 版本管理 | GET /forms//versions     | 获取版本   |
| 版本管理 | POST /forms//rollback    | 版本回滚   |
| 表单数据 | POST /form-data          | 保存表单   |
| 表单数据 | GET /form-data/          | 获取表单数据 |
| 表单数据 | POST /form-data/validate | 动态校验   |
| 组件管理 | GET /form-components     | 获取组件列表 |
| 规则管理 | GET /forms//rules        | 获取规则配置 |

建议后端职责划分：

```
form
├── controller
├── service
├── domain
├── repository
├── engine
│   ├── FormRenderSchemaService
│   ├── FormValidationEngine
│   ├── FormRuleEngine
│   ├── FormDataEngine
│   └── FormPermissionEngine
├── component
└── integration
    └── bpm
```

## 三、关于 JavaScript 响应函数的设计

结合你的需求，我建议专门设计一个代码块组件。

例如：

```
// 当采购数量发生变化时
function onQuantityChange(context) {
    const { row, formData } = context;

    row.amount = row.quantity * row.price;

    return {
        success: true
    };
}
```

响应函数可以支持：

| 事件         | 说明     |
| ---------- | ------ |
| onLoad     | 表单加载   |
| onChange   | 字段值变化  |
| onFocus    | 字段获得焦点 |
| onBlur     | 字段失去焦点 |
| onAdd      | 明细新增   |
| onDelete   | 明细删除   |
| onSubmit   | 表单提交   |
| onValidate | 表单校验   |

建议给代码块提供统一上下文：

```
{
  formData: {},
  field: {},
  value: null,
  oldValue: null,
  row: null,
  rowIndex: null,
  api: {},
  utils: {}
}
```

**重要的安全建议：**

- 不要直接使用 `eval()` 执行管理员配置的 JS。
- 建议使用 QuickJS、GraalJS 等隔离执行环境，或者受限的表达式解释器。
- 限制执行时间、内存、可访问对象。
- 不允许直接访问服务器 JVM、数据库连接及操作系统。
- 后端必须独立执行关键业务校验，不能信任前端 JS 返回结果。
- 如果需要访问业务接口，应使用受权限控制的 API 白名单。

另外，建议将普通规则和 JavaScript 代码块分开：80% 的常见业务通过可视化规则完成，复杂业务再使用代码块。

## 五、建议的实际开发顺序

不要一开始就开发全部功能，建议分成四个阶段。

**第一阶段：基础表单引擎** (优先开发)

建立基本的设计、渲染、保存能力

- 组件注册体系
- 表单拖拽设计器
- 基础属性配置
- JSON Schema
- 动态表单渲染器
- 表单数据保存与回显

---

**第二阶段：动态规则引擎**

建立复杂表单的业务处理能力

- 动态显隐
- 条件显隐
- 字段联动
- 动态校验
- 明细表
- JavaScript 响应函数

---

**第三阶段：企业级管理能力**

建立长期维护和扩展能力

- 表单版本管理
- 自定义组件接入
- 表单权限管理
- 表单模板
- 数据导入导出
- 操作日志

---

**第四阶段：BPM 深度集成**

实现表单与流程的完整业务闭环

- 流程绑定表单
- 节点字段权限
- 节点动态显隐
- 节点动态必填
- 审批数据回显
- 流程数据归档

## 六、我建议特别重视的三个架构问题

这三个问题会直接影响未来系统能否扩展。

**1. 表单设计器与表单渲染器必须分离**

不要让设计器承担运行时渲染职责。两者都依赖统一的组件协议，设计器负责编辑 Schema，渲染器负责解释 Schema。

**2. 规则引擎必须独立**

不要把显隐、联动、校验写入各个字段组件。应该建立统一事件总线：

```
字段值变化
    ↓
事件总线
    ↓
规则引擎
    ↓
匹配相关规则
    ↓
执行规则动作
    ↓
更新表单状态
    ↓
触发后续规则
```

需要处理循环触发、重复执行、依赖顺序和最大执行次数，避免字段 A 更新 B、B 又更新 A 导致无限循环。

**3. 表单数据与业务数据需要分层**

动态表单负责收集和管理数据，具体业务模块负责业务处理。

例如：

```
采购申请表
    ↓
动态表单引擎
    ↓
采购申请业务模块
    ↓
采购订单 / 库存 / 财务
```

不要让动态表单引擎直接承担采购、报销、合同等业务逻辑。

---

## 七、最终推荐的模块结构

结合你的 OA 综合管理平台，我建议将动态表单设计为一个独立模块：

```
动态表单模块
│
├── 表单设计管理
│   ├── 表单设计器
│   ├── 表单模板
│   ├── 表单发布
│   └── 表单版本
│
├── 表单组件管理
│   ├── 基础组件
│   ├── 业务组件
│   ├── 明细组件
│   └── 自定义组件
│
├── 表单运行引擎
│   ├── 表单渲染器
│   ├── 数据绑定
│   ├── 事件总线
│   └── 组件适配
│
├── 表单规则引擎
│   ├── 显隐规则
│   ├── 联动规则
│   ├── 校验规则
│   └── JS 响应函数
│
├── 表单数据管理
│   ├── 数据保存
│   ├── 数据查询
│   ├── 数据校验
│   └── 数据归档
│
└── 表单集成
    ├── BPM
    ├── 组织架构
    ├── 权限系统
    └── 业务模块
```

**我的建议：先把组件协议、JSON Schema、规则引擎和渲染器四个基础设计确定下来，再开始编写具体组件。** 这比先做一个拖拽设计器更重要，因为后续所有扩展能力都建立在这四个基础上。
