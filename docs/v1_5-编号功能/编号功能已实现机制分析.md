# 编号功能已实现机制分析

> 分析基准：当前仓库代码事实（backend / frontend / db/migration），截至 V1_01_043。
> 对比基线：`docs/开发规范.md`（模块表「编号规则 number」）、`docs/系统模块/系统模块需求文档.md` 第 4 章「编号机制模块」、`docs/系统模块/系统模块UI设计文档任务清单.md`（PAGE-SYS-014/015）。
> 结论先行：**需求文档规划的「编号规则（sys_number_rule）」模块完全未实现**；当前系统已实现的「编号」能力是三套分散机制——① 全局 32 位主键 ID 生成（前端预取 + 后端兜底）、② 流程实例编号自动生成、③ 流程节点编号归一，外加一批以 `field_code` 承载、人工/配置来源维护的业务编号字段。

## 1. 现状总览

| # | 机制 | 编号形态 | 生成方 | 唯一性保障 | 状态 |
| --- | --- | --- | --- | --- | --- |
| 1 | 主键 ID（field_id） | 32 位：毫秒时间戳 + UUID v4 补位 | 前端预取（`/initID`）或后端兜底（`BaseModel`） | 主键约束 | 已实现，全局通用 |
| 2 | 流程实例编号 | `P + yyyyMMddHHmmss + 4位随机数`（19 位） | 后端自动（`generateCode`），可传入覆盖 | 无唯一索引、无查重 | 已实现，仅流程模块 |
| 3 | 流程节点编号 | 整数序号（START=1、DRAFT=2、中间顺延、END 置末） | 后端归一（模板保存时） | 模板内逻辑唯一 | 已实现，仅流程模块 |
| 4 | 业务编号字段（field_code） | 人工 / yml 配置来源 | 页面录入、导入导出、启动期同步 | 仅 `sys_org_auth.field_code` 有 UNIQUE KEY；i18n 语言码 Service 层校验 | 已实现，分散在各模块 |
| 5 | 编号规则模块（规则配置、前缀/日期段/流水号/重置周期、预览测试、重置补号） | — | — | — | **未实现**（仅文档规划） |

## 2. 已实现机制明细

### 2.1 全局主键 ID 生成（field_id）

这是全系统唯一的「发号」公共机制，所有继承 `BaseModel` 的实体主键都由它产生；数据库全部表 `field_id VARCHAR(32) PRIMARY KEY`，无自增列。

**生成算法**（`backend/src/main/java/com/eric/base/common/utils/IDUtil.java`）：

- `IDUtil.initID()`：13 位毫秒时间戳 + UUID v4 去横线后取前 19 位，拼接截取为 32 位字符串（`generate()`，`substring(0, 32)`）。
- `IDUtil.initID(String id)`：入参非空且长度等于 32 时原样采纳，否则重新生成——即「校验并初始化」。

**三层落地点**：

| 层 | 位置 | 行为 |
| --- | --- | --- |
| 工具层 | `IDUtil` | 算法本体 |
| 模型层 | `common/base/model/BaseModel.java:23-33` | `initFieldId()`（就地补号并返回）、`setFieldId(fieldId)`（set 时经 `IDUtil.initID(String)` 校验兜底，非 32 位自动重生成） |
| 服务层 | `common/base/service/BaseService.java:67-70` | 保存前 `requireModelId(model)` 调 `model.initFieldId()`，前端漏传 ID 时后端兜底生成 |
| 接口层 | `common/base/controller/InitController.java:50-56` | `GET /backend/common/initID` 返回一个 32 位 ID；无需登录，`@SecurityRequirements` 免鉴权（无 `ACTION_*` 常量） |
| 启动期 | `common/module/service/CommonModuleService.java:121` | 模块注册落库时由后端直接 `IDUtil.initID()` 生成 |

### 2.2 前端「新建先取号」规范（getInitID）

前端新建页/新建弹窗打开时先调 `getInitID()`（`frontend/src/api/common.js:15`，`GET /backend/common/initID`），将 32 位 ID 赋给表单 `fieldId`，随 save 请求提交；遵循 `docs/开发规范.md`「前端新建页/弹窗 fieldId 初始化规范」。

### 2.3 流程实例编号自动生成

`sys/process/service/SysProcessExampleService.java`：

- 生成规则（`generateCode`，1466-1470 行）：`"P" + yyyyMMddHHmmss + %04d 随机数`（`ThreadLocalRandom`），共 19 位。
- 调用点（201 行）：发起流程创建草稿实例时 `example.setFieldCode(StringUtil.isEmpty(code) ? generateCode() : code.trim())`——**code 为空自动生成，非空采纳传入值**（业务单据编号可直接作为流程编号入参）。
- 落库字段：`sys_process_example.field_code VARCHAR(50) DEFAULT NULL`（`V1_01_008__sys_process_example_schema.sql:27`）。
- 边界：**无数据库唯一索引，服务层无查重**；时间戳 + 随机数撞号概率低但无结构性保障，传入 code 亦可重复。

### 2.4 流程节点编号归一

模板侧（`sys/process/service/SysProcessTemplateService.java#validateAndNormalizeNodes`，397-456 行）：

- 归一规则：START=1、DRAFT=2、审批/机器人节点按传入顺序从 3 顺延、END 置末（结束节点编号随节点创建往后顺延）。
- 固定节点（开始/草稿/结束）编号、名称、类型由服务端强制（`toFixedNode`），不保存节点配置。
- 常量定义：`SysProcessConstants` 的 `FIXED_NODE_NO_START = 1`、`FIXED_NODE_NO_DRAFT = 2`（131-133 行）。

实例侧（`SysProcessExampleService.java:212-219`）：创建实例时从模板节点快照复制 `fieldNodeNo`；节点查询一律按 `field_node_no` 升序（`idx_example_node_no` 联合索引 `(field_example_id, field_node_no)`）。流转时按编号顺延找下一节点（1185 行）。

### 2.5 业务编号字段（field_code）来源清单

各表以 `field_code` 承载业务编号，来源分三类：**人工维护 / yml 配置同步 / 自动生成**。目前只有流程编号一类是自动生成（见 2.3）。

| 表.列 | 编号语义 | 来源 | 唯一性 | 代码位置 |
| --- | --- | --- | --- | --- |
| `sys_org_element.field_code` | 组织元素编码（部门/岗位/用户等） | 人工（页面 + 导入导出） | 无唯一索引 | `SysOrgElementService.java:467` |
| `sys_org_role.field_code` | 角色编码 | 人工；启动期管理员角色固定 `admin`（`SysStartupTask.java:180`） | 无唯一索引 | `SysOrgRoleService.java:111,143` |
| `sys_org_auth.field_code` | 权限码 | 启动期 `roles.yml` 同步 + 角色镜像行同步 | **UNIQUE KEY `uk_org_auth_code`**（`V1_01_001__sys_org_schema.sql:95`） | `SysOrgAuthService.java:109,173,184` |
| `sys_dict_type.field_code` | 码值类型编号（如 `yes_no`） | 仅 `dict.yml` 启动同步（类型不可维护） | 普通索引 `idx_dict_type_code` | `SysDictService.java:377-382` |
| `sys_i18n_language.field_code` | 语言码（如 `zh_CN`） | 人工维护 + 启动 yml 同步 | 普通索引；**Service 层 save 前经 `selectByCode` 查重，创建后不可修改** | `SysI18nLanguageService.java:84-90` |
| `sys_process_template.field_code` | 流程模板编号 | 人工（可空，无查重） | 无 | `SysProcessTemplateService.java:175,225` |
| `sys_process_example.field_code` | 流程编号 | **自动生成**（可传入覆盖） | 无（见 2.3） | `SysProcessExampleService.java:201,1467` |
| `sys_org_group` | 群组 | **无编号**：`field_code` 列 NOT NULL 但恒写空串 | — | `SysOrgGroupService.java:524,549` |

同步类编号的其他落点：`SysI18nSyncService.java:142`（语言码启动同步）、`SysDictService`（码值项 `field_value` 人工维护，同类型下码值唯一在 Service 校验）。

| 编号组成（前缀、日期段、流水号长度、重置周期、组织范围匹配） | 未实现；当前唯一自动业务编号是流程编号的「P+时间戳+随机数」，无流水段、无重置周期 |

即：本仓库当前不存在统一取号服务；`docs/开发规范.md` 第 106 行「`field_code` 由编号规则生成」**与现实不符**，现实是人工/yml/单点自动生成三种来源并存。

## 4. 差距与风险

1. **流程编号无唯一性保障**：`sys_process_example.field_code` 无唯一索引、服务层无查重；并发或传入重复 code 时可产生重复编号。若按规划落地 `sys_number_rule`，此点应纳入 `generate` 接口的唯一性约束设计。
2. **主键发号依赖前端预取**：`/initID` 免登录，未登录也可无限取号（无频率限制）；预取后未提交即丢弃的 ID 无回收（ID 无连续性诉求，仅浪费，不影响正确性）。
3. **编号规则规划与现实的映射缺口**：需求中「编号一经正式生成后不允许普通用户改写」「未匹配到规则不得回退前端本地生成」等约束，在当前无规则模块的前提下无对应实现，落地时需明确存量机制（如流程编号）是否切换到统一取号。
4. **文档偏差**：`docs/开发规范.md` 的字段规范（`field_code` 由编号规则生成）与当前实现不一致，v1.5 落地或决定不落地时需同步修订该文档。
