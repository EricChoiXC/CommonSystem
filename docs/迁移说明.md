## 六、ERP 系统接入指引

本工程为独立可运行的 Spring Boot 单体（后端 + 前端骨架），ERP 系统接入公共模块有两种典型方式：

表结构维护方式见 [注解维护表结构设计方案.md](v1_3-数据源/1_3_2-注解维护表结构替换flyway/注解维护表结构设计方案.md)。

1. **作为独立公共服务**：ERP 前后端通过网关 / HTTP 调用本服务的登录认证、组织架构、附件、通知待办、流程、日志、码值等接口；本服务自带数据库表与 Redis 缓存。
2. **作为依赖模块合并**：将本工程后端以 Maven 依赖（或源码合并）方式引入 ERP 工程，共享同一数据库与 Redis；前端按菜单裁剪说明将公共页面并入 ERP 前端路由。

接入时的注意事项：

- **数据库**：本工程表结构由注解同步引擎（`common.source`）管理，启动期只对自身标注表比对/执行，**不再有迁移脚本与版本号**；ERP 侧表由 ERP 自有 Flyway 脚本机制管理，双方互不触碰、无共享序号空间。合并部署时 ERP 侧先完成其脚本执行，CommonSystem 后启动（引擎自比对；`CS_SOURCE_SYNC_MODE` 按 ERP 部署环境取 VALIDATE / INSTALL）。历史 `flyway_schema_history` 留档不读写；ERP 侧若继续使用 Flyway，其历史表归 ERP 口径。
- **环境变量**：本工程环境变量前缀为 `CS_*`（如 `CS_DB_PASSWORD`）；若部署环境沿用 `ERP_*` 前缀，需在部署配置中补齐映射。
- **配置键**：附件存储路径配置键为 `common.att.storage-path`，ERP 侧原 `erp.att.storage-path` 需同步改名或双写。
- **前端存储键**：本工程使用 `common_token` / `common_visited_tabs`；与 ERP 前端同域名共存时注意键名冲突与互踢问题。
- **启动任务**：本工程 `SysStartupTask` 不含 `ErpMdmBizTypeLoader`；ERP 工程合并本模块后，该任务保留在 ERP 侧自行注册。
- **命名还原**：如需把本工程的增量改动同步回 ERP 工程，按第四章对照表反向替换（`com.eric.base` → `com.project.backend` 等）。

## 七、流程通知收口与配置消费（v1_7，P17-BE-014）

v1_7 起流程模块对通知待办/待阅的发送统一收口（现状核对报告建议 5），接入方（如 ERP 业务模块）需关注以下两点。

### 1. 配置键消费收口（本批无新增键）

- **无新增配置键**：本批消费的均为既有配置——`process.finish_notify_handler`（流程办结通知审批人，缺省 true）与 `notify.*` 6 个标题模板（既有 4 项 + v1_7 前批新增的 `notify_cc_subject` / `notify_expedite_subject`），默认值以 `backend/src/main/resources/properties/sys/process/application.yml` SETTING 段为准，可经「流程管理-公共配置」页维护。
- **消费方收口**：全部流程通知经共享组件 `ProcessNotifySender`（backend `sys/process/service/engine` 包）统一发送，消费映射：
  - `notify_handle_subject`（审批待办，TODO）：引擎生成「实际需审批（PROCESSING）」审批工作项时发送；
  - `notify_refuse_subject`（被驳回待办，TODO）：Service 驳回动作发送（标题占位符 `${fieldHandlerName}` = 驳回人姓名，v1_7 新增占位符）；
  - `notify_finish_drafter_subject` / `notify_finish_handler_subject`（办结待阅，READ）：引擎办结（`enterEnd`）与管理员终审通过发送；**审批人待阅受 `process.finish_notify_handler` 控制（false 关闭），起草人待阅始终发送**；ABANDON 终态（作废/废弃）不发办结待阅；
  - `notify_cc_subject` / `notify_expedite_subject`（抄送/催办待阅，READ）：抄送节点、抄送动作与催办动作发送（v1_7 前批已落地）。
- 触发点与收件人口径详见 [流程核心业务.md](设计文档/sys/process/流程核心业务.md)「通知」章节「实现补充（P17-BE-014）」。

### 2. 业务侧重复发送兼容策略（风险 R05，不强制下线）

- **风险**：现状「接入流程的业务模块自行发送待办/待阅」的分散模式下，业务模块可能已自行发送审批待办、被驳回待办与办结待阅；v1_7 引擎收口后若业务侧仍保留自发通知，同一事件会产生重复通知。
- **策略：不强制下线**。建议接入方按下表按需切换（切换 = 删除业务模块对应自发通知代码，无需其他改造）：

| 通知 | 引擎收口后 | 业务侧建议 |
| --- | --- | --- |
| 审批待办（notify_handle_subject） | 引擎生成审批工作项时统一发送 | **建议下线**自发发送，避免重复 |
| 被驳回待办（notify_refuse_subject） | 驳回动作统一发送起草人 | **建议下线**自发发送 |
| 办结待阅（notify_finish_drafter_subject） | 办结（FINISH）统一发送起草人 | **建议下线**自发发送 |
| 办结审批人待阅（notify_finish_handler_subject） | 办结统一发送实际审批人，受 `finish_notify_handler` 控制 | **建议下线**；如业务侧需保留补充通知，可置 `finish_notify_handler=false` 关闭引擎侧发送以避免重复 |
| 抄送/催办待阅（notify_cc_subject / notify_expedite_subject） | 抄送/催办动作统一发送 | v1_7 新增能力，业务侧无需自行实现 |
| 业务专属通知（如业务状态变更提醒） | 引擎不涉及 | 不受影响，可继续经 `NotifySendEvent` 自行发送 |
