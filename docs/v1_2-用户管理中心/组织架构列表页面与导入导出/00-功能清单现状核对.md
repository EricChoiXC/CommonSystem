# 组织架构模块功能清单核对报告

- **核对日期**：2026-11-09
- **核对范围**：本仓库（CommonSystem）组织架构模块 `sys/org` 的后端接口、数据模型、前端页面
- **对照基准**：v1_2 用户管理中心功能清单（用户管理 / 账号管理 / 用户档案 / 用户关系 / 用户状态 / 用户组管理 / 个人中心）
- **文档定位**：v1_2 现状调研结论，作为后续需求 / UI / API / 数据库设计的输入

## 一、核对方法

三方面交叉核对，任一方面缺失即视为未完成：

1. **后端**：`backend/src/main/java/com/common/system/sys/org/` 下 Controller 接口、Service 业务逻辑、resolver 鉴权分支；
2. **数据模型**：`db/migration/V1_01_001__sys_org_schema.sql`、`V1_01_039__sys_org_group_schema.sql` 表结构与实体字段；
3. **前端**：`frontend/src/api/org.js` 封装、`views/org/` 页面、`router/index.js` 路由。

图例：✅ 已实现 ｜ ⚠️ 部分实现 / 仅有模型 ｜ ❌ 未实现。

## 二、总体结论

- 用户管理的**核心 CRUD、用户组管理（v1.1 新增）、用户关系（部门/岗位/角色）**已实现；
- **用户导入导出、账号锁定机制、个人头像、扩展属性、个人中心整套功能**未实现或仅有数据模型；
- 本项目**没有独立的「用户管理」页面**：人员作为组织架构树（`sys_org_element.field_org_type = 3`）中的一类，在 `OrgManageView.vue` 中统一管理；前端 `api/org.js` 未封装 user 系列 CRUD 接口（仅 `changePwd`），页面实际走 `element/save|update|delete|load` 通用接口。

## 三、分模块核对

### 3.1 用户管理

| 功能 | 状态 | 现状依据 |
| --- | --- | --- |
| 用户列表 | ✅ | `POST /backend/sys/org/user/list`（`SysOrgUserController`），带分页、字段级可见性裁剪（`UserResolver#loadVisibleResult`） |
| 用户新增 | ✅ | `POST /user/save`；登录名格式校验（禁邮箱格式/11 位纯数字）、邮箱/电话唯一性校验、BCrypt 加密 |
| 用户编辑 | ✅ | `PATCH /user/update`；请求携带的密码被忽略（改密走独立接口） |
| 用户删除 | ✅ | `DELETE /user/delete`；仅 `SYS_ORG_ADMIN` / `SYS_ORG_USER_MANAGER` |
| 用户详情 | ✅ | `GET /user/load?fieldId=`；按可见字段集裁剪返回 |
| 用户导入 | ❌ | 无接口。`SysOrgUserProperties` 已预留 `ACTION_IMPORT` 常量但无实现；EasyExcel 目前仅用于 i18n 模块 |
| 用户导出 | ❌ | 同上，`ACTION_EXPORT` 已定义未实现 |

### 3.2 账号管理

| 功能 | 状态 | 现状依据 |
| --- | --- | --- |
| 账号创建 | ✅ | 保存人员时填 `field_login_name` + 密码；`uk_org_user_login_name` 唯一约束 |
| 账号绑定 | ❌ | 无第三方账号（微信/钉钉/OAuth）绑定功能；仅有登录名/邮箱/电话唯一性校验 |
| 账号启停 | ✅ | `field_enable` 经 `element/enable` 停用/启用，登录时校验拦截（「账号已被禁用」） |
| 账号锁定 | ⚠️ 仅模型 | `SysOrgAccountStatus.LOCKED(2)` 存在且登录时拦截非 NORMAL 状态；但**无登录失败自动锁定逻辑、无手动锁定/解锁接口**，该状态实际置不上。配置键已预留未消费：yml `SETTING.system` 中有 `login_open_lock` / `login_lock_time` / `login_locking_time`，会同步到 `common_setting`，但后端主代码无任何消费方 |
| 密码重置 | ⚠️ 部分 | 管理员可经 `user/changePwd` 代改（`OrgFormView`/`OrgDetailView` 弹窗入口）；无「重置随机密码 / 邮件重置链接」流程 |
| 密码策略 | ⚠️ 部分 | 已有：长度 6–32 校验（`SysOrgUserService` 硬编码常量）、`pwd_change_cycle` 定期改密 + `checkPwdChange` 强制改密、`pwd_repeat_limit` 不可重复次数（`common_setting`，yml 默认 3）。**缺**：密码复杂度（大小写/数字/特殊字符）校验 |

### 3.3 用户档案

| 功能 | 状态 | 现状依据 |
| --- | --- | --- |
| 基本信息 | ✅ | `sys_org_element`（姓名/编码/层级）+ `sys_org_user`（性别/生日/在职状态） |
| 联系方式 | ✅ | `field_phone` / `field_email` / `field_address` |
| 个人头像 | ❌ | 无 avatar 字段、无上传入口（附件模块 `sys/att` 未与用户关联） |
| 个人资料 | ⚠️ 部分 | resolver 允许本人 `user/update`（后端具备）；**无独立个人资料自助页面**，仅管理员代改入口 |
| 扩展属性 | ❌ | 无自定义扩展字段机制（无 ext JSON 列、无扩展属性表） |

### 3.4 用户关系

| 功能 | 状态 | 现状依据 |
| --- | --- | --- |
| 用户部门关系 | ✅ | `sys_org_element` 树：人员节点 `field_parent_id` 挂在部门下 |
| 用户岗位关系 | ✅ | `sys_org_post_user` 关联表；登录返回 `user.posts` |
| 用户角色关系 | ✅ | 经 `sys_org_role_element`（角色↔组织元素）间接授权；登录组装 `roles`/`auths`。注意：**无「用户↔角色」直接关联表**，形态是角色绑定组织节点 |
| 直属上级关系 | ⚠️ 隐式 | 机构/部门/岗位有 `field_leader_id` 负责人字段，可沿树推导；**无显式直属上级字段/关系表** |

### 3.5 用户状态

| 功能 | 状态 | 现状依据 |
| --- | --- | --- |
| 在职 | ✅ | `field_job_status = 1`（`SysOrgJobStatus.WORKING`） |
| 离职 | ✅ | `= 0`（`LEAVE`） |
| 停用 | ✅ | `field_enable`（前端「停用/启用」按钮）+ `field_account_status = 0`（`DISABLED` 禁用） |
| 冻结 | ⚠️ 仅模型 | 同账号锁定：`LOCKED(2)` 无操作入口 |
| 待激活 | ❌ | 无此状态值、无激活流程；另有 `CANCELED(4)` 注销同样无操作入口 |

与清单口径差异：`SysOrgJobStatus` 实际枚举为 **在职 / 离职 / 停职 / 休假**，与清单的「在职/离职/停用/冻结/待激活」维度不同（后者偏账号状态，前者偏在职状态），v1_2 设计需先对齐口径。

### 3.6 用户组管理（组织架构 v1.1，`V1_01_039`）

| 功能 | 状态 | 现状依据 |
| --- | --- | --- |
| 用户组创建 | ✅ | `POST /sys/org/group/save`；`PERSONAL` / `COMMON` 两类 |
| 用户组维护 | ✅ | `group/load|update|delete`；删除为四表同事务（成员明细 → 可见范围明细 → 群组扩展行 → 主行） |
| 成员管理 | ✅ | `sys_org_group_user` 明细，保存全量替换（先删后插）；成员须为存在且启用的人员 |
| 用户组授权 | ⚠️ 部分 | 有「可见范围」`sys_org_group_viewer`（谁能看到该群组）；**没有把用户组作为授权主体分配角色/权限**的能力。另注意 `GroupResolver` 对 list/load/save/update/delete 全放行，群组无专门权限码 |

### 3.7 个人中心

| 功能 | 状态 | 现状依据 |
| --- | --- | --- |
| 个人资料 | ❌ | 无 `/profile` 类路由、无个人中心页面 |
| 修改密码 | ✅（挂在别处） | `user/changePwd` + `ChangePwdDialog` 组件 + 强制改密页 `ForceChangePwdView`（`/changePwd`）；入口在管理页/强制改密流程，非个人中心 |
| 登录设备 | ❌ | `LoginSessionService` 仅是内存中 token→userId+过期时间映射；无设备信息记录、无会话列表/踢出接口 |
| 个人偏好 | ❌ | 无 |
| 消息设置 | ❌ | 无（notify 模块也无偏好设置接口） |

## 四、差距汇总

### 4.1 完全缺失

- 用户导入 / 导出（`ACTION_IMPORT` / `ACTION_EXPORT` 常量已预留，无接口无页面）；
- 账号绑定（第三方账号）；
- 登录失败自动锁定与解锁（yml 已预留 `login_open_lock` / `login_lock_time` / `login_locking_time` 配置键，主代码未消费）；
- 待激活状态及激活流程；
- 个人头像；
- 扩展属性；
- 个人中心整套（个人资料页 / 登录设备 / 个人偏好 / 消息设置）。

### 4.2 仅有数据模型或半成品

| 项 | 已有 | 缺口 |
| --- | --- | --- |
| 账号锁定 | `LOCKED(2)` 枚举、登录拦截；yml 预留 `login_open_lock` / `login_lock_time` / `login_locking_time` 配置键（已同步 `common_setting`，主代码未消费） | 失败计数、自动锁定、手动锁定/解锁接口与页面操作 |
| 密码复杂度策略 | 长度 6–32 校验（硬编码） | 复杂度规则可配置化（大小写/数字/特殊字符） |
| 密码重置流程 | 管理员代改（changePwd） | 随机初始密码重置、自助找回（邮件/短信） |
| 直属上级关系 | `field_leader_id` 负责人字段 | 显式直属上级字段或推导规则文档化 |
| 用户组授权 | 可见范围（viewer） | 以用户组为授权主体的角色/权限分配 |
| 个人自助改密 | 后端 resolver 放行本人 | 个人中心入口页面 |

### 4.3 实现形态差异（设计时需对齐）

- **无独立用户管理页**：人员融合在组织架构树中管理；v1_2 若要做独立用户管理列表，需先补 UI 文档明确两者关系；
- **角色授权形态**：现有「角色↔组织元素」（`sys_org_role_element`），无「角色↔用户」直接关联；清单中「用户角色关系」按现有形态视为已覆盖；
- **用户组授权语义**：现仅为可见范围控制，清单中「用户组授权」若指权限分配则为缺口;
- **前端 API 封装**：`api/org.js` 未封装 user 系列 CRUD（仅 `changePwd`），页面走 element 通用接口；v1_2 增加用户专属功能时建议同步补齐封装；
- **群组权限码缺失**：群组五类操作在 `GroupResolver` 全放行，未定义 `SYS_ORG_GROUP_*` 细分权限码（`roles.yml` 仅 `SYS_ORG_GROUP_ADMIN`）。

## 五、后续建议

1. **先对齐口径**：在职状态与账号状态两套维度（`field_job_status` / `field_account_status`）与清单「用户状态」的映射关系，需在需求文档中明确；
2. **按规范补设计文档**：缺口项按 开发顺序 需求 → UI → API → 数据库 → 代码与迁移脚本 推进，迁移脚本从 `V1_01_041` 起递增（当前最新 `V1_01_040`）；
3. **导入导出优先复用现有能力**：EasyExcel 已在 i18n 模块有使用先例，用户导入导出可参考其模式；
4. **个人中心建议新增独立模块**：涉及新路由、新菜单（`HomeView.vue` 菜单与 `activeMenu` 同步）、可能新增个人偏好配置存储，建议单独成册设计；
5. **密码复杂度策略落配置**：接入 `common_setting`（`SETTING.system.*`），沿用 `${CS_X:${SETTING.a.b:default}}` 三段式，避免继续硬编码在 `SysOrgUserService`。
