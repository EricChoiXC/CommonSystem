## 1. 检查基线（报文格式规范）

本次检查以以下规范条款为基线（来源：`docs/开发规范.md`「三：系统统一规范」、
`AGENTS.md` 第 3 节，以及 `common/base/model` 既有实现）：

| 编号 | 条款 | 依据 |
| --- | --- | --- |
| J1 | 所有 JSON 接口统一返回 `BaseResponse<T>`（code / message / data / metadata）；异常经 `GlobalExceptionHandler` 统一转换 | `AGENTS.md` 3「接口」 |
| J2 | 列表请求体 `{ body, params, pages: { pageNo, pageSize, needPage } }` | `BaseRequest` / `Pages` |
| J3 | 分页列表总数经 `metadata.total` 返回 | `AGENTS.md` 3「接口」 |
| J4 | 更新只用 PATCH（禁 PUT）、删除用 DELETE、单 id 或无参用 GET、含非 id 条件用 POST | `AGENTS.md` 3「接口」 |
| J5 | 路径 `/backend/{根模块}/{模块}/{次级模块}/{方法}` | `AGENTS.md` 3「接口」 |
| J6 | 鉴权动作用 `ACTION_*` 常量静态引用，`@Operation.description` 以「鉴权动作 …」开头且与实际一致 | `AGENTS.md` 3「接口文档同步（强制）」 |

## 3. 发现的问题

### 3.1 【注解与代码不一致，违反 J6】SysOrgUserController.list 鉴权动作不符

- 位置：`backend/src/main/java/com/common/system/sys/org/controller/SysOrgUserController.java`
  `POST /backend/sys/org/user/list`（方法 `selectList`）。
- 现象：`@Operation.description` 声称「鉴权动作 `sys.org.user.list`」，但代码实际传入
  `ACTION_LOAD`（值 `sys.org.user.load`）；`SysOrgUserProperties.ACTION_LIST` 已定义却未使用。
- 影响：两者在 `UserResolver` 中行为等价（`ACTION_LIST` 落 default 分支「登录即可」，
  `ACTION_LOAD` 在 `resolve(AuthorizationContext)` 中同样落 default → `resolve(String)` 返回 true），
  但注解与代码不符，违反「接口文档同步（强制）」；且使 `ACTION_LIST` 成为死常量。

### 3.2 【报文模式不一致，偏离 J3】SysOrgUserController.list 未返回 metadata.total

- 位置：同 3.1 接口。
- 现象：该方法按 `pages` 做了分页查询（`selectListWithFields(criteria, pages, visibleFields)`），
  却只返回 `data`，`metadata` 为 `null`，是全部 14 个分页列表接口中**唯一不返回总数**的一个。
- 影响：与统一模式不一致；前端当前无调用方（全库检索无 `org/user/list` 引用），影响面为零，
  但该接口是后续人员列表页落地时可直接复用的存量端点，宜在接入前修正。

### 3.3 【规范偏离，灰色地带】带条件的 GET 列表

严格按 J4「含非 id 条件用 POST」，以下两个 GET 列表接口偏离：

| 接口 | 条件 | 现状说明 |
| --- | --- | --- |
| `SysI18nLanguageController.list`（GET `/backend/sys/i18n/language/list`） | `fieldName` / `fieldCode` / `fieldEnable` 均可选的模糊/精确条件 | 已声明「登录页语言下拉需要，免鉴权、不分页全量」；有模糊条件（`fieldName`、`fieldCode`），严格说应 POST |
| `SysDictController.itemList`（GET `/backend/sys/dict/itemList?fieldTypeId=`） | 单值等值条件 `fieldTypeId` | 介于 load（单 id）与 list（多条件）之间，更接近按外键取子表 |

两接口均为「下拉/全量」场景、不分页、无 `total`，与 J3 无冲突；且已随 v1.1 多语言功能
联调验收。属**存量一致性债务**，改方法会破坏已有前端调用，建议保持现状并在此记录决策。

### 3.4 【项目内不统一】save / update 请求体两种形态并存

规范仅对**列表类**请求明确了 `{ body, params, pages }` 包装（J2），保存类请求体无硬性约束，
当前两种形态并存：

- 包装形态 `{ body: 实体 }`：`SysOrgUserRequest`（user save/update/changePwd）、
  `SysI18nLanguageRequest`（language save/update/setDefault）、`SysNotifySendRequest`（notify send）、
  `SysCalendarSaveRequest`（calendar save/update）等；
- 裸实体形态：`SysDictItem`（dict itemSave/itemUpdate）、`SysOrgElementVo`（element save/update/enable）、
  `SysOrgRoleVo`（role save/update）、`SysProcessTemplateVo`（process template save/update/enable/setDefault）、
  `SysTaskMain`（task update）等。

属一致性债务而非违规；如需统一，宜在后续版本立项（涉及全部前端调用点同步改造）。

### 3.5 【轻微】SysI18nTranslationListRequest 的查询条件置于顶层

- 位置：`backend/src/main/java/com/common/system/sys/i18n/request/SysI18nTranslationListRequest.java`。
- 现象：`fieldModel` 与 `body` / `pages` 平级放在顶层，与 J2「body 承载查询条件」的字面语义不同；
  类内 `@Schema` 已自洽声明「顶层 fieldModel 指定模块（与 body / pages 平级）」。
- 影响：仅语义层面；该接口（翻译矩阵）无分页，`pages` 未使用。属设计取舍，记录备查。

### 3.6 【文档误导】BaseResponse 注解提及未使用的错误码 E_DUPLICATE

- 位置：`backend/src/main/java/com/common/system/common/base/model/BaseResponse.java`。
- 现象：`@Schema(description=…)` 列举错误码时写了 `E_DUPLICATE`，全库实际未使用——
  重复键冲突在 `GlobalExceptionHandler#handleDuplicateKey` 中统一映射为
  `BAD_REQUEST`（「数据已存在，请勿重复提交」）。
- 影响：接口文档（springdoc 生成的模型说明）会展示一个不存在的错误码，误导调用方。

## 4. 文档化例外（不算违规）

以下形态偏离 `BaseResponse` / 常规包装，但均有设计文档支撑，检查中确认为**合规例外**：

| 接口 | 形态 | 依据 |
| --- | --- | --- |
| `GET /locales/{code}.json`（`SysI18nLocalesController`） | 返回裸 `Map<String, String>`（vue-i18n 语言包），免鉴权，路径无 `/backend` 前缀 | v1.1 多语言 D2 决策；Vite `vite.config.js` 已配 `/locales` 代理，前端 `stores/language.js` `fetch` 直连 |
| 附件 download / view / adminDownload、翻译 export | `ResponseEntity<Resource>` 文件流 | `AGENTS.md` 3「接口文档同步」对非 JSON 响应的注解要求已满足 |
| `NotifySseController.subscribe` | `SseEmitter` | SSE 订阅属既定设计 |
| `CommonSettingController.update` | 不走 resolver，入口直判 `SYS_ADMIN` | `@Operation` 已注明「无 ACTION 常量（入口直接判 SYS_ADMIN）」 |

## 5. 修复建议

### 5.1 建议修复（同批一处改动，行为无破坏）

3.1 与 3.2 同属 `SysOrgUserController.list`，一个方法内可同时解决：

1. `authorize(ACTION_LOAD, …)` → `authorize(ACTION_LIST, …)`（`UserResolver` 行为不变）；
2. 补 `count` 查询并返回 `Map.of("total", total)`（与其他 13 个分页列表对齐）；
3. 同步核对 `@Operation.description` 与实际鉴权动作一致（改后即为 `sys.org.user.list`）。

> 注：当前 `SysOrgUserService` 仅有 `selectListWithFields`，若无可直接复用的 count 方法，
> 需在 Dao/Mapper 补一个按 `criteria` 统计的查询；`@EqualsAndHashCode(callSuper = false)`
> 等请求类无需变动。

### 5.2 建议保持现状（记录决策即可）

- 3.3 两个 GET 列表：改 POST 会破坏已有前端调用（语言下拉、字典级联），且均非分页场景；
  如后续版本统一请求格式，应连同前端一并改造。
- 3.4 两种请求体形态：涉及全部模块与前端调用点，建议在 v1.2+ 立项统一，不在本次处理。
- 3.5 翻译矩阵顶层 fieldModel：`@Schema` 已自洽，无调用歧义，不动。

### 5.3 建议顺手修正（低风险）

- 3.6 `BaseResponse` 的 `@Schema` 描述：删除 `E_DUPLICATE` 或替换为实际使用的错误码
  （`UNAUTHORIZED` / `FORBIDDEN` / `BAD_REQUEST` / `E_NOT_FOUND` / `ERROR`）。
  注意 `BaseResponse` 的 `@Schema` 是全模型级描述，修改后 `ApiDocsTest` 需回归。
