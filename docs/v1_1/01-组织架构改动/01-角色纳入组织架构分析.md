# 角色纳入组织架构分析（`field_org_type = 5`）

> 对应需求 1.1（R1-1 ~ R1-4）。数据结构遵循 `docs/设计文档/sys/org/组织架构表结构.md`，
> 结论受 `00-改动总览与影响分析.md` 的决策点 D1 ~ D3 约束。

## 1. 现状：角色与组织架构是两套模型

| 维度 | 组织架构元素 | 角色 |
| --- | --- | --- |
| 主表 | `sys_org_element` | `sys_org_role` |
| 主键 | `field_id` VARCHAR(32) | `field_id` VARCHAR(32) |
| 名称/编码 | `field_name` / `field_code` | `field_name` / `field_code` |
| 启用 | `field_enable` | `field_enable` |
| 审计 | `field_creator_id` / `field_create_time` / `field_updater_id` / `field_update_time` | 同 |
| 类型 | `field_org_type`（1~4） | 无 |
| 树字段 | `field_parent_id` / `field_hierarchy` / `field_level` | 无 |
| 关系 | 通过 `sys_org_role_element` 被角色引用 | 同 |

关键结论：**角色已具备 `sys_org_element` 全部公共字段，字段语义完全对齐**，这是能否「纳入子类」的结构基础。
缺口只有三项：`field_org_type` 取值、树字段（角色不参与，置空即可）、以及主表行的存在性。

## 2. 三种落地方案对比

### 方案 A：主表镜像行（推荐）

角色仍以 `sys_org_role` 为业务主表，同时在 `sys_org_element` 维护一条 `field_org_type = 5` 的镜像行，
`field_id` 与角色一致。

```
sys_org_role (field_id=ID1, field_name=项目经理, field_code=SYS_XXX, field_enable=1)
        │ 1:1（同 field_id）
        ▼
sys_org_element (field_id=ID1, field_name=项目经理, field_code=SYS_XXX, field_org_type=5,
                 field_parent_id=NULL, field_hierarchy=NULL, field_level=1, field_enable=1)
```

- 写入时机：`SysOrgRoleService#saveRole` / `#updateRole` 同事务内 upsert 镜像行；`ensureSystemAdminRole` 同步。
- 删除时机：角色当前无删除接口；若后续新增，需同事务删除镜像行。
- 读取时机：角色详情/列表仍读 `sys_org_role`（唯一数据源）；镜像行仅被地址本与类型判定使用。

**优点**

- 「角色是组织架构子类」在数据层成立，`orgTypes=[5]` 语义自然。
- 地址本「角色」页签可完全复用现有 SQL（`selectTree` / `selectList` / `selectByIds`），仅改 `orgTypes` 参数。
- 未来若需要「角色挂到部门」等能力，树字段已就位。

**代价**

- 双写一致性：需要在 Service 层保证；建议在 `SysOrgRoleService` 内封装 `syncElementMirror(...)`，异常时抛出让事务回滚。
- 名称/编码在两张表重复存储，需明确「以 `sys_org_role` 为准」。

### 方案 B：不落主表，地址本直查角色表

- 地址本「角色」页签调用 `POST /backend/sys/org/addressbook/roleList`（内部查 `sys_org_role`）。
- `sys_org_element` 不新增任何行。

**优点**：零迁移、零双写、零一致性风险；存量角色立即可选。
**缺点**：角色在数据层仍不是组织架构元素；`orgTypes` 的语义被撕开一个特例分支；
`AddressBook.vue` 需为角色页签单独维护一套加载/勾选逻辑（现有组件的「树 + 右表」结构可复用右表部分）。

### 方案 C：全量数据迁移

- 一次性脚本把存量 `sys_org_role` 补写为 `field_org_type = 5` 的主表行。

**缺点**：与 R1-2「历史数据不做迁移」直接冲突。**不建议**，除非业务明确改口。

### 结论

推荐 **方案 A**（已确认）。配套要求：

- `SysOrgRoleService` 内新增 `syncElementMirror(SysOrgRole role)`，在 `saveRole` / `updateRole` / `ensureSystemAdminRole`
  中**同事务**调用，异常时抛出让事务回滚；
- 镜像行只同步 `field_name` / `field_code` / `field_enable` / `field_update_time` / `field_updater_id`，
  其余字段固定（`field_org_type = 5`、`field_parent_id = NULL`、`field_hierarchy = NULL`、`field_level = 1`、`field_is_virtual = b'0'`）；
- 「存量角色补齐」做成独立的可选脚本（不纳入 Flyway），由实施方在需要时手工执行。

> 方案 B 仅作为回退备选：若实施中发现双写带来不可接受的一致性维护成本，可切换为「地址本角色页签直查 `sys_org_role`」，
> 此时常量、码值、树排除等改动可全部保留，仅需替换地址本的角色数据源。

### 3.1 镜像行写入示意

```java
/** 角色主表写入后，同事务维护组织架构镜像行（field_org_type = 5） */
private void syncElementMirror(SysOrgRole role) {
    SysOrgElement exist = sysOrgElementDao.selectById(role.getFieldId());
    if (null == exist) {
        SysOrgElement mirror = new SysOrgElement();
        mirror.setFieldId(role.getFieldId());
        mirror.setFieldName(role.getFieldName());
        mirror.setFieldCode(role.getFieldCode());
        mirror.setFieldOrgType(ORG_TYPE_ROLE);
        mirror.setFieldParentId(null);
        mirror.setFieldHierarchy(null);
        mirror.setFieldLevel(1);
        mirror.setFieldIsVirtual(false);
        mirror.setFieldEnable(role.getFieldEnable());
        mirror.setFieldCreatorId(role.getFieldCreatorId());
        mirror.setFieldCreateTime(role.getFieldCreateTime());
        mirror.setFieldUpdaterId(role.getFieldUpdaterId());
        mirror.setFieldUpdateTime(role.getFieldUpdateTime());
        sysOrgElementDao.insert(mirror);
        return;
    }
    exist.setFieldName(role.getFieldName());
    exist.setFieldCode(role.getFieldCode());
    exist.setFieldEnable(role.getFieldEnable());
    exist.setFieldUpdaterId(role.getFieldUpdaterId());
    exist.setFieldUpdateTime(role.getFieldUpdateTime());
    sysOrgElementDao.update(exist);
}
```

> 注意：`SysOrgElementMapper#update` 对 `field_level` / `field_org_type` / `field_is_virtual` 无条件赋值，
> 复用前须确保镜像对象上这三项已正确赋值（上面代码中 `exist` 来自库，已带正确值）；否则建议新增专用
> `updateRoleMirror` 语句，仅更新名称/编码/启用/审计字段，避免误伤。

## 3. 常量与码值

| 位置 | 改动 |
| --- | --- |
| `SysOrgElementProperties` | 新增 `ORG_TYPE_ROLE = 5`；`validateCommon` 的类型范围校验由 `1~4` 调整为按需求允许的类型集合（角色不走该接口，建议改为白名单 `Set` 而非闭区间） |
| `SysOrgAddressBookQuery` 注释 | `orgTypes` 取值说明补 5=角色、6=群组 |
| `dict.yml#org_element_type` | 增加 `5: 角色`、`6: 群组`，并更新 `desc` |
| `api/org.js#resolveOrgTypes` | 明确 `ALL` 是否含 5/6（推荐不含） |

## 4. 树结构排除（R1-4）

角色不参与树 ⇒ 必须在**三处**保证不被当作树节点返回：

1. **地址本 `tree`**：`selectTree` 的根级分支当前是 `field_parent_id IS NULL OR = ''`，镜像行为 `NULL` 会被命中。
   若 `orgTypes` 未传，必须追加 `AND field_org_type <> 5`（群组同理 `<> 6`）。
2. **组织管理页左侧树**：前端固定 `orgTypes: [1, 2]`，天然排除；但后端需兜底剔除非法类型。
3. **组织管理页右侧列表**：`selectVoList` 的 `VoWhereClause` 根级分支同样会命中镜像行，必须追加排除条件。

推荐实现：在 Mapper 中以 `<if>` 追加

```xml
AND field_org_type NOT IN (5, 6)
```

仅对「树/组织管理页」相关语句生效；地址本的「角色/群组页签」通过显式 `orgTypes` 反向包含。

## 5. 地址本「角色」页签（R1-3）

### 5.1 交互形态

现有地址本中层为两个页签（组织架构树 / 查询）。新增第三个页签：

```
┌─ 地址本 ─────────────────────────────────────────────┐
│ [关键字输入框]                    [查询]               │
│ ┌ 组织架构树 ┬ 查询 ┬ 角色 ┐                          │
│ │  角色列表（名称 / 编码 / 是否启用）                   │
│ │  □ 项目经理   SYS_PM     启用                        │
│ │  □ 系统管理员 SYS_ADMIN  启用                        │
│ └────────────────────────────────────────────────────┘ │
│ 已选：[项目经理] [系统管理员]        [取消] [确认]      │
└───────────────────────────────────────────────────────┘
```

- 角色页签**不做左侧树**（角色无层级），仅一张分页表格。
- 是否展示该页签由新增 prop 控制，例如 `showRole`（默认 `false`），或扩展 `orgType` 语义（如 `ROLE` / `ALLROLE`）。
  推荐**新增布尔 prop**，避免 `orgType` 枚举膨胀；`multi` / 单选行为与现有页签一致。
- 选项数据：方案 A 走 `queryAddressBookList({ orgTypes: [5] })`；方案 B 走新增的角色列表接口。
- 是否过滤停用角色：默认**仅显示启用**（与地址本其它类型一致）；编辑回显时按 id 回填不受启用限制（沿用 `selectByIds`）。

### 5.2 与现有勾选合并逻辑的关系

`AddressBook.vue` 已实现「多页签勾选只增不减 + 按 `fieldId` 恢复」的机制（`treeSelectedRows` / `querySelectedRows` / `mergeSelection`）。
角色页签需新增一个 `roleSelectedRows` 与对应的 `handleRoleSelectionChange` + `restoreTableSelection` 分支，
否则切页签会丢失已选角色。

## 6. 角色选择结果的使用场景

| 场景 | 是否应允许选角色 | 说明 |
| --- | --- | --- |
| 组织架构表单「上级」 | ❌ | 「上级」仅限非虚拟机构/部门，`org-type="ORGDEPT"` 已排除 |
| 组织架构表单「负责人」 | ❌ | 负责人必须是人，`org-type="PERSON"` |
| 角色表单「组织架构」 | ❌ | `org-type="ALL"` 不含 5/6（`resolveOrgTypes` 收敛为 `[1,2,3,4]`），不允许「角色挂角色」 |
| 群组「可见用户」 | ❌ | 可见范围是组织架构，不含角色/群组 |
| 流程模板「审批人」 | ❌ | 当前 `org-type="PERSONPOST"`，天然不含角色/群组 |
| 通知待办「接收人」 | ❌ | 当前 `org-type="PERSON"`，天然不含角色/群组 |

结论：**除显式开启角色页签的场景外，其余调用方必须继续排除 5/6**。这是 `resolveOrgTypes` 的 `ALL` 不含 5/6 的主要理由。

## 8. 存量数据补齐脚本（可选，不纳入 Flyway）

如需让存量角色在地址本中可选，可提供 `docs/v1_1/01-组织架构改动/sql/` 下的手工脚本（草案见 `03-数据库改动设计.md` 第 6 节）：

```sql
-- 可选：为存量角色补写组织架构镜像行（手工执行，勿纳入 db/migration）
INSERT INTO sys_org_element
    (field_id, field_name, field_code, field_creator_id, field_create_time,
     field_updater_id, field_update_time, field_enable,
     field_org_type, field_parent_id, field_hierarchy, field_level, field_is_virtual)
SELECT r.field_id, r.field_name, COALESCE(r.field_code, r.field_id),
       r.field_creator_id, r.field_create_time,
       r.field_updater_id, r.field_update_time, r.field_enable,
       5, NULL, NULL, 1, b'0'
FROM sys_org_role r
WHERE NOT EXISTS (SELECT 1 FROM sys_org_element e WHERE e.field_id = r.field_id);
```

执行前须确认：`field_code` 在 `sys_org_element` 无唯一约束（当前无），空编码可用 `field_id` 兜底。
