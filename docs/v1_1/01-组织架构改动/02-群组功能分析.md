# 群组功能分析（`field_org_type = 6`）

> 对应需求 1.2（R2-1 ~ R2-11）。约束见 `00-改动总览与影响分析.md` 决策点 D4 ~ D6。

## 1. 数据模型

### 1.1 三张表的关系

```
sys_org_element (field_org_type = 6, field_parent_id = NULL, 不参与树)
        │ 1:1（同 field_id）
        ▼
sys_org_group (field_id, field_type, field_owner_id, field_is_all_viewer)
        │ 1:N                                    │ 1:N（仅 field_type = COMMON）
        ├── sys_org_group_user  (field_group_id, field_user_id)   成员
        └── sys_org_group_viewer(field_group_id, field_viewer_id) 可见范围节点
```

- `sys_org_group` 与 `sys_org_element` 的 `field_id` 同值，形态与 `sys_org_org` / `sys_org_dept` / `sys_org_post` 一致。
- 成员与可见范围均为明细表，采用**复合主键 + 全量替换**（先删后插），与 `sys_org_role_element` / `sys_org_post_user` 风格一致。
- 群组不参与树：`field_parent_id = NULL`、`field_hierarchy = NULL`、`field_level = 1`。

### 1.2 字段语义

| 表 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| sys_org_group | field_id | VARCHAR(32) PK | 与 `sys_org_element.field_id` 一致 |
| sys_org_group | field_type | VARCHAR(20) NOT NULL | `COMMON` 公共 / `PERSONAL` 个人 |
| sys_org_group | field_owner_id | VARCHAR(32) | 所有人（`PERSONAL` 必填；`COMMON` 可为空或创建人） |
| sys_org_group | field_is_all_viewer | BIT(1) NOT NULL DEFAULT b'1' | 是否全员可见（仅 `COMMON` 有意义） |
| sys_org_group_user | field_group_id | VARCHAR(32) PK 部分 | 群组 ID |
| sys_org_group_user | field_user_id | VARCHAR(32) PK 部分 | 人员 ID（`sys_org_element.field_org_type = 3`） |
| sys_org_group_viewer | field_group_id | VARCHAR(32) PK 部分 | 群组 ID |
| sys_org_group_viewer | field_viewer_id | VARCHAR(32) PK 部分 | 可见范围组织架构节点 ID |

> 命名说明：需求原文只给了 `field_id` / `field_type` / `field_owner_id` / `field_is_all_viewer` 与两张「明细表」，
> 明细表列名未指定。本文按仓库既有命名（`field_<对象>_id`）取 `field_group_id` / `field_user_id` / `field_viewer_id`，
> 最终以 `03-数据库改动设计.md` 的 DDL 为准。

### 1.3 `field_is_all_viewer` 与明细表的关系（D4）

推荐 `field_is_all_viewer` 为**派生冗余字段**（**已确认**），由 Service 计算，规则：

| `sys_org_group_viewer` | `field_is_all_viewer` | 语义 |
| --- | --- | --- |
| 空 | `b'1'` | 全员可见 |
| 非空 | `b'0'` | 仅可见范围（子集） |

好处：查询可见性时可直接用单字段快速判断，无需 `NOT EXISTS` 子查询；
代价：需在保存时统一维护，**前端传入的该字段一律忽略**。

实现约定：

- `SysOrgGroupService#save` / `#update` 在写入明细后统一 `field_is_all_viewer = viewerIds.isEmpty()`；
- `PERSONAL` 类型不写明细，恒为 `b'1'`（字段语义对个人群组无实际作用，但保持非空）；
- 若后续需要「公共群组显式全员可见但保留已选明细」的场景，再改为独立开关（需同步改本节与 `02` 的 SQL 口径）。

## 2. 可见性与维护权限

### 2.1 角色定义（R2-5）

| 角色 | 权限码 | 能力 |
| --- | --- | --- |
| 群组管理员 | `SYS_ORG_GROUP_ADMIN` | 可见 + 可维护：自己创建的个人群组、**全部**公共群组 |
| 普通用户 | 不设权（仅需登录且账号启用） | 可见：自己创建的个人群组 + 自己被授权的公共群组；可维护：自己创建的个人群组 |
| 模块/系统管理员 | `SYS_ORG_ADMIN` / `SYS_ADMIN` | 由 `BaseResolver.hasAnyRole` 自动放行，等价于群组管理员 |

> `SYS_ORG_ADMIN` 已在 `BaseResolver` 中按「模块管理员」口径覆盖各模块权限，本次沿用该约定；
> 需在 `roles.yml` 中新增 `SYS_ORG_GROUP_ADMIN` 条目并同步到库。

### 2.2 可见性判定（列表 SQL 口径）

设当前用户 `uid`，是否管理员 `isAdmin`：

```text
可见 ⇔ isAdmin
      OR (field_type = 'PERSONAL' AND field_owner_id  = uid)
      OR (field_type = 'COMMON' AND (
             field_is_all_viewer = 1
             OR EXISTS (
                  SELECT 1 FROM sys_org_group_viewer gv
                  INNER JOIN sys_org_element v ON v.field_id = gv.field_viewer_id
                  WHERE gv.field_group_id = g.field_id
                    AND (
                         v.field_id = <当前用户所属组织节点>
                         OR <当前用户所属节点的 hierarchy> LIKE CONCAT('%/', v.field_id, '/%')
                    )
             )
         ))
```

实现要点：

- 「当前用户所属组织节点」= 人员自身节点 + 其所属岗位 + 其所属虚拟组织（与权限计算口径一致，见核心业务设计）。
  最少口径为人员自身节点；推荐取「人员自身 + 上级机构/部门链路」。
- 「可见范围向子集覆盖」= 被选中节点及其**全部后代**可见。判定以「用户节点的 `field_hierarchy` 是否包含可见节点 id」为准
  （`LIKE '%/<viewerId>/%'`），而不是精确匹配 `field_id`。
- **可见范围可选四类节点（已确认）**，语义差异如下：

| 可见节点类型 | 覆盖面 | 判定方式 |
| --- | --- | --- |
| 机构（1）/ 部门（2） | 该节点及其全部后代人员 | `user.hierarchy LIKE '%/<viewerId>/%'` |
| 岗位（4） | 该岗位上的所有人员 | `EXISTS (sys_org_post_user WHERE post_id = viewerId AND user_id = uid)` |
| 人员（3） | 仅该人员 | `viewerId = uid` |

- 三类判定用 `OR` 并联，统一在 `EXISTS` 子查询内完成，避免多次往返。
- 管理员分支整体短路，不参与 `EXISTS` 计算。

参考 SQL（可见性片段，供 `SysOrgGroupMapper.xml` 复用为 `<sql id="VisibleClause">`）：

```xml
AND (
  <if test="!isAdmin">
    g.field_type = 'PERSONAL' AND g.field_owner_id = #{userId}
    OR g.field_type = 'COMMON' AND (
         g.field_is_all_viewer = 1
         OR EXISTS (
              SELECT 1
              FROM sys_org_group_viewer gv
              LEFT JOIN sys_org_element v ON v.field_id = gv.field_viewer_id
              WHERE gv.field_group_id = g.field_id
                AND (
                     /* 机构/部门：包含该节点或其任一层级祖先 */
                     (v.field_org_type IN (1, 2)
                      AND EXISTS (SELECT 1 FROM sys_org_element me
                                  WHERE me.field_id = #{userId}
                                    AND me.field_hierarchy LIKE CONCAT('%/', v.field_id, '/%')))
                     /* 岗位：用户在该岗位上 */
                     OR (v.field_org_type = 4
                         AND EXISTS (SELECT 1 FROM sys_org_post_user pu
                                     WHERE pu.field_post_id = v.field_id
                                       AND pu.field_user_id = #{userId}))
                     /* 人员：就是当前用户 */
                     OR (v.field_org_type = 3 AND v.field_id = #{userId})
                )
         )
       )
  </if>
  <if test="isAdmin"> 1 = 1 </if>
)
```

> `sys_org_post_user` 的实际列名以实现为准（当前为 `field_post_id` / `field_user_id`），编码时须核对 `V1_01_001`。

### 2.3 维护权限判定（Service 层强校验）

| 操作 | 普通用户 | 群组管理员 |
| --- | --- | --- |
| 查看（load） | 可见即可 | 可见即可 |
| 新建 | 仅 `PERSONAL`（`field_type` 强制为 `PERSONAL`） | `PERSONAL` / `COMMON` 均可 |
| 编辑 | 仅 `PERSONAL` 且 `field_owner_id = uid`；**不可**改 `field_type` | 自己的个人群组 + 全部公共群组；可改类型 |
| 删除 | 仅 `PERSONAL` 且 `field_owner_id = uid` | 自己的个人群组 + 全部公共群组 |

> 「普通用户锁定个人」需**双层保证**：前端禁用类型下拉（默认且锁定 `个人`），后端在 Service 强制
> `field_type = PERSONAL` 且 `field_owner_id = 当前用户`，忽略请求中的越权值。

### 2.4 删除语义（R2-6）

- 群组可被删除 ⇒ **物理删除**（与组织架构元素「置为无效」不同）：
  `sys_org_group_user` → `sys_org_group_viewer` → `sys_org_group` → `sys_org_element`，同事务。
- 无子级校验（群组不参与树）。
- 公共群组被删除时，已引用其 id 的业务数据（如待办接收人）不做级联处理，需在文档中标注为「引用失效」。

## 3. 页面设计要点

### 3.1 入口（R2-7）

- 顶部菜单栏右上角新增「多人」图形按钮，位于现有「日程」按钮与用户头像之间（参考 `HomeView.vue` 的 `.header-user-box`）。
- 点击跳转 `/org/group`（群组列表页），在页签栏中作为普通标签打开。
- 按钮**对所有登录用户可见**（普通用户也要用），不做 `meta.auth` 限制。

### 3.2 群组列表页（`GroupManageView.vue`，`/org/group`）

沿用三段式列表页规范（`list-page.css`）：

| 区域 | 内容 |
| --- | --- |
| 筛选区 | 名称（文本）、类型（不限/公共/个人）、是否全员可见（不限/是/否，仅管理员或选「公共」时可用） |
| 工具区 | 左侧排序（创建时间/更新时间/名称），右侧：查询、创建 |
| 列表区 | 首列复选框（批量删除）、列：名称、类型、成员数、所有人、全员可见、启用状态、创建时间；末列操作：详情 / 编辑 / 删除（`fixed="right"`） |

- 列表数据范围由后端按 2.2 过滤，前端不再二次过滤。
- 普通用户无「类型」筛选的必要性（只会看到个人 + 被授权公共），但保留以保持一致。
- 删除操作二次确认；批量删除逐条调用（与 `OrgManageView` 的「置为无效」一致）。

### 3.3 群组编辑页（`GroupFormView.vue`，`/org/group/create`、`/org/group/edit/:id`）

表单字段（R2-11）：

| 字段 | 控件 | 必填 | 约束 |
| --- | --- | --- | --- |
| 名称 | `el-input` | 是 | 最长 200（与 `field_name` 一致） |
| 类型 | `el-select`（公共/个人） | 是 | 普通用户：默认「个人」且禁用；管理员：可选 |
| 群组成员 | `AddressBook`（`multi`，`org-type="PERSON"`） | 否 | 写 `sys_org_group_user` |
| 可见用户 | `AddressBook`（`multi`，`org-type="ORGDEPTPOSTPERSON"` = 机构/部门/岗位/人员） | 否 | 写 `sys_org_group_viewer`；`个人` 类型隐藏；为空 ⇒ 全员可见 |

- 布局遵循 `form-page.css`：默认一行两字段（`label-width="40%"` + `:span="12"`），
  群组成员/可见用户独占一行（label 20% / 内容 80%）。
- 新建时 `onMounted` 调 `getInitID()` 取 32 位 ID。
- 「可见用户」为空时的提示文案：「不选择时默认全员可见」。
- 保存成功后 `markTabToClose` 关闭标签并返回 `/org/group`。

### 3.4 群组详情页（`GroupDetailView.vue`，`/org/group/detail/:id`）

- 只读展示基本字段 + 成员标签列表 + 可见范围标签列表（或「全员可见」）。
- 提供「返回」「编辑」按钮；「编辑」按 2.3 判定显隐。

### 3.5 地址本「群组」页签（R2-8）

```
┌─ 地址本 ───────────────────────────────────────────────────────┐
│ [关键字]                                        [查询]          │
│ ┌ 组织架构树 ┬ 查询 ┬ 群组 ┐                                    │
│ │ 可见群组列表 │  选中群组的成员列表（多选）                     │
│ │ ▸ 项目A组    │  □ 张三  工号001  手机...                      │
│ │ ▸ 部门协作组 │  □ 李四  工号002                               │
│ └──────────────────────────────────────────────────────────────┘ │
│ 已选：[张三] [李四]                          [取消] [确认]       │
└─────────────────────────────────────────────────────────────────┘
```

- **仅当选择范围包含「人员」时可见该页签**：即 `resolveOrgTypes(orgType)` 含 `3` 时渲染
  （`PERSON` / `PERSONPOST` / `ALL`）。
- 左侧：可见群组列表（复用 2.2 的可见性 SQL），点击后右侧加载该群组成员（**仅人员**，且需再与当前 `orgType` 求交）。
- 右侧：成员表格，支持多选；勾选结果进入现有 `selected` 合并逻辑（新增 `groupSelectedRows`）。
- 选择结果回填的是**人员 id/名称**（不是群组 id），这是与角色页签的本质区别。
- 群组本身**不可被选为值**，仅作为「批量选人」的快捷方式。

## 4. 后端接口概要

详见 `04-API改动清单.md`。概要：

| 分组 | 接口 | 说明 |
| --- | --- | --- |
| 群组维护 | `POST /backend/sys/org/group/list` | 列表分页（按 2.2 可见性过滤） |
| | `GET  /backend/sys/org/group/load?fieldId=` | 详情（基本 + 成员 + 可见范围） |
| | `POST /backend/sys/org/group/save` | 新建（全量写明细） |
| | `PATCH /backend/sys/org/group/update` | 编辑（明细先删后插） |
| | `DELETE /backend/sys/org/group/delete?fieldId=` | 物理删除（四表同事务） |
| 地址本 | `POST /backend/sys/org/addressbook/groupList` | 地址本可见群组列表（按关键字/分页） |
| | `POST /backend/sys/org/addressbook/groupUsers` | 指定群组的成员人员列表 |

> 地址本的两个接口挂在 `addressbook` 分组下，沿用 `AddressBookResolver`（仅登录即可），
> 但 `groupList` 必须内部按 2.2 过滤；`groupUsers` 必须先校验该群组对当前用户可见，否则返回空/`FORBIDDEN`。

## 6. 与现有模块的交叉影响

| 模块 | 影响 |
| --- | --- |
| 组织架构管理页 | 列表与树必须排除 `field_org_type = 6` |
| 权限预览 | 仅接受人员节点（`field_org_type = 3`），群组天然被前端拦截；后端无需改动，建议加显式校验 |
| 角色管理 | 「组织架构」选择器必须排除 5/6（否则可把群组挂给角色） |
| 通知待办 / 日程 / 流程 | 使用 `AddressBook` 且 `org-type` 不含 5/6，默认不受影响；群组页签默认关闭 |
| 权限计算 | `selectListByUserId` 限定 1/2/3/岗位/虚拟组织，群组不参与，**无改动** |
| 密码相关 | 无影响 |

## 7. 待确认事项（群组）

1. 群组是否需要在组织架构管理页「置为无效」之外单独入口？——本文按独立列表页处理。
2. ~~公共群组的 `field_owner_id`~~ → **已确认**：记录创建人（`COMMON` 也写 `field_owner_id = 创建人`），便于审计与列表展示「所有人」列；归属维护权限仍以「管理员可维护全部公共群组」为准，不因此产生额外权限。
3. 群组成员是否允许包含离职/停用人员？推荐保存时校验人员存在且启用；已停用人员保留在明细中但在地址本不展示。
4. ~~可见范围是否可选「人员」节点~~ → **已确认**：可选范围限定为**机构 / 部门 / 岗位 / 人员**四类，以适配多种场景。
   因此「子集覆盖」语义需完整支持四类节点：命中节点本身及其全部后代（对岗位/人员无后代，等价于自身）。
5. 群组数量上限 / 成员数量上限：建议不设硬限，列表分页即可。
