# 流程管理模块功能清单核对报告

- **核对日期**：2026-11-11
- **核对范围**：本仓库（CommonSystem）流程模块 `sys/process` 的后端接口、数据模型、前端页面，以及通知待办模块 `sys/notify` 中与审批相关的部分
- **对照基准**：v1_3 流程管理功能清单（流程设计 / 流程模板 / 流程实例 / 审批管理 / 审批操作 / 流程监控 / 流程规则 / 流程统计，共 8 个二级模块 33 项三级功能）
- **文档定位**：v1_3 现状调研结论，作为后续需求 / UI / API / 数据库设计的输入

## 一、核对方法

三方面交叉核对，任一方面缺失即视为未完成：

1. **后端**：`backend/src/main/java/com/common/system/sys/process/` 下 Controller 接口、Service 业务逻辑、`ProcessResolver` 鉴权分支、`SysProcessConstants` 常量全集（节点类型 / 审批模式 / 实例状态 / 审批记录类型 / 特权操作）；
2. **数据模型**：`db/migration/` 中流程相关脚本仅 `V1_01_007`（模板结构）、`V1_01_008`（实例结构）、`V1_01_019` / `V1_01_038`（默认模板）4 个，表结构实核对 `SysProcessTemplate` / `SysProcessTemplateNode` / `SysProcessExample` / `SysProcessExampleNode` / `SysProcessExampleWorkitem` / `SysProcessAuditNote` 实体字段；
3. **前端**：`frontend/src/api/process.js` 封装、`views/process/`（TemplateManageView、TemplateFormView、ExampleManageView、ExampleDetailView、ProcessSettingView）、`components/process/ProcessApprovalPanel.vue`。

图例：✅ 已实现 ｜ ⚠️ 部分实现 / 仅有模型 ｜ ❌ 未实现。

## 二、总体结论

- 当前系统是**线性串行流程引擎**：模板为「固定顺序节点链」（开始 → 草稿 → 审批节点 ×N → 结束，按 `field_no` 顺序流转），面向 ERP 业务单据审批（项目 / 合同等模块经 `SysProcessExampleService#startByModel` 接入），不是可自由连线的工作流设计器；
- **已实现且完整**：模板维护（含版本归档、默认模板）、单签 / 会审、驳回重提（重新流转 / 转回本节点）、起草人收回 / 废弃、管理员五类特权操作（跳转 / 终审 / 作废 / 暂停 / 恢复）、自动跳过重复审批人体系、审批记录全留痕；
- **核心差距**：流程连线（DAG）、流程变量、模板复制、流程重启、转办 / 委托 / 加签 / 减签、抄送、超时规则、异常处理闭环、全部统计分析能力；
- 与清单 33 项三级功能对照：**完全满足 16 项、部分满足 4 项、不满足 13 项**（覆盖率约 52%）。

## 三、分模块核对

### 3.1 流程设计

| 功能 | 状态 | 现状依据 |
| --- | --- | --- |
| 流程定义 | ✅ | `sys_process_template` + `SysProcessTemplateService`；更新时历史版本全量归档到 `sys_process_template_history.field_content`，版本号 +1 |
| 流程节点 | ✅ | `sys_process_template_node`，节点类型 START / END / DRAFT / APPROVE / ROBORT，配置存 `field_node_config`（JSON）；注意 **ROBORT（机器人节点）仅在模板保存时做合法性校验，运行期流转无任何消费方** |
| 流程连线 | ❌ | 节点模型无连线字段；流转逻辑 `SysProcessExampleService#nextNode` 按 `field_no` 顺序取下一节点——**线性串行**，无分支 / 汇聚 / 条件跳转的连线结构 |
| 流程变量 | ❌ | `SysProcessExample` 无变量字段；「条件判断」公式只能引用文档实体字段（`process_template.${fieldModelName}.fields` 字典），不存在独立的流程变量集 |

### 3.2 流程模板

| 功能 | 状态 | 现状依据 |
| --- | --- | --- |
| 模板创建 | ✅ | `POST /backend/sys/process/module/save`，初始版本号 1，固定三节点（开始 / 草稿 / 结束）自动生成 |
| 模板复制 | ❌ | `SysProcessTemplateService` 全文无 copy 逻辑，前端模板页亦无「复制」按钮 |
| 模板发布 | ⚠️ 等价实现 | 无独立「发布」动作；以「启用（`field_enable`）+ 置为默认（`field_default`，每分类唯一，`V1_01_019` 数据库生成列唯一索引兜底）」代替。语义可接受，但无发布历史 / 灰度能力 |
| 模板停用 | ✅ | `PATCH /module/enable`，请求体 `{ fieldId, fieldEnable }`；停用模板不可置为默认，默认模板被停用后该分类无默认模板（启动流程时兜底报错） |

### 3.3 流程实例

| 功能 | 状态 | 现状依据 |
| --- | --- | --- |
| 发起流程 | ✅ | `createDraft` / `startByModel`：保存时创建 DRAFT 实例，提交转 PROCESSING 并流转；**发起由业务模块调用 Service 完成，无独立 REST 接口**；启动模板选择规则完整（单据指定 / 分类默认模板，无默认则启动失败） |
| 流程撤回 | ✅ | `back()` 起草人收回：PROCESSING → DRAFT，节点转回起草节点、在途工作项废弃，生成 `DRAFTER_BACK` 审批记录 |
| 流程终止 | ⚠️ 等价实现 | 无发起人「终止」动作；管理员 `adminOperate(ABANDON)` 作废覆盖 PROCESSING / RETURN / DRAFT / PAUSE 四种状态，起草人 `abandonByDrafter` 限 DRAFT / RETURN。审批中的单据发起人自行终止需「收回 → 废弃」两步 |
| 流程重启 | ❌ | 无重启能力；驳回后重新提交按 `resumeMode`（重新流转 / 转回本节点）继续**同一实例**，不是废弃原单后新建实例 |

### 3.4 审批管理

| 功能 | 状态 | 现状依据 |
| --- | --- | --- |
| 待办任务 | ✅ | notify 模块 `POST /sys/notify/todo/myList`（`fieldIsDone=false`）+ SSE 实时推送（`NotifySseController`）；注意 **流程引擎不直接产生待办**，由接入流程的业务模块经 `NotifySendEvent` 发送 |
| 已办任务 | ✅ | `myList`（`fieldIsDone=true`）+ `done` / `undone` 单个与 batch 批量互转 |
| 我发起的 | ⚠️ 等价实现 | notify 待办按接收人过滤，不是按发起人；「我发起的流程」可经流程实例列表 `fieldCreatorName` 筛选近似实现，但无专属视图 / 菜单入口 |
| 抄送我的 | ❌ | 通知类型仅 `SysNotifyType.TODO`（待办）/ `READ`（待阅）两种，无抄送（CC）类型；流程引擎无「抄送人」节点配置或抄送动作 |

### 3.5 审批操作

| 功能 | 状态 | 现状依据 |
| --- | --- | --- |
| 同意 | ✅ | `pass()`：单签一票通过（其余工作项转 FINISH），会审全员通过；生成 `HANDLER_PASS` 审批记录 |
| 驳回 | ✅ | `reject()`：固定驳回到起草节点，流程转 RETURN；驳回时选择「重新提交后流转方式」（重新流转 / 转回本节点）存工作项 `field_config`，生成 `HANDLER_RETURN` 记录 |
| 转办 | ❌ | 全模块无 transfer 关键词；工作项与审批人绑定，无改派能力 |
| 委托 | ❌ | 无 delegate 能力，无代理配置 |
| 加签 | ❌ | 无 addSign；会审名单在实例创建时从模板节点配置原样复制（`sys_process_example_node.field_node_config`），无法动态增加审批人 |
| 减签 | ❌ | 无 removeSign，同上无法动态减少 |

### 3.6 流程监控

| 功能 | 状态 | 现状依据 |
| --- | --- | --- |
| 流程跟踪 | ✅ | `GET /example/load` 返回实例 + 节点 + 工作项 + 审批记录；`GET /example/panel` 供业务文档页嵌入 `ProcessApprovalPanel` 组件（审批 / 审批记录 / 流程三卡片 + nodeOps 操作标识） |
| 节点状态 | ✅ | 节点状态 WAITING / PROCESSING / FINISH / PASS / REJECT；自动跳过场景自动创建办结工作项并生成 `AUTO_PASS` 记录 |
| 耗时分析 | ❌ | **数据基础已具备**（实例与工作项均有 `field_create_time` + `field_finish_time`，实例另有 `field_finish_time`），但无任何耗时计算接口与页面 |
| 异常处理 | ❌ | 无异常标记 / 挂起原因 / 人工干预队列；管理员 JUMP / PAUSE / RESUME 是主动特权操作，不构成异常检测 → 处理的闭环 |

### 3.7 流程规则

| 功能 | 状态 | 现状依据 |
| --- | --- | --- |
| 条件分支 | ⚠️ 弱实现 | 节点级「触发条件」（`triggerType=condition` + 判断公式 + `${field}` 占位符，占位符字段必须是文档实体字段）；但公式只决定**线性链上单个条件节点是否执行**，不是路由级的条件分支选择 |
| 会签规则 | ✅ | `approveMode`：single（单签）/ countersign（会审），会审全员通过语义完整 |
| 审批规则 | ⚠️ 部分 | 已成体系：审批人解析（组织架构 / 表单字段两种来源、解析为空跳过节点）、自动跳过（重复审批人 / 含起草人 / 连续跳过，系统级配置 + 节点级覆盖三段式）；**缺**或签、票签比例、空审批人兜底策略等扩展规则 |
| 超时规则 | ❌ | 无超时规则；Quartz 定时任务体系（`sys/task`）中也无流程超时催办 / 自动处理任务 |

## 四、差距汇总

### 4.1 完全缺失（13 项）

流程连线、流程变量、模板复制、流程重启、抄送我的、转办、委托、加签、减签、耗时分析、异常处理、超时规则、流程统计（审批数量 / 审批效率 / 人员工作量三类均无接口）。

### 4.2 部分实现或仅有数据基础

| 项 | 已有 | 缺口 |
| --- | --- | --- |
| 条件分支 | 节点级触发条件（公式 + 文档实体字段占位符） | 路由级条件分支：多候选分支按条件选择路径，需连线结构支撑 |
| 审批规则 | 审批人双来源解析、自动跳过三段式配置 | 或签 / 票签比例 / 空审批人兜底策略 |
| 模板发布 | 启用 + 默认模板（每分类唯一） | 独立发布动作、发布历史 |
| 流程终止 | 管理员作废（全状态）+ 起草人废弃（DRAFT / RETURN） | 审批中状态发起人一键终止（当前需收回 + 废弃两步） |
| 我发起的 | 实例列表 `fieldCreatorName` 筛选 | 专属视图 / 菜单入口 |
| 耗时分析 | 实例与工作项的创建 / 完成时间字段 | 耗时计算接口、按节点 / 人员 / 模块的聚合口径、页面 |
| 抄送 | 通知体系（待办 / 待阅双类型、SSE 推送） | 抄送类型、抄送人节点配置、流程引擎抄送动作 |
| 超时规则 | Quartz 定时任务框架、流程公共配置体系（`SETTING.process.*`） | 超时规则配置（节点级 / 模板级）、超时催办 / 自动处理定时任务 |

### 4.3 实现形态差异（设计时需对齐）

- **无独立设计器形态**：模板编辑是「节点列表 + 配置弹窗」（多标签：基础 / 审批权限），不是画布式流程设计器；若 v1_3 要做连线 / 分支，前端需整体替换模板编辑形态；
- **审批操作仅 通过 / 驳回 两种**：`SysProcessConstants` 审批记录类型全集为 DRAFTER_SUBMIT / DRAFTER_BACK / DRAFTER_ABANDON / HANDLER_PASS / HANDLER_RETURN / AUTO_PASS / ADMIN_* 五类，无转办 / 委托 / 加签 / 减签留痕类型，扩展需同步审批记录类型与工作项模型；
- **流程待办由业务侧发送**：流程引擎不直接调用通知待办模块；公共配置页已提供 4 个通知标题模板配置（`notify_handle_subject` 等，`SETTING.notify.*`），但主代码无消费方——当前由接入流程的业务模块自行组织标题发送待办。v1_3 若要统一催办 / 抄送通知，需将发送逻辑收归流程模块并消费这批配置；
- **发起流程无 REST 接口**：`createDraft` / `startByModel` 仅 Service 层方法，由业务模块后端调用；若 v1_3 要提供统一发起入口，需新增接口并定义 `ACTION_*` 与 resolver 分支；
- **权限模型已就绪**：`SYS_PROCESS_ADMIN` / `TEMPLATE_ADMIN` / `TEMPLATE_VIEWER` / `EXAMPLE_ADMIN` / `EXAMPLE_VIEWER` / `SETTING_ADMIN` 六角色齐全，新增能力可按现有 `ProcessResolver` switch 分支扩展，无需调整角色体系。

## 五、后续建议

1. **先对齐功能口径**：「模板发布 ≈ 启用 + 置默认」「流程终止 ≈ 作废 + 收回组合」「我发起的 ≈ 实例列表按发起人筛选」三处等价实现是否被 v1_3 验收口径接受，需在需求文档中明确；
2. **按改动深度分级推进**：
   - **仅补接口 / 页面**（数据模型已支持）：模板复制、我发起的视图、耗时分析、审批数量 / 效率 / 人员工作量统计；
   - **需引擎改造**（表结构 + 流转逻辑 + 迁移脚本）：流程连线（DAG 化）、条件分支路由、流程变量、加签 / 减签、抄送、超时规则（可先借 Quartz 做催办）、异常处理闭环；
3. **按规范补设计文档**：缺口项按 开发顺序 需求 → UI → API → 数据库 → 代码与迁移脚本 推进，迁移脚本从 `V1_01_043` 起递增（当前最新 `V1_01_042`）；
4. **统计功能建议独立成册**：审批数量 / 效率 / 工作量需要新的聚合查询与页面，建议单独补 API 与数据库设计（只读查询，建议新增统计专用 Mapper XML，不侵入现有流转 SQL）；
5. **通知收口**：统一催办 / 抄送 / 办结通知建议由流程模块直接消费 `SETTING.notify.*` 配置发送待办待阅，替代当前「业务侧自行发送」的分散模式，先例可参考 `NotifySendEvent` 机制。
