# 接口开关机制需求分册

> 本文档为接口开关机制（V1.1，模块组级启停）的需求分册，依据《接口开关机制设计方案-修订稿.md》（下称「修订稿」）第 1 / 2 / 5 / 6 / 9 / 10 / 11.2 节拆分整理。
> 修订稿第 13 节列出的五项分歧点均已按修订稿正文默认决策落定（见本文第 10 节），本分册不保留未决项。
> 配套分册：[接口开关机制UI设计分册.md](接口开关机制UI设计分册.md)、[接口开关机制API设计分册.md](接口开关机制API设计分册.md)、[接口开关机制数据库设计分册.md](接口开关机制数据库设计分册.md)。

## 1. 目标与非目标

**目标**

1. 按「模块组」粒度对一组接口做**运行期整体启停**：管理员不改代码、不重启即可关闭/恢复一个模块组；
2. 提供模块组的管理面：【系统管理-模块管理】页面 + 后端列表/切换接口；
3. 前端运行期感知：模块关闭后，用户侧菜单与页面有明确的降级表现，而非一堆报错；
4. 单机与多实例部署下开关状态正确收敛。

**非目标**

1. **不替代权限体系**：开关是「模块能不能用」的功能门禁，与「谁能用」的 `ACTION_* + resolver` 鉴权正交；
2. 不做方法级/接口级精细灰度（粒度固定为模块组）；
3. 不提供定时自动启停、生效时间段等高级能力（后续迭代再议）。

## 2. 核心概念

| 概念 | 定义 |
| --- | --- |
| 模块组（module-group） | 接口开关的单位。key 为**全局唯一命名空间**，kebab-case 命名（如 `calendar`、`org-group`） |
| 模块组 ≠ 模块目录 | 一个模块目录可声明多个模块组（如 `sys/org` 可拆 `org-group`）；一个模块组也可覆盖跨模块的业务域（如 `third-party`） |
| 开关归属声明 | Controller 类或方法上的 `@ModuleGroup(moduleGroupKey = "...")`；**方法级覆盖类级** |
| 默认语义 | **无注解 = 不受开关控制（放行）**。这是机制成立的前提：登录、`/init`、`/initID`、`setting/load`、SSE 订阅、swagger 等公共入口均不打注解，天然不受开关影响 |
| 开关与 SYS_ADMIN | 系统管理员**不穿透**模块开关。开关是功能级而非人级门禁，管理员同样被拒，否则无法验证关闭效果；模块管理接口自身不打注解、永远可用 |

## 3. 行为语义总表

请求命中开关时的统一行为（逐条与修订稿第 2 节一致）：

| # | 场景 | 行为 |
| --- | --- | --- |
| 1 | 请求命中无注解的 Controller | 放行，进入既有鉴权链路 |
| 2 | 已登录 + 命中开启模块组的注解 | 放行，进入既有鉴权链路 |
| 3 | 已登录 + 命中关闭模块组的注解 | 返回 `MODULE_DISABLED`（"该模块未开启"），**不进入** Controller 与 resolver |
| 4 | 未登录 + 命中关闭模块组的注解 | 放行给后续最终鉴权，返回 `UNAUTHORIZED`。理由：匿名请求无论如何都过不了鉴权，放行可避免向匿名暴露模块开关状态（来自修订稿默认决策 D2） |
| 5 | 注解 key 在 `common_module_group` 中不存在 | 启动期校验告警；运行期按"开启"放行（fail-open），不因误配置扩大故障面 |
| 6 | 模块组从 yml 中移除 | 库中记录保留（关闭历史可追溯），不做自动清理（来自修订稿默认决策 D3） |
| 7 | Redis 不可用 | 进程内缓存 + TTL 兜底，开关功能不受影响（来自修订稿默认决策 D1） |

补充语义规则：

- 开关判定位于业务鉴权**之前**：模块未开启时无需再讨论权限，符合「门禁」语义；
- 系统管理员（`SYS_ADMIN`）**不穿透**模块开关：关闭模块组下系统管理员同样收到 `MODULE_DISABLED`；
- 模块管理接口（`CommonModuleController`）自身不打 `@ModuleGroup`，保证关闭任意模块组后管理面仍可用。

## 4. 开关与权限体系的关系

- 开关是**功能门禁**（模块能不能用），权限是**人级门禁**（谁能用），两者正交、串联生效：拦截器开关判定 → Controller `authorize(action, documentId)` 鉴权 → 业务逻辑；
- 公共入口（登录认证、`/init`、`/initID`、`setting/load`、SSE 订阅、swagger 等）不打注解，不受开关影响，保证系统自举能力；
- 面向最终用户的功能模块才可纳入开关范围；登录认证、组织架构主干、权限、字典、日志、公共配置、定时任务、i18n 等基础设施与系统管理类模块**不纳入**（关闭它们会破坏系统自举能力）。

## 5. 模块组数据来源与纳入原则

### 5.1 moduleGroup.yml 声明

各模块在 `resources/properties/{common|sys}/{模块}/moduleGroup.yml` 中声明本模块的模块组，由启动期统一扫描（不在 Spring 配置体系内）。命名与粒度规范：

1. key 统一 **kebab-case**；key 即注解值与前端常量，禁止大小写混用；
2. key **全局唯一**、一经发布**不复用/不重命名**（重命名视为新模块组，旧组按"yml 移除"保留在库）；
3. `name` 为页面展示中文名，`remark` 为卡片描述，两者必填（缺失时同步任务告警并跳过该条目）。

### 5.2 纳入原则

面向最终用户的功能模块才可纳入开关范围；登录认证、组织架构主干、权限、字典、日志、公共配置、定时任务、i18n 等基础设施与系统管理类模块不纳入。后续追加只需「moduleGroup.yml 加条目 + Controller 加注解」，机制本身无需改动。

### 5.3 首批清单（来自修订稿默认决策 D5）

| 模块组 key | 名称 | 覆盖范围（Controller） | 说明 |
| --- | --- | --- | --- |
| `calendar` | 日程 | `SysCalendarMainController`（sys/calendar 全部接口） | 现有模块，作为机制验证 |
| `org-group` | 组织架构-群组 | `SysOrgGroupController` | v1.1 群组功能的灰度入口 |
| `third-party` | 第三方 | （预留，暂无 Controller） | 原方案示例保留为占位，第三方账号接入模块落地时启用（首批不建 yml、不标注） |

其余 Controller 首批不标注，既有接口零回归。

## 6. 启动同步与状态生命周期

### 6.1 幂等三边界

启动同步作为第 10 个启动任务追加到 `SysStartupTask#run`（不另建 ApplicationRunner），扫描 `classpath*:properties/**/moduleGroup.yml` 的 `module-group` 段增量同步到 `common_module_group`：

1. **不存在 → 插入**，`field_enable` 默认开启；
2. **已存在 → 只回写元信息**：`name / remark` 变更时更新，`field_enable` **一律不动**——否则管理员关闭后重启即被 yml 重置，机制失效；
3. **yml 中移除 → 库中记录保留**，不删除、不改状态，可人工清理（来自修订稿默认决策 D3）。

### 6.2 启动期注解校验

同步完成后扫描全部 `@ModuleGroup` 注解，校验 `moduleGroupKey` 在 `common_module_group` 中存在；未知 key 记 **WARN 日志**（不阻断启动），防止注解 key 与 `field_key` 拼写不一致导致开关静默失效。

### 6.3 状态缓存与多实例一致性（来自修订稿默认决策 D1）

| 场景 | 行为 |
| --- | --- |
| 启动 | 同步任务完成后全量预热缓存 |
| 请求判定 | 读进程内不可变 Map；缓存超过 TTL（默认 30 秒）时回源 DB 刷新（表量极小，全量查询代价可忽略） |
| 切换成功 | 更新 DB → 本实例立即刷新缓存 → 尝试 Redis pub/sub 广播失效通知其他实例（best-effort） |
| Redis 不可用 / 广播失败 | 仅记日志，依赖 TTL 收敛，全实例最迟 30 秒一致 |
| DB 异常且无可用缓存 | **放行并告警**（fail-open）：开关属增强管控，不应在 DB 故障时放大为全站拒绝 |
| DB 异常但有缓存 | 沿用上次缓存值并告警 |

TTL（30s）为默认值，常量定义于 `CommonModuleProperties`，多实例收敛上限即该值。

## 7. 角色与权限

权限码定义于 `properties/common/roles.yml`（表属 common 层），经既有权限同步链路增量同步到 `sys_org_auth`：

| 权限码 | 中文名 | 描述 |
| --- | --- | --- |
| SYS_MODULE_ADMIN | 模块组管理员 | 维护模块组开关状态（系统管理-模块管理） |

权限判定口径：

- 模块组列表（`common.module.list`）：**登录即可访问**，无角色要求——模块组列表暴露系统拓扑，定为登录即可、免登录不可访问；
- 模块组启停（`common.module.enable`）：需 `SYS_MODULE_ADMIN`；
- `SYS_ADMIN` 经 `BaseResolver` 自动放行（模块 resolver 分支内不重复列举），但如第 2 节所述**不穿透模块开关**。

## 8. 异常处理与降级

### 8.1 MODULE_DISABLED（模块关闭）

- 已登录请求命中已关闭模块组的注解时，拦截器抛 `ModuleDisabledException`，经 `GlobalExceptionHandler` 返回 `BaseResponse.failure("MODULE_DISABLED", "该模块未开启，请联系管理员")`；
- HTTP 状态仍为 200 + code 体系（全工程惯例）；请求**不进入** Controller 与 resolver；
- `BaseResponse` 的 code `@Schema` 描述同批追加 `MODULE_DISABLED` 错误码；
- 前端 axios 拦截器（`api/index.js`）识别该码做统一提示（详见 UI 分册第 8 节）。

### 8.2 匿名请求（来自修订稿默认决策 D2）

未登录请求命中关闭模块组的注解时**放行给最终鉴权**，返回 `UNAUTHORIZED`（登录已过期，请重新登录）；不返回 `MODULE_DISABLED`，避免向匿名暴露模块开关状态。

### 8.3 fail-open 语义

开关属增强管控，以下场景一律按「开启」放行并告警，不放大故障面：

| 场景 | 行为 |
| --- | --- |
| 注解 key 未在 `common_module_group` 中登记 | 运行期放行；启动期记 WARN |
| DB 异常且缓存不可用 | 放行并告警 |
| DB 异常但有缓存 | 沿用上次缓存值并告警 |
| 前端 store 模块状态缺失 | 菜单不过滤、页面不拦空态，按开启放行 |

### 8.4 Redis 不可用

广播失败仅记日志，依赖进程内 TTL 兜底收敛，全实例最迟 30 秒一致；开关功能不受影响。

## 9. 用户侧运行期感知

模块关闭后，用户侧为**两级感知**（交互细节见 UI 分册）：

1. **菜单过滤**：前端登录后拉取模块组状态缓存（Pinia store `stores/module.js`），菜单按「权限 auth + 模块可用性」双重过滤，已关闭模块的菜单项**隐藏**（首批映射：日程菜单 → `calendar`、群组菜单 → `org-group`）；
2. **页面空态**：路由守卫检测目标页面所属模块组已关闭时，渲染「模块未开启」空态提示（**不重定向首页**，避免与无权限重定向语义混淆）。

模块恢复开启后菜单与页面自动恢复可见（前端于下次状态拉取后生效）。
