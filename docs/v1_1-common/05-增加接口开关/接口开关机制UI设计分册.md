# 接口开关机制UI设计分册

> 本文档为接口开关机制（V1.1，模块组级启停）的前端 UI 分册，依据《接口开关机制设计方案-修订稿.md》（下称「修订稿」）第 8.3 / 11 节拆分整理，菜单挂载与路由口径遵循修订稿默认决策 D4。
> 配套分册：[接口开关机制需求分册.md](接口开关机制需求分册.md)、[接口开关机制API设计分册.md](接口开关机制API设计分册.md)、[接口开关机制数据库设计分册.md](接口开关机制数据库设计分册.md)。

## 1. 页面目标与入口

- 页面清单：

| 页面 | 路由 | 组件 | 菜单入口 | 路由权限（meta.auth） |
| --- | --- | --- | --- | --- |
| 模块管理 | `/module` | ModuleManageView.vue（`views/setting/`） | 系统管理 → 后台管理 → 模块管理 | SYS_MODULE_ADMIN |

- 页面类型：纯卡片操作页（无新建 / 编辑表单、无子路由；来自修订稿默认决策 D4 的路由形态）。
- 主要角色：模块组管理员（`SYS_MODULE_ADMIN`，系统管理员 `SYS_ADMIN` 自动放行）；普通登录用户不可见入口、直访被路由守卫拦截。
- 页面用途：查看全部模块组并整体启停；模块关闭后用户侧菜单隐藏、页面呈现「模块未开启」空态、接口返回 `MODULE_DISABLED`。
- API 落点：页面只 import `api/common.js` 的 `listModules()`、`updateModuleEnable()` 具名函数，统一经 `src/api/index.js` axios 实例请求，不直接写 axios 或裸 URL。
- 状态基建：模块组状态缓存于 Pinia store `stores/module.js`，登录后（应用初始化）调 `listModules()` 拉取；管理页切换成功后同步刷新该 store。

## 2. 路由与菜单

### 2.1 路由

- 路由：`/module`，顶层扁平路径（与 `/setting`、`/dict` 同惯例，来自修订稿默认决策 D4）；
- 路由 meta：`{ title: '模块管理', parent: '系统管理', group: '后台管理', auth: 'SYS_MODULE_ADMIN' }`；
- 无子路由，不设 `meta.tab`；无权限用户直访由既有路由守卫按 `meta.auth` 重定向首页（与角色管理等页面同行为）。

### 2.2 菜单挂载

- `HomeView.vue` 菜单在【系统管理】分组 →【后台管理】子组追加「模块管理」菜单项，与「公共配置」并列（来自修订稿默认决策 D4）：

```text
系统管理
└─ 后台管理
   ├─ 公共配置   （auth: 'SYS_ADMIN'，既有可见面不变）
   └─ 模块管理   （auth: 'SYS_MODULE_ADMIN'）
```

- 鉴权下放落点（来自修订稿默认决策 D4 的必要落点）：现有【后台管理】子组整体 `auth: 'SYS_ADMIN'`、子项「公共配置」`auth: ''`。为使模块组管理员可见「模块管理」入口、且不放大「公共配置」可见面，子组整体 auth 下放为空、子项各自声明 auth：「公共配置」补 `auth: 'SYS_ADMIN'`（可见面与现状一致）、「模块管理」声明 `auth: 'SYS_MODULE_ADMIN'`。菜单过滤仍走既有 `filterMenuNode` 递归逻辑（分组下无可见子项时整组隐藏）。
- `activeMenu` 核对（修订稿 11.1 要求同步补归约）：`/module` 为顶层扁平叶子路径，既有前缀归约（`/org/`、`/role/`、`/calendar/`、`/attOperation/`、`/log/`、`/task/` 等）均不会命中，返回 `route.path` 本身即正确高亮；实现时核对确认无前缀冲突，如出现误命中再补归约分支。

## 3. 模块管理页布局

四分栏卡片布局：

```text
┌────────────────────────────────────────────────────────────┐
│  页面标题：模块管理                                            │
├──────────────┬──────────────┬──────────────┬──────────────┤
│  ┌────────┐  │  ┌────────┐  │  ┌────────┐  │  ┌────────┐  │
│  │ 日程    │  │  │ 组织架构 │  │  │ 第三方  │  │  │ ……     │  │
│  │ 日程模块 │  │  │ -群组   │  │  │ 第三方账号│  │  │        │  │
│  │         │  │  │ -群组模块│  │  │ 接入模块 │  │  │        │  │
│  │ ● 启用  │  │  │ ● 启用  │  │  │ ● 启用  │  │  │        │  │
│  │ [══●]  │  │  │ [══●]  │  │  │ [══●]  │  │  │        │  │
│  └────────┘  │  └────────┘  │  └────────┘  │  └────────┘  │
└──────────────┴──────────────┴──────────────┴──────────────┘
```

- 布局控件：`el-row` + `el-col :span="6"` 四分栏；模块组超出四个时自然换行；
- 每个模块组一张 `el-card` 卡片，卡片内自上而下：模块组名称（卡片标题）→ 描述（`field_remark`）→ 状态（el-tag：启用 success / 停用 danger）→ `el-switch` 开关；
- 数据来源：`listModules()` 全量返回（后端按 `field_key` 排序），页面不分页、不提供筛选区（模块组数量极少，与列表页三段式规范无关，属卡片操作页形态）；
- 卡片不展示主键 `fieldId`（全工程列表/卡片不展示主键的惯例）。

## 4. 卡片字段与开关规格

| 卡片元素 | 来源字段 | 展示控件 | 说明 |
| --- | --- | --- | --- |
| 模块组名称 | `fieldKey` 对应 `fieldName` | 卡片标题文本 | 中文名（如「日程」「组织架构-群组」） |
| 描述 | `fieldRemark` | 正文文本 | 卡片描述；未维护时显示「-」 |
| 状态 | `fieldEnable` | el-tag | 启用（success）/ 停用（danger） |
| 开关 | `fieldEnable` | el-switch | 与状态标签同源联动；切换走第 5 节交互 |

- 开关切换目标值：开启 → `fieldEnable: true`，关闭 → `fieldEnable: false`，以卡片记录的 `fieldId` 为操作对象；
- 模块组列表与 `stores/module.js` 共用同一份数据；管理页切换成功后同步更新 store，保证菜单过滤即时生效。

## 5. 开关切换交互（二次确认）

启停用须二次确认是全工程硬规则：

1. 点击 `el-switch` 时**不立即变更显示态**，先弹出 `ElMessageBox.confirm` 二次确认，文案按目标值区分：
   - 关闭：`确认关闭模块组「{模块组名称}」？关闭后该模块组全部接口停止服务，用户侧菜单将隐藏并提示「模块未开启」。`
   - 开启：`确认开启模块组「{模块组名称}」？开启后该模块组全部接口恢复服务。`
2. 确认 → 调 `updateModuleEnable({ fieldId, fieldEnable })`：
   - 成功：更新开关与状态标签显示态、同步刷新 `stores/module.js`，`ElMessage.success` 提示（如「模块组已开启/已关闭」）；后端在成功路径内完成缓存刷新与广播（前端无感）；
   - 失败：**回滚开关显示态**（恢复切换前 `fieldEnable`），并提示失败原因（`MODULE_DISABLED` 等错误码经 axios 拦截器统一提示，页面可再补局部提示），不残留半更新状态；
3. 取消：不发起请求，开关显示态维持原值；
4. 切换属低频敏感操作，操作日志由后端 Service 层记录（`action = common.module.enable`），前端无感。

## 6. 运行期感知：菜单 moduleGroup 过滤

- 状态基建：Pinia store `stores/module.js` 在登录后（应用初始化）调 `listModules()` 缓存模块组状态，并提供按 key 查询模块可用性的方法；store 数据缺失时**按开启放行**（fail-open）；
- `HomeView.vue` 菜单配置项增加可选 `moduleGroup` 键，声明该菜单项所属模块组；首批映射：`/calendar → calendar`、`/org/group → org-group`（与首批模块组清单一致）；
- 菜单按「权限 `auth` + 模块可用性」**双重过滤**：在既有 `filterMenuNode` 权限过滤之外叠加模块组状态判断，已关闭模块的菜单项**隐藏**（分组下无可见子项时分组随之隐藏）；
- 模块恢复开启后，菜单随下次模块状态拉取自动恢复可见。

## 7. 运行期感知：路由守卫「模块未开启」空态

- 页面所属模块组的声明落点：路由 `meta.moduleGroup`（与菜单 `moduleGroup` 键同值同源，守卫经 `to.meta.moduleGroup` 读取；首批仅 `/calendar` 与 `/org/group` 及其子路由声明；不声明该键的路由不受空态检测影响）；
- 守卫检测顺序：未登录重定向登录页 → `meta.auth` 无权限重定向首页（既有）→ `meta.moduleGroup` 所属模块组已关闭 → **渲染「模块未开启」空态，不重定向首页**（避免与无权限重定向语义混淆）；
- 空态表现：目标路由区域渲染「模块未开启」空态提示（含模块组名称与「请联系管理员开启」说明），页面不加载业务数据；
- store 数据缺失时按开启放行（fail-open），不拦空态。

## 8. 异常与提示

| 错误码 | 前端处理 |
| --- | --- |
| `MODULE_DISABLED` | axios 响应拦截器（`api/index.js`）识别后统一 `ElMessage` 提示「该模块未开启，请联系管理员」，**仅提示、不跳转**（区别于 `UNAUTHORIZED` 清登录态跳登录页；与 `FORBIDDEN` 同级处理）；页面仍可按需做局部处理 |
| `UNAUTHORIZED` | 既有处理：清理登录态并跳转登录页（含匿名请求命中关闭模块组、被最终鉴权拒绝的场景） |
| `FORBIDDEN` | 既有处理：仅提示，不跳转（如无 `SYS_MODULE_ADMIN` 权限调 `/enable`） |

- 管理页开关切换失败即依赖上述统一提示，并按第 5 节回滚开关显示态；
- 提示不影响页面局部错误处理（拦截器提示后仍向调用方抛出/传递失败结果）。
