> 版本：v1.1

## 1. 需求摘要

本次改动包含两条主线：

### 1.1 角色纳入组织架构（`field_org_type = '5'`）

| 编号 | 需求点 |
| --- | --- |

| R1-3 | 地址本选择器新增「角色」页签，用于选择角色 |
| R1-4 | 角色**不参与**组织架构树结构 |

### 1.2 新增「群组」类型（`field_org_type = '6'`）

| 编号 | 需求点 |
| --- | --- |
| R2-1 | 群组 `field_org_type = 6` |
| R2-2 | 群组子表 `sys_org_group`：`field_id`、`field_type`（`COMMON`/`PERSONAL`）、`field_owner_id`（`PERSONAL` 时使用）、`field_is_all_viewer`（`COMMON` 时使用） |
| R2-3 | 成员明细表 `sys_org_group_user`（群组包含的用户） |
| R2-4 | 可见范围明细表 `sys_org_group_viewer`（仅 `COMMON` 使用） |
| R2-5 | 权限区分：管理员 `SYS_ORG_GROUP_ADMIN` / 普通用户（不设权） |
| R2-6 | 群组不参与组织架构树，可被删除（物理删除） |
| R2-7 | 新增群组列表 / 编辑 / 详情页，入口为顶部菜单栏右上角「多人」图形按钮 |
| R2-8 | 地址本新增「群组」页签：左侧可见群组、右侧选中群组的人员；仅当选择范围包含「人员」时可见 |
| R2-9 | 普通用户：可见自己创建的个人群组 + 自己可见的公共群组；可维护自己创建的个人群组 |
| R2-10 | 管理员：可见且可维护自己创建的个人群组 + 全部公共群组 |
| R2-11 | 编辑字段：名称、类型（普通用户锁定「个人」）、群组成员（人员多选）、可见用户（组织架构多选，个人类型隐藏；为空默认全员可见，按子集覆盖） |

## 2. 现状基线

### 2.1 数据模型

- `sys_org_element` 为主表，`field_org_type` 取值 1=机构、2=部门、3=人员、4=岗位；树字段为
  `field_parent_id` / `field_hierarchy` / `field_level`。
- `sys_org_role` 是**独立主表**（自带 `field_id`/`field_name`/`field_code`/`field_enable` 与审计字段），
  与 `sys_org_element` 无主从关系；角色通过 `sys_org_role_element(field_element_id, field_role_id)`
  关联组织架构元素，通过 `sys_org_role_auth` 关联权限。
- 人员扩展表 `sys_org_user`，其它类型扩展表为 `sys_org_org` / `sys_org_dept` / `sys_org_post`。
- 码值 `org_element_type` 定义于 `backend/src/main/resources/properties/sys/org/dict.yml`，当前仅 1~4。

## 3. 改动要点概览

| 层 | 角色（type=5） | 群组（type=6） |
| --- | --- | --- |

### D1（关键）角色是否在 `sys_org_element` 中落镜像行

需求「角色纳入组织架构子类，`field_org_type = 5`」与「历史数据不迁移」存在张力：不迁移则存量角色没有 `field_org_type = 5` 的主表记录。

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A（推荐）** | `sys_org_role` 仍为角色业务主表；新建/编辑角色时在**同一事务**内向 `sys_org_element` 写一条 `field_org_type = 5` 的镜像行（`field_id` 与角色相同，`field_parent_id`/`field_hierarchy` 置空，仅用于类型统一与地址本查询） | 真正落实「角色是组织架构子类」；地址本、`orgTypes` 语义统一；`sys_org_role_element` 无需改结构 | 双写一致性成本；存量角色在地址本「角色」页签不可见（符合「不迁移」但需业务确认可接受） |
| B | 地址本「角色」页签直接查 `sys_org_role`，不写 `sys_org_element`；仅在常量/码值层定义 `ORG_TYPE_ROLE = 5` | 零迁移、零双写、风险最低 | 严格意义上角色并未落入主表；`orgTypes=[5]` 无法直接走地址本通用 SQL |
| C | 写一次性数据迁移脚本，把存量 `sys_org_role` 全量补入 `sys_org_element` | 存量角色可在地址本选择 | 与「历史数据不做迁移」直接冲突 |

**已确认采用 A**（2026-11-04）。配套约定：

- 镜像行与 `sys_org_role` **同事务**写入，失败整体回滚；
- 新增 `SysOrgRoleService#syncElementMirror(...)` 统一封装 upsert，禁止在 Controller 层散写；
- 为存量角色提供**离线/可选**补齐脚本（不纳入 Flyway，见 `01-角色纳入组织架构分析.md` 第 8 节），由部署方按需执行；
- 不迁移是本次明确范围：存量角色默认不出现在地址本「角色」页签，需在发布说明中标注。

### D2 角色镜像行的编码与名称来源

若采用 A：`sys_org_element.field_name` / `field_code` 与 `sys_org_role` 同义字段重复。推荐**以 `sys_org_role` 为准**，
`sys_org_element` 行仅作索引与类型标识，编辑角色时同事务同步名称/编码/启用状态；读取角色详情仍取 `sys_org_role`。

### D3 角色的树字段与删除语义

- 角色不参与树：`field_parent_id = NULL`、`field_hierarchy = NULL`、`field_level = 1`（占位，不参与计算）。
- 地址本 `tree` 接口与组织管理页左侧树必须排除 `field_org_type = 5`，即使调用方传入。
- 角色删除：当前角色无删除接口（仅编辑 `field_enable`）。本次是否新增角色删除（含镜像行清理）？**建议不新增**，沿用现状。

### D4 群组「全员可见」的单一数据源

表中同时存在 `field_is_all_viewer` 与 `sys_org_group_viewer` 明细，存在双源不一致风险。推荐：

- `field_is_all_viewer` 为**派生态**：可见用户为空 ⇒ `true`（全员可见）；非空 ⇒ `false`。
- 保存时由 Service 统一计算，不接受前端直接写入该字段；`sys_org_group_viewer` 仅在 `field_type = COMMON` 时写入。
- 「可见范围向子集覆盖」按 `field_hierarchy` 前缀匹配：被选中节点及其全部后代可见。

### D5 群组「自己创建」与「所有人」的判定口径

- `field_owner_id` 为群组所有人；`sys_org_element.field_creator_id` 为创建人。二者在群组场景下应一致。
- 推荐：**以 `field_owner_id` 作为归属判定唯一依据**，创建时强制等于当前登录人且不允许修改；
  `field_creator_id` 仅作审计。普通用户「自己创建的个人群组」= `field_type = PERSONAL AND field_owner_id = 当前用户`。

### D6 公共群组的可见性对管理员是否豁免

需求「管理员可见且可维护……所有公共群组」⇒ 管理员对 `COMMON` 群组**忽略** `field_is_all_viewer` 与
`sys_org_group_viewer` 过滤；普通用户严格按可见范围过滤（全员可见 或 命中可见范围节点及其子树）。

## 7. 风险与约束

1. **双写一致性（方案 A）**：角色保存/编辑/启停用必须与镜像行同事务；失败需整体回滚。
2. **历史数据**：不迁移 ⇒ 存量角色在地址本角色页签不可见、组织管理页不受影响；需在发布说明中明确。
3. **树污染**：角色/群组 `field_parent_id` 为空，若不显式排除会出现在根级列表，必须改 SQL 与 Service 双保险。
4. **权限越权**：群组为「不设权 + 按归属过滤」，所有读写接口都必须在 Service 层做归属校验，不能只靠前端。
5. **AGENTS 约束**：新迁移脚本从 `V1_01_039` 起；新权限码必须同时改库与 `roles.yml`；新接口必须有 `ACTION_*` + resolver 分支 + `authorize(...)`；前端改动以 `npm run build` 通过为准。
