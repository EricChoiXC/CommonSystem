# 字段级可见性设计方案 —— load 接口按用户权限返回不同字段

## 1. 背景与目标

### 1.1 需求来源

[系统模块需求文档](D:/Program/erp/docs/系统模块/系统模块需求文档.md) 1.2.2 明确：

> 组织架构、机构、部门、人员、岗位**普通信息读取：不设权**
> 组织架构、机构、部门、人员、岗位**完整信息读取：人员本人 OR 组织架构管理员 OR 对应表的维护者**

即：同一个读取接口（如 `/load`），不同用户应看到不同的字段内容。本设计将该语义落地为统一的**字段级可见性（Field-Level Visibility）机制**，并复用现有 "接口标识 + 文档 ID" 的 resolver 鉴权体系。

### 1.2 目标

- 同一 `load` 接口，按当前用户的角色/归属返回**不同的字段集合**；
- 不可见字段**不输出**到响应体，同时在 `metadata` 中给出可见性说明，供前端渲染与审计；
- 机制横切所有模块（org、attachment、process、erp 等），一次实现、全模块复用；
- 规则**以代码常量配置起步，预留数据库表驱动扩展**（本次决策已确认）。

### 1.3 适用代码目录

- 后端：`artificial/backend/`（包根 `com.project.backend`）
- 本设计为机制基线，落地后需同步更新 [系统模块需求文档](D:/Program/erp/docs/系统模块/系统模块需求文档.md) 与 [系统模块API接口设计文档](D:/Program/erp/docs/系统模块/系统模块API接口设计文档.md) 中的 load 契约。

## 2. 现状与约束（代码事实）

以 `GET /backend/sys/org/user/load?fieldId=${id}` 为例，现有链路：

```text
SysOrgUserController.select(fieldId)
  → authorize(fieldId, ACTION_LOAD)             // UserResolver.resolve(ctx)，返回 允许/拒绝
  → SysOrgUserService.selectById(fieldId)       // BaseService 继承方法，查全量字段
  → SysOrgUserResponse.success(model)           // data = 完整 SysOrgUser（所有字段）
```

关键事实与约束：

| 事实/约束 | 出处 |
| --- | --- |
| resolver 语义被规范限定为"允许/拒绝"（boolean 结论 + 可追踪原因），不做数据裁剪 | [开发规范](D:/Program/erp/docs/开发规范.md) 三.8 |
| Controller 只接收/校验/返回，不写业务逻辑；业务逻辑在 Service | 开发规范 二.2、AGENTS.md 4.1 |
| 鉴权核心参数 = 接口标识(action) + 文档ID(documentId)，承载于 `AuthorizationContext` | `common/resolver/AuthorizationContext.java` |
| 当前用户经 `UserUtil.getCurrentUser()` 获取（含角色列表） | `common/utils/UserUtil.java`、`CurrentUserHolder` |
| 模型对象当前直接作为响应 `data`（`SysOrgUserResponse extends BaseResponse<SysOrgUser>`） | `sys/org/response/SysOrgUserResponse.java` |
| 字段统一 `field_` 前缀；数据库变更走 Flyway | 开发规范 三.5、AGENTS.md 6 |
| 现有常量类模式：`SysOrgUserProperties`（ACTION_*、ROLE_*） | `sys/org/properties/SysOrgUserProperties.java` |
| 批量鉴权接口仅用于前端预判，不能替代最终鉴权 | 开发规范 三.8 |

## 3. 总体设计

### 3.1 两层权限模型

| 层级 | 语义 | 现有/新增 | 返回 |
| --- | --- | --- | --- |
| ① 文档访问级 | 该用户**能否**访问该文档 | 现有 resolver（如 `UserResolver`） | 允许/拒绝 |
| ② 字段可见级 | 允许访问后，**哪些字段**可见 | 新增 `FieldVisibilityResolver` | 可见字段集合 + 策略 |

两层必须**串行执行**：① 拒绝则直接返回 FORBIDDEN；① 通过后由 ② 决定响应字段子集。

### 3.2 总体流程

```text
GET /backend/sys/org/user/load?fieldId=${id}
  ├─ Controller.select(fieldId)
  │    ├─ ① authorize(fieldId, ACTION_LOAD)                 # 现有 UserResolver，允许/拒绝（不变）
  │    ├─ ② FieldVisibilityResult v =
  │    │      userResolver.resolveFieldVisibility(ctx)       # 新增：角色/归属 → 可见字段集
  │    └─ Map<String,Object> data =
  │           service.loadDetail(fieldId, v)                 # 新增：查全量 + FieldProjector 裁剪
  └─ 返回 SysOrgUserDetailResponse
        data     = 仅可见字段
        metadata = { policy, visibleFields, hiddenFields }
```

### 3.3 设计原则

1. **不破坏 resolver 语义**：允许/拒绝仍由 resolver 负责；字段可见性判定作为 resolver 的"附加能力"（新增方法返回 `FieldVisibilityResult`），不改变既有 `resolve` 契约。
2. **裁剪逻辑归属 Service**：Controller 只调用 `service.loadDetail(...)`，不出现业务分支。
3. **通用机制放 common，业务规则放模块**：`FieldVisibilityResult`、`FieldVisibilityResolver` 骨架、`FieldProjector` 放 `common`；`SysOrgUser` 的可见性规则放 `sys/org`。
4. **字段不输出 + metadata 说明**（本次决策已确认）：不可见字段不出现在 `data` 中；前端依据 `metadata.visibleFields / hiddenFields` 渲染，不依赖"字段是否存在"猜测。
5. **规则可平滑升级**：代码常量配置为默认实现，通过统一接口预留表驱动实现，`@ConditionalOnProperty` 切换。

## 4. 权限模型细化

### 4.1 文档访问级（沿用现有，不改造）

- `UserResolver.resolve(ctx)` 保持"允许/拒绝"语义不变；
- 各接口仍定义自身 resolver，禁止复用无差别的通用判断。

### 4.2 字段可见级（新增）

判定输入：

- 当前用户（`UserUtil.getCurrentUser()`，含角色列表）
- 接口标识（`ctx.getAction()`）
- 文档 ID（`ctx.getDocumentId()`，load 场景即被查看对象的 fieldId）

判定输出：`FieldVisibilityResult`

| 属性 | 说明 | 示例 |
| --- | --- | --- |
| `policy` | `FULL`：所有字段可见；`PARTIAL`：部分字段可见 | `PARTIAL` |
| `visibleFields` | 可见字段名集合（`field_` 前缀的 Java 属性名） | `[fieldId, fieldName, ...]` |
| `hiddenFields` | 隐藏字段名集合 = 全字段 - 可见字段 | `[fieldPhone, fieldEmail, ...]` |
| `reason` | 判定依据（角色/归属），供审计与前端提示 | `role=SYS_ORG_USER_MANAGER` |

### 4.3 规则定义（代码常量起步）

以 `sys.org.user.load` 为例（字段清单以需求确认为准，以下为设计示例）：

```java
// sys/org/properties/SysOrgUserProperties.java（或独立 SysOrgUserFieldVisibilityProperties）
/** 普通信息（任意有读权用户可见） */
public static final Set<String> USER_LOAD_PUBLIC_FIELDS = Set.of(
        "fieldId", "fieldCode", "fieldName",
        "fieldCreatorId", "fieldCreateTime", "fieldUpdaterId", "fieldUpdateTime", "fieldEnable");

/** 完整信息才可见（隐私字段） */
public static final Set<String> USER_LOAD_PRIVATE_FIELDS = Set.of(
        "fieldPhone", "fieldEmail", "fieldAddress", "fieldGender", "fieldBirthday", "roles");
```

完整可见判定规则（`UserResolver.resolveFieldVisibility`）：

```text
完整可见 = 当前用户角色含 ROLE_SYS_ORG_ADMIN
        OR 当前用户角色含 ROLE_SYS_ORG_USER_MANAGER（人员维护者）
        OR 当前用户 == 目标文档（documentId == 当前用户 fieldId，本人）
否则 → PARTIAL，可见字段 = USER_LOAD_PUBLIC_FIELDS
```

规则注册表（通用机制，`common/resolver`）：

```java
// common/resolver/FieldVisibilityRule.java
public class FieldVisibilityRule {
    private final String action;                       // 接口标识，如 sys.org.user.load
    private final Set<String> publicFields;            // 公共可见字段
    private final Predicate<AuthorizationContext> fullVisible;  // 完整可见判定
}

// common/resolver/CodeFieldVisibilityResolver.java
public class CodeFieldVisibilityResolver implements FieldVisibilityResolver {
    private final Map<String, FieldVisibilityRule> rules = new HashMap<>();
    // 模块通过 register(rule) 注册规则；resolve(ctx) 按 action 查规则并输出 FieldVisibilityResult
}
```

### 4.4 预留表驱动扩展（Phase 2）

```text
sys_field_visibility
  field_id             varchar(32)  PK
  field_module         varchar(50)           -- 模块，如 sys.org
  field_action         varchar(100)          -- 接口标识，如 user.load
  field_role_id        varchar(32)           -- 角色 ID；空 = 公共默认
  field_visible_field  varchar(50)           -- 可见字段名（field_ 前缀）

```

- 新增 `TableFieldVisibilityResolver implements FieldVisibilityResolver`（查询上表组装 `FieldVisibilityResult`）；
- 通过 `@ConditionalOnProperty(prefix = "erp.field-visibility", name = "mode", havingValue = "table")` 切换，业务调用方（Controller/Service）**无需改动**；
- 需配套 Flyway 迁移脚本（如 `V13__sys_field_visibility_schema.sql`）与种子数据、角色维护者维护接口。

### 5.2 关键类设计

**FieldVisibilityResult**

```java
@Data
public class FieldVisibilityResult {
    private String policy;                 // FULL / PARTIAL
    private Set<String> visibleFields;
    private Set<String> hiddenFields;
    private String reason;

    public Map<String, Object> toMetadata() {
        Map<String, Object> m = new LinkedHashMap<>();
        m.put("policy", policy);
        m.put("visibleFields", visibleFields);
        m.put("hiddenFields", hiddenFields);
        return m;
    }
}
```

**FieldProjector**（通用裁剪，反射按可见字段拷贝）

```java
public final class FieldProjector {
    /** 仅保留 visibleFields 命中的属性，输出 Map；嵌套对象（如 roles）整体保留 */
    public static Map<String, Object> project(Object source, Collection<String> visibleFields) {
        // 1. 遍历 visibleFields，解析 JavaBean getter（属性名与字段名一致，如 fieldName）
        // 2. 仅拷贝命中字段；未命中字段不进入结果 Map
        // 3. 嵌套集合（List<SysOrgRole> roles）按字段名整体放入（Phase 2 支持 "roles.fieldCode" 子字段裁剪）
    }
}
```

**SysOrgUserService 新增**

```java
@Service
public class SysOrgUserService extends BaseService<SysOrgUser, SysOrgUserDao> {
    /** load 专用：查全量 → 按可见字段集裁剪，业务逻辑归属 Service */
    public Map<String, Object> loadDetail(String id, FieldVisibilityResult visibility) {
        SysOrgUser model = selectById(id);
        return FieldProjector.project(model, visibility.getVisibleFields());
    }
}
```

**UserResolver 新增**

```java
public class UserResolver extends BaseResolver {
    // 原有 resolve 允许/拒绝逻辑不变

    /** 字段可见性判定：完整可见 OR 公共字段集 */
    public FieldVisibilityResult resolveFieldVisibility(AuthorizationContext context) {
        SysOrgUser current = UserUtil.getCurrentUser();
        boolean full = isAdminOrUserManager(current)
                || (current != null && current.getFieldId().equals(context.getDocumentId()));
        if (full) {
            return FieldVisibilityResult.full(ALL_FIELDS, "FULL: admin/manager/self");
        }
        return FieldVisibilityResult.partial(USER_LOAD_PUBLIC_FIELDS, ALL_FIELDS,
                "PARTIAL: default public fields");
    }
}
```

> 实现细节：`FieldVisibilityResult.full/partial` 静态工厂负责计算 `visibleFields/hiddenFields`，避免各 resolver 重复写集合差集逻辑。

**SysOrgUserController.load 改造**

```java
@GetMapping("/load")
public SysOrgUserDetailResponse select(@RequestParam("fieldId") String fieldId) {
    authorize(fieldId, ACTION_LOAD);                       // ① 允许/拒绝（不变）
    AuthorizationContext ctx = loadContext(fieldId);       // action=ACTION_LOAD, documentId=fieldId
    FieldVisibilityResult visibility = userResolver.resolveFieldVisibility(ctx);  // ② 可见字段集
    Map<String, Object> data = getBaseService().loadDetail(fieldId, visibility);  // ③ 裁剪
    return SysOrgUserDetailResponse.success(data, visibility.toMetadata());       // ④ 响应
}
```

### 5.4 兼容性说明

- `load` 接口的 `data` 从"全字段 `SysOrgUser`"变为"可见字段子集（`Map`）"，属**预期契约变更**，需前后端同步改造；
- `save/update/delete/list` 接口本轮**不改造**，保持 `SysOrgUserResponse` 不变；
- 前端详情页/表单回填改为按 `metadata.visibleFields` 渲染，隐藏字段不回显。

## 6. 前端联动

- `load` 成功后读取 `metadata.policy / visibleFields / hiddenFields`：
  - `FULL`：正常渲染全表单；
  - `PARTIAL`：仅渲染 `visibleFields` 对应控件，隐藏控件不渲染、不提交；
- 编辑场景：被隐藏字段提交为 `null` 时，后端 `update`（mapper 已按 `<if test="fieldXxx != null">` 动态拼接）天然忽略，不会覆盖原值；如后续需要更强约束，见 7.4 可编辑白名单；
- 列表页按钮显隐仍走批量鉴权接口，字段可见性不做前端预判接口（最终以后端 load 裁剪为准）。

## 7. 安全边界与注意事项

1. **隐藏字段必须不出现在响应 JSON 中**：`FieldProjector` 的 Map 裁剪保证；禁止依赖 `@JsonIgnore` 等隐式方案（不可调试、易误伤）。
2. **超高敏字段（后续如密码哈希、身份证号）走 SQL 列裁剪**：Mapper 增加 `selectByIdScoped(id, columns)` 动态列查询，敏感列不出库、不进内存；普通敏感度字段（手机号、邮箱）本轮走 `FieldProjector` 出参裁剪即可。
3. **本人判定**：`documentId == 当前用户 fieldId` 只适用于"被查看对象是用户"的场景；其他实体（如机构、单据）的"归属本人"语义由各模块规则自行定义。
4. **防越权写入**：`update/save` 接口应校验请求 body 字段是否在"可编辑白名单"内（Phase 2 落地），防止用户手工构造请求写入被隐藏字段。
5. **list/export 复用**：列表列可见性与导出列可见性复用同一 `FieldVisibilityResolver`（Phase 2），本轮不实现。
6. **审计**：`reason` 记录了字段可见性判定依据，可作为审计线索；如需要可随审计模块写入操作记录。
7. **缓存**：代码常量规则无需缓存；表驱动实现后规则查询可加本地/Redis 缓存（规则变更频率低）。

## 9. 备选方案对比

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. resolver 直接返回字段集并裁剪 | 少一层调用 | 违反 resolver"允许/拒绝"语义，与规范冲突 | 不采用 |
| B. 出参 Map 裁剪（本设计） | 通用、横切复用、不可见字段天然不出 JSON；与现有分层一致 | 普通敏感字段仍在内存过一圈 | **采用**（结合 C 处理超高敏字段） |
| C. SQL 动态列裁剪 | 最强安全，敏感列不出库 | 每表需两套 SQL，维护成本高 | 仅对超高敏字段局部采用 |
| D. Jackson 全局过滤（@JsonView/Filter） | 少写裁剪代码 | 隐式、静态视图难做运行时角色差异、易误伤 | 不采用 |
| E. 每模块手写"可见 VO" | 类型安全 | 每张表两个 VO，模型膨胀、重复代码 | 不采用（Map + metadata 已满足） |
