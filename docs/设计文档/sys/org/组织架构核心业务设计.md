# 组织架构核心业务设计

> 本文档描述组织架构（org）模块的业务规则与权限模型，依据现有实现（后端 `com.common.system.sys.org`、前端 `views/org`）回写。
> 接口约定见 [组织架构接口清单.md](./组织架构接口清单.md)，后端实现见 [组织架构后端业务设计.md](./组织架构后端业务设计.md)，
> 数据结构见 [组织架构表结构.md](./组织架构表结构.md)，页面交互见 [组织架构前端页面设计.md](./组织架构前端页面设计.md)。

## 权限

权限码存储于 `sys_org_role.field_code`（权限判定经 `sys_org_role_auth` 关联 `sys_org_auth.field_code`），
由 `backend/src/main/resources/properties/sys/org/roles.yml` 定义并在启动时增量同步到 `sys_org_auth`。

| 权限名 | 中文名 | 描述 |
| --- | --- | --- |
| SYS_ADMIN | 系统管理员 | 超级管理员（`CommonProperties.ROLE_ADMIN`），后端 `BaseResolver` 与前端 `hasAuth` 均自动放行，不在模块分支中重复列举 |
| SYS_ORG_ADMIN | 组织架构模块管理员 | 拥有该模块下所有权限（元素增删改查、人员维护、修改密码、角色管理） |
| SYS_ORG_ELEMENT_ADMIN | 组织架构管理员 | 拥有所有 `SYS_ORG_ELEMENT_*` 权限 |
| SYS_ORG_ELEMENT_ADD | 组织架构添加权限 | 添加组织架构元素；同时用于「置为无效」（删除）鉴权 |
| SYS_ORG_ELEMENT_EDIT | 组织架构编辑权限 | 修改组织架构元素、启停用 |
| SYS_ORG_ROLE_ADMIN | 权限管理员 | 拥有权限、角色管理权限（角色列表/新建/编辑/权限选项、权限预览） |
| SYS_ORG_USER_MANAGER | 人员维护者 | 可维护人员信息与修改密码 |
| SYS_ORG_GROUP_ADMIN | 群组管理员 | 可见并维护全部群组（全部公共群组 + 全部个人群组，含他人个人群组）；接口层仅要求登录，归属与可见性由 `SysOrgGroupService` 判定。口径备注：管理员可见范围含他人个人群组（04 鉴权矩阵「全部」口径，VisibleClause 管理员分支短路） |

## 核心功能

### 组织架构

组织架构元素分六类（`field_org_type`）：1=机构、2=部门、3=人员、4=岗位、5=角色、6=群组；
「虚拟组织」是元素级标记（`field_is_virtual`），虚拟组织可作为上级挂机构/部门/人员/岗位。

> 角色（5）与群组（6）**不参与组织架构树**：`field_org_type IN (5, 6)` 的行 `field_parent_id` / `field_hierarchy` 为 `NULL`、
> `field_level = 1`，组织管理页树与根级列表、地址本树查询均永久排除该两类；
> `sys.org.element.*` 接口写入校验只接受 1~4（`SysOrgElementProperties.ELEMENT_WRITABLE_ORG_TYPES`）。
> 两类数据分别由角色（`sys.org.role.*`）与群组（`sys.org.group.*`）维护接口管理。

#### 层级规则（树形结构）

- 层级仅由主表 `sys_org_element` 三字段表达：`field_parent_id`（根级为 `NULL`）、
  `field_hierarchy`（形如 `/{根id}/{子id}/`，含自身）、`field_level`（根级为 1，向下递增）；
- 上级可选范围仅限**非虚拟组织的机构或部门**（1/2 且 `field_is_virtual = false`）；
- 保存/编辑时由 `SysOrgElementService#rebuildHierarchy` 计算层级；编辑发生父级变更时，新父级不能是自身或其后代
  （按 `field_hierarchy` 前缀判定，防环），并递归修正全部直接/间接下级的 `field_hierarchy` / `field_level`；
- 「启停用」（enable）仅更新元素自身一行，不级联后代；
- 「置为无效」按物理删除实现（主表 + 对应类型扩展表同事务删除），仅允许无直接下级的节点。

#### 创建组织架构元素

拥有 `SYS_ORG_ELEMENT_ADMIN`（或 `SYS_ORG_ADMIN`、`SYS_ORG_ELEMENT_ADD`）权限的用户可以进行组织架构元素的创建；

创建时，需要指定组织架构元素的类型，是否虚拟组织为独立开关，两者不存在冲突；

根据选择的组织架构类型，页面上提供公共字段填写和类型专有字段填写：

| 字段名 | 描述 | 是否必填 | 默认值 | 所属 |
| --- | --- | --- | --- | --- |
| field_name | 名称 | 是 | `` | 公共字段 |
| field_code | 编码 | 是 | `` | 公共字段 |
| field_parent_id | 上级组织架构元素 | 否 | 根据进入新建页面时的树形地址本选中项决定 | 公共字段 |
| field_org_type | 组织架构类型 | 是 | 根据进入新建页面时查询列表的查询条件决定，无时默认 `机构`（编辑时禁用，不可变更） | 公共字段 |
| field_is_virtual | 是否虚拟组织 | 是 | `否` | 公共字段 |
| field_enable | 启用状态 | 是 | `启用` | 公共字段 |
| field_leader_id | 组织架构负责人 | 否 | `` | 机构、部门、岗位字段 |
| field_phone | 联系电话 | 否 | `` | 机构、部门、人员字段 |
| field_email | 联系邮箱 | 否 | `` | 机构、人员字段 |
| field_address | 联系地址 | 否 | `` | 机构、部门、人员字段 |
| field_login_name | 登录名 | 是 | `` | 人员字段 |
| field_password | 密码 | 是（仅新建） | `` | 人员字段 |
| field_gender | 性别 | 是 | `男` | 人员字段 |
| field_birthday | 生日 | 否 | `` | 人员字段 |
| field_job_status | 在岗状态 | 是 | `在职` | 人员字段 |

补充约束：

- 上级组织架构元素的可选范围仅限非虚拟组织的机构或部门；
- 人员 `field_login_name` 唯一（库上唯一索引兜底），且不可为邮箱格式、不可为 11 位纯手机号；
  联系电话（`field_phone`）、联系邮箱（`field_email`）在人员间亦唯一；
- 人员 `field_password` 仅新建时在表单中设置初始密码（必填），后续一律通过「修改密码」弹窗（`changePwd` 接口）维护；
- 岗位-人员关联（`sys_org_post_user`）、虚拟组织-人员关联（`sys_org_virtual_user`）目前仅由数据侧维护，
  组织架构保存/编辑接口不写入，前端页面不提供入口（预留）。

#### 编辑组织架构元素

拥有 `SYS_ORG_ELEMENT_EDIT` 权限（或 `SYS_ORG_ADMIN` / `SYS_ORG_ELEMENT_ADMIN`）、或用户本人，可进行组织架构元素的编辑维护；

对人员（`field_org_type = 3`）的维护范围视维护人而定：

> 用户本人：仅允许维护联系电话、联系邮箱、联系地址、性别、生日；
> 权限用户：可允许维护所有可填写字段。

> 人员的密码不在编辑/详情表单中维护：前端编辑/查看页通过按钮区「修改密码」弹窗修改，走 `changePwd` 接口；
> 编辑/更新接口（`sys.org.element.update`、`sys.org.user.update`）一律忽略请求中携带的密码字段。

#### 密码安全

- `field_password`（密码）在创建用户时必填，以 **BCrypt 单向加密**（自带随机盐、不可逆，`PasswordUtil.encode/matches`）后入库，明文不落库；
- 任何查询（load / list / 导出）的列集合都不返回密码字段（模型上标注 `@JsonProperty(WRITE_ONLY)`，响应永不回显）；
- 修改密码走 `changePwd` 接口（`PATCH /backend/sys/org/user/changePwd`），仅更新 `field_password` 与 `field_last_chg_pwd_time`，不影响用户其他字段；
- `changePwd` 鉴权与编辑一致：`SYS_ORG_ADMIN`、`SYS_ORG_USER_MANAGER` 或用户本人；
- 密码长度 6–32 位；新密码不得与最近 N 次历史密码相同（`KEY_PWD_REPEAT_LIMIT`，全量比对 `sys_org_pwd_history`）；
- 定期改密：距 `field_last_chg_pwd_time` 超过 `KEY_PWD_CHANGE_CYCLE`（天）后，登录响应携带 `metadata.forceChangePwd`，
  前端跳转强制改密页（`/changePwd`）；`GET /backend/sys/org/user/checkPwdChange` 可随时查询该标记。

#### 读取，查询组织架构元素

不设权（已登录且账号启用即可查询），仅对人员数据做可读信息限制：

> 用户本人、权限用户（`SYS_ORG_ADMIN` / `SYS_ORG_ELEMENT_*` 任一权限，或该用户在人员直属组织架构链路上的
> 机构/部门的负责人/管理员）：除密码不限制；
> 非本人、非权限用户：登录名不可见，联系电话、联系邮箱、联系地址做脱敏处理。

实现为「双保险」：`UserResolver.loadVisibleResult` 按登录人判定可见性标识
（`SYS_ORG_ADMIN` = 完整 / `SYS_ORG_USER_VISITOR` = 受限），`SysOrgUserMapper` 的 `BaseColumns`（完整列）
与 `NormalColumns`（脱敏列）按该标识二选一；列表接口同时由 `SysOrgElementService` 对返回 VO 做登录名裁剪兜底。

### 权限与角色

#### 创建与维护角色

拥有 `SYS_ORG_ROLE_ADMIN` 权限（或 `SYS_ORG_ADMIN`）的用户可创建或编辑角色；

编辑信息：

| 字段名 | 描述 | 是否必填 | 关联表 |
| --- | --- | --- | --- |
| field_name | 角色名称 | 是 | sys_org_role |
| field_code | 角色编码（权限码，前端 hasAuth 判定依据） | 否 | sys_org_role |
| field_enable | 角色是否启用 | 是（默认启用） | sys_org_role |
| elementIds | 组织架构列表（地址本多选，保存时全量替换） | 否 | sys_org_role_element |
| authIds | 权限列表（按模块分组复选，保存时全量替换） | 否 | sys_org_role_auth |

角色删除、角色启停用接口当前未提供（角色仅可编辑与停用于表单内 `field_enable`）。

系统内置管理员角色 `SYS_ADMIN`（`field_id = 32 个 '0'`），由启动任务 `ensureSystemAdminRole` 幂等创建并绑定管理员用户，不在角色管理页维护。

#### 角色纳入组织架构（v1.1）

角色（`field_org_type = 5`）纳入组织架构后，在 `sys_org_element` 同事务维护镜像行（`field_id` 与角色一致）：

- 维护时机：`saveRole` / `updateRole` / `ensureSystemAdminRole` 均经 `SysOrgRoleService#syncElementMirror`
  同事务维护——缺失时按角色全字段插入；已存在时经专用 SQL `updateRoleMirror` 仅同步名称/编码/启用与审计字段，
  不复用通用 update（其对 `field_level` / `field_org_type` / `field_is_virtual` 无条件赋值，禁止用于镜像行）；
  更新返回 0 行视为镜像行缺失，补插入自愈；异常随事务回滚角色与镜像行；
- 镜像行取值：`field_org_type = 5`、`field_parent_id` / `field_hierarchy` 为 NULL、`field_level = 1`（不参与树）；
  **镜像行 `field_code` 存角色编码**（角色编码可空，同步时允许为 NULL / 清空）；
- 树与组织管理列表排除：`SysOrgElementMapper.xml#VoWhereClause` 根级分支与 `SysOrgAddressBookMapper.xml#selectTree`
  固定 `field_org_type NOT IN (5, 6)`，角色/群组不进组织管理树与地址本树；
- 写入口径：`sys.org.element.*` 通用维护接口经 `SysOrgElementService#validateCommon` 白名单
  （`ELEMENT_WRITABLE_ORG_TYPES = Set.of(1, 2, 3, 4)`）拒绝写入类型 5/6，角色仅经 `sys.org.role.*` 维护；
- 地址本「角色」页签：`AddressBook.vue` `showRole` 开启时渲染（默认关闭），复用通用 `addressbook/list` 接口
  传 `orgTypes = [5]`（方案 A，无新接口），角色无层级、分页表格 + 独立刷新按钮，选择结果为角色 id/名称；
- 存量角色**不做迁移**（明确决策）：镜像行仅由角色写路径增量维护，历史角色无镜像行（不进组织树/列表，不影响角色管理页与鉴权）；
  如需补齐可手工执行离线可选脚本（分册建议路径 `docs/v1_1/01-组织架构改动/sql/optional_backfill_org_role_element.sql`，由实施方决定执行与否）。

### 群组管理（v1.1，`field_org_type = 6`）

群组为「主表镜像行 + 扩展表 + 两张明细表」的建模，与角色镜像行同构：

| 项 | 说明 |
| --- | --- |
| 主表镜像行 | `sys_org_element`（`field_org_type = 6`，`field_parent_id` / `field_hierarchy` 为 NULL、`field_level = 1`，不参与树）；**镜像行 `field_code` 恒写空串**（列 `NOT NULL`，禁写 NULL，与角色镜像行存编码不同） |
| 扩展表 | `sys_org_group`（`field_type` COMMON/PERSONAL、`field_owner_id`、`field_is_all_viewer`） |
| 成员明细 | `sys_org_group_user`（复合主键，成员为启用人员 `field_org_type = 3`） |
| 可见范围明细 | `sys_org_group_viewer`（复合主键，可见范围限机构/部门/岗位/人员且非虚拟组织） |

核心规则（详见分册 `docs/v1_1/01-组织架构改动/02-群组功能分析.md` 2.2/2.3）：

- 可见性（VisibleClause，列表/单条/地址本群组页签同口径）：**管理员（SYS_ADMIN / SYS_ORG_ADMIN / SYS_ORG_GROUP_ADMIN）分支短路、可见全部群组**（含他人个人群组，取 04 鉴权矩阵「全部」口径）；普通用户 = 自己的个人群组 OR（公共群组 AND（全员可见 OR 可见范围命中））；可见范围四类节点判定：机构/部门按用户 `field_hierarchy LIKE '%/viewerId/%'`（含后代）、岗位经 `sys_org_post_user`、人员精确等于本人 id；
- 维护权限：普通用户仅可创建个人群组、仅可维护自己的个人群组且不可改类型（Service 强制，前端表单类型下拉同步锁定）；管理员可维护全部公共群组与自己的个人群组（他人的个人群组不可维护）；
- 归属与派生：`field_owner_id` 新建取当前登录人、编辑恒保持原值；`field_is_all_viewer` 一律按「可见范围明细是否为空」派生（明细空 ⇒ 1，前端传值无效）；`PERSONAL` 不写可见范围明细、恒全员可见；成员/可见范围明细保存与编辑均全量替换（先删后插）；
- 删除：物理删除，同事务按 成员明细 → 可见范围明细 → 群组扩展行 → 主表镜像行 顺序删除；
- 接口：维护 5 个（`sys.org.group.list/load/save/update/delete`）+ 地址本 2 个（`addressbook.groupList/groupUsers`），均「不设权 + 数据级过滤」（接口级仅要求登录，可见性与维护权限由 Service 承担）；
- 页面：群组管理（`/org/group`）、新建/编辑（`/org/group/create`、`/edit/:id`）、详情（`/org/group/detail/:id`）三段式页面，地址本「群组」页签（`showGroup`，按群组批量选人）。

#### 权限计算

用户权限集合 = 以该用户为起点、按以下四个来源取到的角色（须启用）所绑定的权限（`sys_org_role_auth` → `sys_org_auth`，须启用）的并集：

1. **直属人员元素**：人员（`field_org_type = 3`、非虚拟）自身通过 `sys_org_role_element` 绑定的角色；
2. **所属岗位**：经 `sys_org_post_user` 关联的岗位元素绑定的角色；
3. **所属虚拟组织**：经 `sys_org_virtual_user` 关联的虚拟组织元素绑定的角色；
4. **直属组织架构链路**：以该人员的 `field_hierarchy` 为前缀向上追溯的全部机构/部门元素
   （`field_org_type IN (1, 2)`）绑定的角色。

即：从用户出发，包含所属岗位、所属虚拟组织架构，及其直属组织架构链路上的机构/部门，这些组织架构元素拥有的角色和权限的集合，即为用户的权限集合。

计算结果在登录时随用户信息返回（`roles` 角色列表、`auths` 权限码列表），前端存储于 `localStorage`
（键 `common_user`），经 `utils/auth.js#hasAuth` 做按钮/菜单级预判；最终权限仍由后端各 `Resolver` 在接口层兜底。
