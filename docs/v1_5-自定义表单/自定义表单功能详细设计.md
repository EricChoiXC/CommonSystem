# 自定义表单功能详细设计（v1.5）

- 自定义表单是本工程的**动态表单引擎**：统一组件协议与前端物料库 + 表单设计器 + 动态渲染器 + 动态规则引擎（前后端各一）+ 表单数据引擎（JSON 存储）+ 不可变版本管理，为 v1.8 BPM 提供表单与字段级权限元数据底座，不是某个业务页面的附属表单。
- 落地顺序依据 [docs/开发计划.md](../开发计划.md) 依赖图：`公式定义器 → 自定义表单 → BPM`；F14 公式定义器已于 2026-11-18 收尾（`FormulaDesigner` 组件与 options/functions/validate/simulate 四接口可用）、F18 数据源取数通道已落地，本模块无外部阻塞。
- 模块编号 F15，模块 key 为 `form`，包 `com.eric.base.sys.form`，表 `sys_form` / `sys_form_version` / `sys_form_data`（一期三表倾向，R05 随数据库分册定稿），权限码候选 `SYS_FORM_ADMIN`。
- 源文档：[自定义表单开发要点.md](自定义表单开发要点.md)（主输入：五层架构、10 步开发路径、8 表草案、JS 响应函数安全建议、三条架构原则）、[自定义表单组件.md](自定义表单组件.md)（主输入：组件全集与固定属性项）。两份输入存在待裁决分歧（xml vs JSON Schema、组件清单口径、明细表嵌套等），本文 §0.3 逐条裁决；本文按 §7 将要点文档第 9 步的 domain/repository 通用建议映射为仓库分层规范。

### 0.3 关键裁决（R01~R04/R08）

#### R01 Schema 序列化格式：JSON Schema（定稿）

- **分歧描述**：组件文档第 1 条写「封装 xml、解析 xml 生成配置页，编辑页，详情页」；要点文档第 2 步写「设计器最终输出统一的 JSON Schema」并在第四节技术选型列 JSON Schema / Ajv / Monaco Editor。影响协议 POJO、解析器与全部下游任务。
- **候选方案对比**：

| 方案 | 优势 | 劣势 |
| --- | --- | --- |
| A. JSON Schema（要点文档） | 仓库 JSON 列先例充分（`sys_formula.field_dependencies`、`sys_task_main.field_params`、`sys_number_rule.field_rule`、`sys_process_template_node.field_node_config`）；Jackson 协议 POJO 先例（`SysProcessTemplateNodeConfigDo`）；前端 JS 生态原生（Ajv/Monaco/JSON 编辑器均以 JSON 为对象模型）；前后端解析零成本；设计器导入导出即 JSON 文件 | 无（相对本场景） |
| B. XML（组件文档） | XSD 等文档类型定义体系成熟 | 仓库零先例；前端需额外引 XML 解析库，Vue/JS 生态以 JSON 为主；与 Jackson 协议 POJO、Ajv/Monaco 选型直接冲突；解析与转义成本高，转 JSON 的中间层无收益 |

- **裁决结论**：**采用方案 A，一期序列化定稿 JSON Schema**；组件文档 xml 表述按裁决标注修正（标注保留原文不删除，见文末同步记录）。
- **理由**：与仓库既有 JSON 存储与 POJO 序列化惯例一致（一处先例即可类推，这里是成体系的先例族）；前后端均为 JSON 原生，解析成本最低；Ajv/Monaco 生态即开即用；Schema 以 JSON 文件导入导出天然成立。
- **影响面与下游任务**：F15-BE-001（协议 POJO + Jackson 序列化 + `ColumnType.JSON` 列）、F15-DOC-003（`field_schema_json` / `field_form_data` JSON 列口径）、F15-FE-002（registry 与 Schema 编辑）、F15-FE-008（导入导出 JSON 文件）；R07 中 Ajv 依赖可由自研轻量结构校验器替代（倾向自研：校验规则即 §2.2 资源限制常量 + §3 DSL 合法性，不需要完整 JSON Schema Draft 校验器；随 F15-BE-001/F15-FE-002 编码复核）。

#### R02 JS 响应函数：一期仅预留协议，不落地执行引擎（定稿）

- **分歧描述**：要点文档第 1/4 步与第三节要求 JS 响应函数（代码块组件 + 八事件 + 统一上下文），并给出安全建议；后端沙箱（GraalJS/QuickJS）成本高，前端 `eval` 有注入风险。v1.5 一期落地深度未定。
- **候选方案对比**：

| 方案 | 说明 | 评估 |
| --- | --- | --- |
| A. 一期落地后端沙箱执行（GraalJS） | 完整代码块能力 | 沙箱硬化是独立安全工程（超时/内存/类白名单/权限白名单/后端不信任前端结果全套单测），pom 新增大依赖，v1.5 排期风险高；80% 常见业务已可由声明式规则 DSL + F14 公式覆盖 |
| B. 一期仅预留协议、二期隔离执行（推荐） | 代码块组件协议位 + 规则 DSL 覆盖常见业务 | 不触碰安全红线（不 eval）；要点文档自身建议「80% 常见业务通过可视化规则完成，复杂业务再使用代码块」，两者分离正是分期依据 |
| C. 前端 eval / new Function 执行 | 成本最低 | 注入风险，要点文档安全建议明令禁止，直接否决 |

- **裁决结论**：**采用方案 B**。一期仅：①预留代码块组件协议位（type=`code`，不注册物料、物料栏不展示）；②登记事件清单与统一上下文协议（§3.7）；③规则 DSL 不含 script 类动作（一期动作全集 §3.3）。**不落地任何 JS 执行引擎**；二期以 GraalJS/受限解释器隔离执行，落地时全数采纳要点文档安全建议（不使用 `eval`、限制执行时间/内存/可访问对象、禁直接访问 JVM/数据库/OS、后端独立执行关键业务校验不信任前端 JS 结果、业务接口走权限白名单）。
- **理由**：安全面优先——沙箱不是「能跑就行」的功能项，而是需要专项单测（超时/超内存/禁用对象访问）与部署参数的安全工程；声明式 DSL + 公式字段的组合已覆盖显隐/联动/动态校验/自动计算等主流诉求；先协议后引擎的分期方式保证二期落地时协议不变、只补执行通道。
- **影响面与下游任务**：F15-BE-007 随此**移出 v1_5**（任务标记 SKIPPED，工作量转移至后续版本专项）；R07 中 Monaco Editor 一期不引入；UI 分册不设计代码块编辑面板；§3.7 为二期落地的协议契约。

#### R03 组件清单：组件文档基线 + 分组/栅格布局组件（定稿）

- **分歧描述**：组件文档列 12 数据 + 4 内容 + 1 控制（无布局组件）；要点文档第 1 步列基础输入（含密码）、人员组件（员工/部门/岗位/角色）、数据组件（含关联数据/自动编号）、高级组件（富文本/图片/地图）、布局组件（分组/栅格/标签页/折叠面板）、明细组件（含嵌套明细表）、自定义组件，两份清单不一致。
- **候选方案对比**：

| 方案 | 说明 | 评估 |
| --- | --- | --- |
| A. 严格按组件文档 | 12 数据 + 4 内容 + 1 控制 | 缺布局组件，分组排版类诉求无处安放；人员四组件与地址本重复建设 |
| B. 按要点文档全集 | 两份清单并集 | 范围失控：地图/关联数据/富文本/自定义组件均无 v1.5 需求来源，自动编号还依赖 v1.6 编号机制 |
| C. 组件文档基线 + 布局组件（分组/栅格）+ 人员类并入地址本 + 密码并入单行文本（推荐） | 裁剪合并 | 复用既有公共组件能力，一期范围可控，协议留扩展位 |

- **裁决结论**：**采用方案 C**。一期组件全集 = 组件文档基线（12 数据：单行文本/多行文本/数字/选择框/下拉选择器/日期/开关/级联选择器/公式计算/数据源/地址本/附件 + 4 内容：表格/明细表/文本/图片）**+ 布局组件一期仅「分组、栅格」两项 + 控制类权限组件仅预留协议位**（运行时随 v1.8 BPM 消费）。人员类（员工/部门/岗位/角色）**由地址本组件覆盖不单列**（AddressBook 的 orgType 全集与角色页签已覆盖，见 [前端公共组件.md](../系统模块/前端公共组件.md) §一）；密码**并入单行文本「是否密码」属性**。地图、关联数据、自动编号、富文本、标签页、折叠面板、子表嵌套、自定义 Vue 组件、批量导入 → 二期（§9）。
- **理由**：地址本 orgType 语义（ALL/ORG/DEPT/ORGDEPT/PERSON/POST/PERSONPOST/ORGDEPTPOSTPERSON + showRole 角色页签）完整覆盖人员四组件的选择语义，单列四组件是重复建设；密码本质是输入框的展示属性（掩码），不值得独立组件；布局一期分组（区块标题）+ 栅格（列跨度）已覆盖主流表单排版，标签页/折叠面板属交互增强；自动编号依赖 v1.6 取号通道与幂等语义，随 R05 倾向二期复用 `NumberRuleComposer`/取号接口；自定义组件依赖 `sys_form_component` 注册表（R05 裁减二期）。
- **影响面与下游任务**：F15-FE-002（物料分类骨架按 §1.3 登记）、F15-FE-003/004/007（运行时组件范围）、F15-DOC-004（属性面板逐组件按 §1.3 属性项登记）；与 R05 一致（`sys_form_component` 二期再评估）。

#### R04 明细表嵌套深度：一期一层明细表（定稿）

- **分歧描述**：要点文档第 1/5 步要求「子表、嵌套明细表」；组件文档未明确嵌套深度。
- **候选方案对比**：

| 方案 | 说明 | 评估 |
| --- | --- | --- |
| A. 一期一层明细表（推荐） | 明细表内不得嵌套明细表，嵌套深度上限由 Schema 结构校验器固化 | 一层明细已覆盖采购/报销/领料等主流单据；行上下文（row/rowIndex）与服务端校验复杂度线性可控 |
| B. 一期支持多级嵌套 | 子表嵌套子表 | 行上下文嵌套注入、服务端校验/归一、渲染器递归边界均非线性增长，一期排期与质量风险大 |

- **裁决结论**：**采用方案 A**。一期一层明细表；Schema 结构校验器固化容器嵌套深度上限（§2.2 `MAX_NEST_DEPTH`）并**禁止明细表行内嵌套任何容器组件**；多级嵌套二期放开时仅放宽常量与校验规则，协议结构不变（前向兼容）。
- **理由**：服务端对明细的校验/归一（行结构、行数上限、行内公式逐行重算）在一层模型下是扁平行对象的线性处理；多级嵌套是协议已预留（`children[]` 递归结构天然支持）、仅由校验器封顶的能力，二期放开成本可控，一期先封顶可防止脏 Schema 入库。
- **影响面与下游任务**：F15-FE-007（明细表行内仅数据类字段组件）、F15-BE-003（明细行数据结构归一为扁平行对象数组）、F15-BE-001（校验器常量固化）。

#### R08 级联选择项「公式」执行位置：前端本地条件过滤 + 保存时服务端复核（定稿）

- **分歧描述**：组件文档级联选择器要求「选择项公式（父数据项的公式判断，决定是否显示该选择项，一公式可配置多选择项）」；执行位置未定——逐项调用 F14 `/formula/simulate` 在父项值每次变化 × 每选项一次请求，是请求风暴，不可行；纯前端执行又违反「校验权威在后端」红线。
- **候选方案对比**：

| 方案 | 说明 | 评估 |
| --- | --- | --- |
| A. 逐项调用 simulate | 每选项一次后端求值 | 父项变化触发 N 个选项 × M 次请求，性能与稳定性均不可行，否决 |
| B. 前端本地条件过滤 + 保存时服务端统一复核（推荐） | 本地毫秒级过滤可选集，后端按同一条件语义复核提交值 | 无轮询；前端过滤仅是交互预演，越权提交被后端兜底 |
| C. 纯前端执行完整公式 | 不走后端 | 违反 F14 A1（校验与执行权威在后端）与要点安全红线，否决 |

- **裁决结论**：**采用方案 B，落地口径四条**：
  1. **一期选项显隐条件采用规则 DSL 条件形态**（`{ operator, value }`，作用于父数据项字段值，语义同 §3.2 operator 全集）——组件文档「公式判断」在一期的本地可求值等价形态即条件 DSL；完整内联 AviatorScript 公式形态（FormulaDesigner 配置 BOOLEAN 公式）二期随「批量求值通道」评估（一次请求求值全部选项，仍不走逐项 simulate）。
  2. **前端本地过滤**：运行期监听父数据项值变化，按各选项显隐条件本地求值过滤可选集；父项值清空时清空本字段已选值（级联组件内置联动，不经规则 DSL 配置）。
  3. **保存时服务端统一入口复核**：数据引擎保存时以同一条件求值器（`FormRuleEngine`）复算「父项当前条件下允许的选项集」，提交值必须 ∈ 允许集，否则拒绝（错误语义随 F15-DOC-002 定稿编码）。
  4. **设计期校验**：Schema 结构校验器校验父数据项必须为已配置的数据类字段、显隐条件 operator/value 合法、不可引用自身。
- **理由**：本地条件求值 O(1) 网络请求、交互即时；前后端共用同一 DSL 条件求值语义保证过滤与复核结果一致；后端复核是权威裁决，前端被绕过（直接调接口提交越权选项）也会被拒绝——「前端隐藏/过滤 ≠ 后端放行」在级联场景同样成立。
- **影响面与下游任务**：F15-FE-010（本地过滤 + 配置面板按条件 DSL 编辑）、F15-BE-005（复核入口落 `FormRuleEngine`）、F15-DOC-004（级联配置形态细化）、F15-DOC-002（复核失败错误语义编码）。

## 1. 组件协议定稿

### 1.1 统一组件元数据结构

每个组件物料（material）= 元数据 + 七件套（要点文档第 1 步），结构定稿如下：

```text
组件物料 material = {
  ── 元数据 ──
  type:        string   // 组件类型码，全局唯一（registry 查重键），也是 Schema 字段对象 field.type 的取值域
  name:        string   // 组件名（与 type 同值惯例，要点第 1 步示例形态）
  label:       string   // 物料栏显示名（中文）
  category:    string   // 类别 DATA / CONTENT / LAYOUT / CONTROL（对齐组件文档 数据/内容/控制 + R03 增布局）
  icon:        string   // 物料栏图标
  defaultProps: object  // 属性默认值（固定属性项 + 扩展属性项的初始值）
  ── 七件套 ──
  ① propSchema            // 设计器配置面板描述（属性项 schema，属性面板按其动态渲染）
  ② component             // 运行时 Vue 组件引用（CONTROL 类一期为 null，仅协议位）
  ③ defaultValueGenerator // 默认值生成器 () => value（按数据类型生成）
  ④ dataType              // 数据类型 STRING / NUMBER / BOOLEAN / DATE / ARRAY / OBJECT
  ⑤ validator             // 校验器 (value, props, context) => errors[]（必填/类型/长度/范围/正则接此口径）
  ⑥ serializer            // 序列化方法：组件值 → 提交载荷形态（跨模块值结构在此适配，如地址本/附件）
  ⑦ deserializer          // 反序列化方法：回显数据 → 组件值（serializer 的逆运算）
}
```

- 元数据示例（对齐要点文档第 1 步）：

```json
{
  "type": "input",
  "name": "input",
  "label": "单行文本",
  "category": "DATA",
  "icon": "edit",
  "defaultProps": { "placeholder": "请输入", "maxlength": 200, "required": false }
}
```

- 物料是纯前端概念；后端仅持 **type 白名单**（`SysFormConstants` 常量集 + `SysFormComponentCategory` 枚举），Schema 结构校验器按白名单拒绝未注册 type（ADR-10）。
- 固定属性项（组件文档第 2 条）按组件类别裁剪：

| 类别 | 固定属性项 |
| --- | --- |
| DATA（数据类 12 组件） | 名称 label、ID field（字段码）、是否必填 required、说明文本 tooltip、默认值 defaultValue |
| CONTENT（内容类 4 组件，除明细表） | 名称 label、说明文本 tooltip（不承载数据，无 ID/必填/默认值） |
| LAYOUT（布局类 2 组件） | 名称 label（分组即区块标题）（无 ID/必填/说明/默认值） |
| detailTable（明细表，数据容器特例） | 名称 label、ID field、是否必填（语义 = 至少一行，按 rowMin）、说明文本 tooltip（默认值不适用，行由用户增删） |

### 1.2 前端物料注册协议

对齐要点文档第 3 步注册表形态（任务 F15-FE-002 落地）：

```js
// frontend/src/components/form/registry.js
const componentRegistry = new Map()

/**
 * 注册组件物料；重复 type 注册抛错，物料元数据与七件套完整性断言（缺失即抛错，fail-fast）。
 * 渲染器与设计器只经 registry 取物料，任何组件不直接 import 其他组件的运行时实现。
 */
function registerComponent(material) { /* … */ }
```

- 协议先于实现（要点文档第七节最终建议）：registry 与 FormRenderer 契约先定稿（本文 §1/§4），物料按任务分批注册（F15-FE-003 基础七件 → F15-FE-004 业务四件 → F15-FE-007 内容与明细）。
- 新增组件只需注册物料、不改渲染器与规则引擎（开闭原则）；CONTROL 类（权限组件）一期仅登记元数据协议位，`component` 为 null、物料栏不展示。
- 分类分组：物料栏按 `category` 分组展示（数据/内容/布局/控制），与 §1.3 清单一一对应。

字段对象（要点文档第 2 步示例结构定稿扩展）：

## 3. 规则协议定稿

### 3.1 统一 DSL

四类规则（显隐 show/hide、联动 setValue/clear、动态校验 setRequired 等、自定义响应占位）统一为一套声明式 DSL（要点文档第 4 步结构定稿），**规则随触发字段存放于字段对象 `rules[]`**（§2.1），DSL 内 `triggerField` 显式保留（服务端平铺索引求值）：

```jsonc
{
  "ruleId": "rule_001",             // 表单内唯一
  "event": "onChange",              // §3.4 事件全集
  "triggerField": "payType",        // 触发字段码（= 宿主字段对象 field；明细容器事件为其字段码）
  "condition": {                    // 可省略：无条件规则（事件即触发，如 onAdd 行初始化 setValue）
    "operator": "equal",            // §3.2 operator 全集
    "value": "transfer"             // 比较值（标量或数组，随 operator）
  },
  "actions": [                      // 动作数组，按序执行（§3.3 动作全集）
    { "type": "setRequired", "target": "bankAccount", "value": true },
    { "type": "show", "target": "bankAccount" }
  ]
}
```

- 明细行事件规则：`triggerField` = 明细表字段码，动作 `target` 为行内字段码；执行时注入行上下文（`row` / `rowIndex`），动作作用于当前行（要点第 5 步行内规则原则）。
- 前后端分工：前端规则引擎（F15-FE-006）按 DSL 求值是**交互预演**；服务端（F15-BE-004 的 `FormValidationEngine` / `FormRuleEngine`）按同一 DSL 复算是**权威裁决**（R09 安全面：服务端独立校验不信任前端）。
- 动态校验语义：`props.required`（静态基础必填）与规则 `setRequired`（动态覆盖）在服务端合并为最终校验口径；`setValidate` 覆盖同理（仅覆盖所列项，其余保持字段静态校验器）。

### 3.2 operator 全集（10 个，一期定稿）

| operator | 语义 | value 形态 | 备注 |
| --- | --- | --- | --- |
| equal | 等于 | 标量 | 字符串/数值/布尔精确匹配 |
| notEqual | 不等于 | 标量 | |
| gt / gte / lt / lte | 大于 / ≥ / 小于 / ≤ | 标量 | NUMBER 数值比较；date 按 same-format 字符串字典序比较 |
| in | 属于 | 数组 | 提交值 ∈ value |
| notIn | 不属于 | 数组 | |
| empty | 为空 | 省略 | null / undefined / 空串 / 空数组 |
| notEmpty | 不为空 | 省略 | |

- 结构校验器约束：operator 必须在全集内；in/notIn 的 value 必须为数组；gt/gte/lt/lte 的 value 必须为数值或日期字符串；condition 引用的 triggerField 必须存在且为已配置数据类字段。
- 一期不开放：正则匹配类 operator（`matches`）、跨字段比较（`compare`）——若下游出现诉求随二期扩展，扩展只增 operator 不改 DSL 结构。

### 3.3 动作类型全集（6 个，一期定稿）

| type | 语义 | 载荷 | 备注 |
| --- | --- | --- | --- |
| show | 恢复目标字段渲染可见性 | target | 在 props.hidden 静态态之上切换 |
| hide | 隐藏目标字段（**不删值**，§3.6） | target | 仅渲染可见性，不触发清值 |
| setValue | 给目标字段赋值 | target, value | value 为字面量或 `${字段码}` 引用（联动赋值，如选部门带出负责人场景的字段回填） |
| clearValue | 清空目标字段值 | target | 显式清值动作，与 hide 语义严格分离 |
| setRequired | 动态必填切换 | target, value(boolean) | |
| setValidate | 动态校验覆盖（条件范围/条件正则） | target, validate{ min?, max?, pattern?, message? } | 覆盖语义：仅覆盖所列项，其余保持字段静态校验器；覆盖 F15-BE-004「条件必填/条件范围/条件正则」诉求 |

- 一期不开放 script 类动作（R02）；`setValue` 在 onSubmit 事件上禁止配置（防提交竞态，§3.4）。

### 3.4 事件清单（8 个，一期定稿）

| 事件 | 触发时机 | 一期消费范围 |
| --- | --- | --- |
| onLoad | 表单初始化/回显完成后 | 声明式规则可用（初始化联动） |
| onChange | 字段值变化 | 主力事件（显隐/联动/动态校验） |
| onFocus / onBlur | 字段获得/失去焦点 | 仅事件透传给物料组件，声明式规则一期不开放配置（焦点类联动场景极少，防规则风暴） |
| onAdd | 明细表新增行 | 行初始化动作（如行内默认值）；行上下文注入 |
| onDelete | 明细表删除行 | 行后处理（如合计刷新由统计行内置，无需规则） |
| onSubmit | 表单提交前 | 仅支持 setRequired/setValidate/show/hide；禁止 setValue/clearValue |
| onValidate | 表单校验阶段 | 同 onSubmit 载荷约束；服务端校验链消费（§6.2） |

### 3.5 循环防护口径

事件链（要点文档第六节 2）：`字段值变化 → 事件总线 → 规则匹配 → 动作执行 → 状态更新 → 触发后续规则`。防护三层（常量见 §2.2）：

1. **次数熔断**：单次交互引发的规则风暴内动作执行计数达 `MAX_RULE_EXECUTIONS_PER_CYCLE`（50）即熔断本次风暴：剩余规则跳过、控制台告警、渲染器状态位提示（不阻断已渲染表单）。
2. **深度熔断**：规则链级联深度达 `MAX_RULE_CHAIN_DEPTH`（5）即熔断（A→B→A 互写场景在深度 5 内必被拦截）。
3. **幂等短路**：`setValue` 目标值与当前值相等时不回写、不触发该字段的后续规则链（切断 A→B→A 的最常见的无限振荡形态）。

服务端复算（显隐复算/动态校验/级联复核）受同语义常量约束，超限抛确定性 `CS_FORM_*` 错误（编码随 F15-DOC-002），不允许无限求值。

### 3.6 隐藏字段值保留策略（定稿，ADR-08）

三层口径，前后端一致执行：

| 层 | 口径 | 执行方 |
| --- | --- | --- |
| ① 渲染层 | **隐藏不删值**：show/hide 动作仅切换渲染可见性，hide 不触发 clearValue、不清空模型值；编辑过程中被隐藏字段的值保留，恢复显示即恢复可见（编辑态） | 前端规则引擎（F15-FE-006） |
| ② 持久层 | **提交裁剪**：数据引擎保存时按提交数据 + 版本 Schema 复算显隐规则（`FormRuleEngine` 同一条件求值器），判定为隐藏的字段值**不落库**（从落库 JSON 裁剪）；字段级权限 `permission=hidden` 的字段无论渲染态一律裁剪（后端不信任前端） | 后端数据引擎 + 裁剪引擎（F15-BE-003/004） |
| ③ 读取层 | **服务端裁剪**：回显/详情响应按存量数据复算同一口径——提交时刻被裁剪的字段不下发；`permission=hidden` 字段不下发 | 后端裁剪引擎（F15-BE-004） |

- **理由**：(a) 编辑体验——隐藏删值会让「改条件回来」必须重填，且与动态必填规则互相干扰；误触显隐不应丢值。(b) 数据卫生——落库数据与「提交时刻的可见形态」一致，详情页不会翻出「提交时不可见」的僵尸值，编辑回显与详情回显自然一致（跨会话隐藏字段的旧值不再存在，属本策略的接受行为）。(c) 安全面——要点第 7 步红线「前端隐藏字段不等于后端禁止访问」：隐藏判定权威在后端，前端显隐只是预演；越权提交的隐藏字段值会被持久层裁剪。(d) 确定性——同一版本 Schema + 同一份数据，前后端共用同一 DSL 条件求值语义，结果一致。
- **一期边界**：服务端显隐复算裁剪作用于**主表（顶层）字段**的显隐规则与 `permission=hidden` 字段；**明细行内显隐一期为渲染层语义**（行数据按行原样落库，行内必填/类型/枚举校验服务端仍执行），行级裁剪随二期评估。
- 需要清值的业务场景必须显式配置 `clearValue` 动作（语义严格分离，不借 hide 隐式清值）。

### 3.7 代码块组件协议占位（R02：一期不执行）

一期仅固化协议、不落地执行引擎（裁决见 §0.3 R02）；以下为二期落地时的协议契约（要点文档第三节登记）：

- 组件协议位：type=`code`（category=CONTROL），一期不注册物料、物料栏不展示、结构校验器拒绝其出现在 Schema 中。
- 事件清单：onLoad / onChange / onFocus / onBlur / onAdd / onDelete / onSubmit / onValidate（§3.4 全集复用）。
- 统一上下文：`{ formData, field, value, oldValue, row, rowIndex, api, utils }`；`api` 仅暴露权限白名单内的业务接口。
- 二期落地红线（要点文档安全建议五条全数采纳）：不使用 `eval`；使用 QuickJS/GraalJS 等隔离执行环境或受限表达式解释器；限制执行时间、内存、可访问对象；不允许直接访问 JVM/数据库连接/OS；后端独立执行关键业务校验、不信任前端 JS 返回结果；业务接口走权限白名单。
- 普通规则与代码块分离原则维持：80% 常见业务走声明式 DSL（§3.1），复杂业务二期走代码块。

## 4. 渲染器契约

### 4.1 组件与三形态

`frontend/src/components/form/FormRenderer.vue`，三形态复用同一渲染器（要点第 3 步原则：设计器预览、填写页、BPM 审批页共用；BPM 审批页归 v1.8）：

| mode | 形态 | 语义 |
| --- | --- | --- |
| `design` | 配置（设计器画布） | 设计器画布内部复用渲染器：渲染物料占位态（选中/拖拽插入/属性面板联动），数据绑定旁路（无真实数据读写） |
| `edit` | 编辑（填写） | 完整数据绑定 + 默认值初始化 + 规则引擎挂载 + 校验 |
| `detail` | 详情（只读） | 全部字段只读回显；显隐规则照常求值（与提交时刻形态一致）；动态校验不执行 |

### 4.2 props、v-model 与事件

| 项 | 契约 |
| --- | --- |
| props.schema | 版本 Schema 对象（§2.1）；渲染器只解释 Schema、不感知表单元数据接口 |
| props.mode | `design` / `edit` / `detail`（默认 edit） |
| props.modelValue | 表单数据对象（v-model）：渲染器为受控组件，字段值变更经 `update:modelValue` 回传全量数据对象，宿主持值提交 |
| props.fieldPermissions | 字段级权限外部覆盖映射 `{ 字段码: editable/readonly/hidden }`，默认 null；v1.8 BPM 节点权限注入位（一期设计器预览可传）；与 Schema 内 `props.permission` 合并时外部覆盖优先 |
| emits.update:modelValue | 任意字段值变化回传全量数据对象 |
| emits.change | 单字段明细载荷 `{ field, value, oldValue }`（宿主按需监听） |
| expose.validate() | 全量校验（基础校验 + 规则动态校验合并），返回 `{ pass, errors: [{ field, ruleId, message }] }`；提交由宿主页面发起，渲染器不发请求 |
| expose.reset() | 重置：清空后按物料 defaultValueGenerator 重新生成默认值（而非回快照） |
| expose.getData() | 取当前数据对象 |

### 4.3 渲染行为定稿

- **组件加载**：`<component :is="componentRegistry.get(field.type).component">`，props 透传 `field.props`，v-model 绑定 `modelValue[field.field]`；容器组件（group/grid/detailTable）递归渲染 `children`（递归深度受 Schema 校验器前置保证）。
- **默认值初始化**：挂载时对未赋值字段执行物料 `defaultValueGenerator`；编辑回显时以回显数据优先、缺失字段补默认值。
- **事件统一分发**：渲染器内置事件总线（onLoad/onChange/onFocus/onBlur/onAdd/onDelete/onSubmit/onValidate），规则引擎（F15-FE-006）订阅同一事件流完成规则匹配与动作执行；字段组件只 emit 原始事件，不感知规则（架构原则 2：规则不写死在任何字段组件内）。
- **字段级权限渲染**：`permission=readonly`（或外部覆盖 readonly）→ 组件置灰只读；`permission=hidden` → 不渲染、值不进入提交载荷（静态可知，前端一致裁剪，后端兜底裁剪，见 §3.6）。规则动态显隐字段则相反：渲染层隐藏**不删值**、提交原样携带由服务端裁决（§3.6 两类隐藏的行为差异即在此）。
- **未知 type 兜底**（ADR-10）：registry 未注册的 type 渲染「组件未注册」占位块（type 文案 + 告警样式），不抛异常、不阻断整表渲染；保存期结构校验器已拒绝未注册 type，此为库内 Schema 的最后防线。
- **渲染器零业务规则**：渲染器不写任何具体业务规则，显隐/联动/校验全部交规则引擎（F15-FE-006 验收红线）。

## 5. 版本机制与定义面业务规则

### 5.1 不可变版本五原则（要点第 8 步逐条落地）

| # | 原则 | 落地语义 |
| --- | --- | --- |
| 1 | 每次发布产生一个新版本 | 发布动作将草稿 Schema 冻结为版本行：版本号单调递增分配、`published_at` 回填；版本行发布后内容不可变 |
| 2 | 已创建的实例继续使用原版本 | `sys_form_data.field_form_version_id` 锁定实例版本；load/validate/再编辑一律按实例版本 Schema 求值，不随主档当前版本漂移 |
| 3 | 新创建的实例使用最新发布版本 | 提交入口取 `sys_form.field_current_version_id` 指向的版本 |
| 4 | 不允许直接修改已发布的历史版本 | 更新仅作用于草稿态版本行；PUBLISHED / DEPRECATED 行拒绝任何内容更新与状态回退（ADR-06 快照原子性） |
| 5 | 回滚 = 重发布历史版本副本 | 回滚动作复制目标历史版本内容产生**新版本行**（版本号新增、内容与目标版本一致、`published_at` 为回滚时刻、不经草稿态一步发布）；不产生「指针回拨」 |

### 5.2 状态机

```text
表单主档 sys_form
  field_status：DRAFT（从未发布）──首次发布──▶ PUBLISHED（存在当前发布版本）
  启停用走 field_enable（独立字段，updateEnable 只更新自身，先例 org）：停用后填写入口与数据提交关闭，定义面与数据查询保留

版本行 sys_form_version
  DRAFT ──发布──▶ PUBLISHED ──被新版本替代──▶ DEPRECATED
    ▲                                        │
    └── 再编辑 = 复制当前发布版本内容为新草稿行 ─┘（DEPRECATED 不可逆）

非法流转拒绝（确定性 CS_FORM_* 错误，编码随 F15-DOC-002）：
  · PUBLISHED → DRAFT（发布不可撤销，修正走「再编辑 → 新版本」）
  · DEPRECATED → PUBLISHED（恢复走「回滚 = 重发布副本」）
  · 终态行（PUBLISHED/DEPRECATED）内容更新
  · 无草稿行时直接发布 / 草稿 Schema 结构校验不通过时发布
```

- 版本号语义：`field_version` 为整数单调序号（1, 2, 3…）；要点文档版本树「V1.0 / V1.1 / V2.0」为展示层示意，落库取整数序号。
- 草稿模型：任意时刻每表单至多一行 DRAFT 版本行；新建/再编辑动作从「当前发布版本副本」或「空白」初始化草稿行；发布 = 草稿行原地冻结（版本号回填、状态 PUBLISHED、`published_at` 回填、主档 `field_current_version_id` 切换、原当前版本自动转 DEPRECATED），事务内完成。草稿行的列承载形态（同表 draft/published 行）随 F15-DOC-003 定稿。

### 5.3 发布快照内容

- **快照即 `field_schema_json` 单列**（ADR-06）：完整承载 `{ formId, formCode, formName, version, fields[] }`——组件树（含容器 `children[]`）、组件属性、字段级权限元数据（`props.permission`）、规则（字段对象 `rules[]`）全部内嵌。要点文档第 10 步草案的 `rules_json` 独立列**不采纳**：规则与字段树同源同快照，分离存储必然出现「规则与结构版本错位」，违背不可变版本原则。
- 发布校验链（全部通过方可发布，任一失败确定性拒绝）：Schema 结构校验（字段码唯一/合法、type 白名单、容器与明细嵌套规则、资源上限 §2.2）→ 公式静态校验（服务内调用 F14 校验服务：表达式合法、引用字段存在、依赖图无环）→ 级联条件校验（R08 第 4 条）→ 规则校验（operator/动作/事件合法、target 存在、规则数上限）。
- **发布快照不可变**：发布后该行内容永不更新；「修改表单」语义 = 复制当前版本为新草稿 → 编辑草稿 → 再发布产生新版本。

### 5.4 `field_current_version_id` 语义

- 始终指向**最新发布的版本行**；表单从未发布时为空（主档 DRAFT）。
- 回滚后指向回滚产生的新版本行（原则 5）；新版本发布后指向新版本行。
- 主档 `field_enable=false`（停用）**不改变**该语义——停用关闭的是填写入口，不抹掉当前版本。
- 数据面提交入口（无显式版本指定时）取该字段锁定版本；显式携带版本的提交（v1.8 BPM 按流程绑定版本提交）以显式值为准。

## 6. 数据引擎与集成口径

### 6.1 数据与定义分离存储（原则 3，ADR-07）

- **定义面**（`sys_form` / `sys_form_version`）：结构与规则；**数据面**（`sys_form_data`）：实例 JSON + 归属 + 关联。数据引擎不承载任何具体业务逻辑（要点第六节 3：采购申请表的数据归采购业务模块处理，表单引擎只收集与管理数据）。
- `field_form_data` JSON 结构与版本 Schema `fields[].field` 同构（白名单归一后）：`{ 字段码: 值, …, 明细表字段码: [扁平行对象数组] }`（§2.3 示例）。
- 保存校验链（按序执行，全部服务端权威）：①按 `field_form_version_id` 锁定版本 Schema；②未知字段校验（按版本 Schema 字段白名单比对，处置策略已由 F15-DOC-002 定稿为**拒绝**并返回 `CS_FORM_UNKNOWN_FIELD`，不做静默裁剪，见 API 分册 §7.4）；③基础校验（必填/类型/长度/枚举选项值/明细行结构与行数上限）；④显隐复算与提交裁剪（§3.6 持久层）；⑤动态校验（规则 setRequired/setValidate 与静态校验合并，errors 数组含 fieldCode/规则 ID/文案）；⑥级联选项复核（R08）；⑦公式重算（§6.3）；⑧权限裁剪（permission=readonly 编辑提交值变更拒绝；hidden 一律裁剪）。
- 结构化业务数据映射层与报表统计：不排期（要点第 6 步——后续按需增加映射层，不一开始为动态表单建独立业务表，§9）。

### 6.2 business_id 绑定

- `field_business_id`（草案列名）为提交方传入的**弱关联外键**（外部业务对象 id，如 v1.8 流程实例或业务单据），参与查询条件过滤；`field_process_instance_id` 为 v1.8 预留列（一期不写入）。
- 一期保存**不做** business_id 唯一性约束（同一 business_id 下同表单是否允许多条数据由业务侧定，v1.8 BPM 适配层细化）；list 查询支持 formId/businessId/processInstanceId/时间筛选 + 创建人归属过滤 + 分页（总数经 `metadata.total`）。
- 数据归属口径（R06 倾向，终稿随 F15-DOC-005）：登录即可提交/查询本人数据（按创建人 `field_creator_id` 判定，先例日程归属判定），`SYS_FORM_ADMIN` 可查询全部；三种拒绝语义（未登录/无权限/非本人非管理员）由 resolver + Service 双层保证。

### 6.3 公式字段服务端重算（F14 集成，ADR-09）

- **提取**：保存时从版本 Schema 提取 type=formula 字段（主表 + 明细行内）。
- **依赖图**：对每个公式表达式静态解析变量依赖（`${code}` 根码与 `${list.field}` 根码提取；服务内调用 F14 校验服务，不经 HTTP），构建字段码有向图并拓扑排序；设计期发布校验已拒绝循环依赖，运行期拓扑深度上限兜底。
- **执行**：复用 `com.eric.base.sys.formula.service.engine.FormulaEngine#execute(expression, FormulaContext, SysFormulaReturnType)`（服务内调用，不经 HTTP）：
  - **主表公式**：上下文变量 = 主表字段值映射（字段码 → `${code}`）+ 明细表数组变量（支持 `${list.field}` 两级路径投影，如 `SUM(${purchaseDetails.amount})` 走 COLLECTION 函数合计）+ 服务端注入系统变量（`UserUtil`，F14 语义）；
  - **明细行内公式**：逐行执行，行上下文 `row` 注入——变量表 = 当前行字段值（行内字段码直接 `${code}` 引用，如 `ROUND(${quantity} * ${price}, 2)`）+ 主表字段值；每行一次求值。
- **失败处置**：公式执行失败复用 F14 `CS_FORMULA_*` 语义映射为确定性错误（不裸异常穿透），**阻断保存**（公式字段值是数据的一部分，不允许带空落库）。
- **前后端值不一致处置策略（定稿）**：**保存时以服务端重算结果为准落库；前端展示值仅预览性质，差额不报错**。理由：(a) 前端没有 AviatorScript，无法复算含 COLLECTION/IF/DS_QUERY 等函数的公式——前端值本就是估算展示（行内四则可本地预演，主表合计等无法保证）；(b) 要点安全红线：后端不信任前端计算结果；(c) 报错策略会制造「明明按公式算对了却提交失败」的伪故障（精度与四舍五入口径的毫厘差异即触发）；(d) 回显以落库值为准，前后端展示自然收敛。提交载荷中公式字段值不参与校验；保存成功后宿主以回显数据（或保存响应携带的最终数据）刷新展示。
- 沙箱与资源限制随 `FormulaEngine` 既有语义，本模块不重复造沙箱（F15-BE-005 口径）。

### 6.4 级联选择项公式执行位置（R08 落地）

- 落地口径四条见 §0.3 R08：一期选项显隐条件为 DSL 条件形态、前端本地过滤、保存时 `FormRuleEngine` 服务端复核（提交值 ∈ 父项当前条件允许选项集）、设计期结构校验。
- 组件内置行为：父项值清空时清空本字段已选值（不经规则 DSL 配置）；级联值变化照常进入事件总线触发后续规则。
- 完整内联公式形态（FormulaDesigner BOOLEAN 公式）二期随「批量求值通道」评估（§0.3 R08 第 1 条），一期结构校验器不接受。
