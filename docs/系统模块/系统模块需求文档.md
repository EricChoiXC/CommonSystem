# 1. 组织架构模块

## 1.1 表

```
组织架构表 sys_org_element
    L 机构表 sys_org_org （一对一）
    L 部门表 sys_org_dept（一对一）
    L 人员表 sys_org_user（一对一）
    L 岗位表 sys_org_post（一对一）
        L 岗位人员表 sys_org_post_user （人员表、岗位表多对多）
权限表 sys_org_auth
角色表 sys_org_role （另在 sys_org_element 维护 field_org_type = 5 镜像行，不参与组织架构树）
    L 角色分配 sys_org_role_element （角色表、组织架构表多对多）
    L 角色权限 sys_org_role_auth （角色表、权限表多对多）
群组表 sys_org_group （与 sys_org_element 一对一，field_org_type = 6 镜像行，不参与组织架构树）
    L 群组成员 sys_org_group_user （群组表、人员表多对多）
    L 群组可见范围 sys_org_group_viewer （群组表、组织架构表多对多，仅公共群组）
```

> v1.1 同步：表名以 `V1_01_001__sys_org_schema.sql` 为准（人员表 `sys_org_user`、岗位人员表 `sys_org_post_user`，

> 角色/群组镜像行不参与组织架构树，存量角色镜像行不迁移（仅写路径增量维护）。

组织架构、机构、部门、人员、岗位查询：不设权

组织架构、机构、部门、人员、岗位完整信息读取：人员本人 OR 组织架构管理员 OR 对应表的维护者

组织架构、机构、部门、人员、岗位的新建、编辑、启停用：组织架构管理员 OR 对应表的维护者

人员编辑：本人 OR 组织架构管理员 OR 人员维护者

个人资料（本人自助）维护：登录用户本人（登录且账号启用即可，不设权限码；接口不收 userId 参数，操作对象由会话定位，仅可读写本人数据）

角色查询：不设权

角色权限查询：普通用户可查询自己被分配的角色；角色维护者可查询所有

角色分配查询：普通用户可查询自己被分配的角色；角色维护这可查询所有

群组维护：个人群组由本人维护；公共群组由群组管理员维护（管理员可维护全部公共群组与自己的个人群组，他人的个人群组不可维护；公共群组可见范围为空表示全员可见，可见范围限机构/部门/岗位/人员）

## 1.3 业务

[组织架构、机构、部门、人员、岗位] + [查询、普通信息读取、完整信息读取、新建、编辑、启停用] 以上互相组合

人员所属组织架构读取：提供传入用户id的接口，返回和当前用户关联的所有机构、部门、岗位、人员、角色。

角色新建、编辑、删除：后台提供维护页面，有角色维护者进行维护

地址本：结合查询、基本信息读取接口，提供前端页面的进行组织架构选择的弹窗，弹窗内可通过组织架构树和岗位列表，选择对应的组织架构目标；v1.1 起弹窗支持「角色」页签（showRole，复用关键字列表查询按角色类型分页）与「群组」页签（可选类型含人员时自动显示，左侧可见群组列表、右侧群组成员人员表格，按群组批量选择人员）

个人资料页：登录用户经顶栏用户区下拉【个人信息】进入本人自助资料页（/profile，登录且账号启用即可，不设权限码）。可维护用户名、手机、邮箱、联系地址、性别、生日——用户名可编辑，保存时同步组织架构树节点名称（sys_org_element.field_name）并重算拼音两列，组织架构树与拼音检索即时反映新名；登录名只读（账号唯一标识，仅管理员在组织架构人员维护中修改）；头像与顶栏用户区一致，经附件公共通道维护（绑定 `modelName=sys_org_user` + `modelId=用户ID` + `key=profile`，单张语义：上传新头像成功后删除旧头像附件，未上传时回退用户名首字符显示）。

第三方账号绑定：个人资料页关联账号区支持微信 / QQ 账号绑定，仅限对已存在账号绑定（不支持第三方注册）；openid 全局唯一，相同 openid 不允许重复绑定；总开关 `openid_bind_enable`（common_setting 配置，bool）默认关闭——关闭时前端入口整卡提示、后端绑定接口拒绝，管理员经系统设置页开启，渠道应用凭证由部署配置；解绑不影响登录能力（本系统不支持第三方登录），解绑后该 openid 可被他人绑定。

顶栏登出入口：独立【登出】按钮移除，退出登录经顶栏用户区下拉【退出登录】（与既有登出链路等价：清空会话与标签页记录）。

| SYS_PROCESS_TEMPLATE_EDITOR | 流程模板维护者 | 拥有流程模板配置和启停用权限 |

### 3.2.2 业务权限

流程模板查询：不设权

流程模板完整信息读取、新建、编辑、启停用：流程管理员 OR 流程模板维护者

流程实例查询、读取：不设权

流程发起：业务单据提交审批时，由业务模块传入单据ID、单据标题、发起人、所属组织等信息创建流程实例；流程模块只负责流程流转，不负责替代业务模块做单据鉴权

流程查询、读取：不设权，但普通用户仅对与自己有关的流程有查询、读取权限；“与自己有关”包括本人发起、本人当前待审批、本人已审批、本人被抄送等场景

流程审批：普通用户仅对自己当前审批的流程有审批权限；审批时必须记录审批结论、审批意见、审批时间，并写入流程审批记录

流程撤回：对自己已提交审批的，且流程配置可收回的流程，提交人可发起收回；收回后流程实例回退到提交前状态，并同步结束当前审批待办

特权审批：后台提供所有流程的查询页面，仅流程管理员可访问；流程管理员在该页面可进行特权审批处理

待办联动：流程到达审批节点时，自动向当前审批人生成待办；审批通过、驳回、撤回后，自动将对应待办转为已处理，并保留流转记录供后续查询

编号规则查询：不设权

编号规则完整信息读取、新建、编辑、启停用：编号管理员 OR 编号规则维护者

编号生成：业务模块在新增单据、草稿转正式、提交流程等需要落正式编号的场景调用编号模块；编号一经正式生成后，不允许由普通业务用户手工改写

编号唯一性：同一规则在同一重置周期内生成的编号必须唯一；若流水号已用尽、规则未启用或规则配置不完整，则本次业务保存/提交失败，并返回明确错误信息

组织适配：编号规则可按单据类型、组织范围等条件匹配；未匹配到规则时，不得回退到前端本地生成，必须由后台返回失败结果

审计联动：编号规则的新建、编辑、启停用、重置、补号等维护操作，需记录操作人和操作时间，供后续审计模块查询

## 5.1 表

## 5.2 权限

### 5.2.1 权限

| 权限名              | 中文名       | 说明                           |
| ------------------- | ------------ | ------------------------------ |
| SYS_NOTIFY_ADMIN    | 待办管理员   | 拥有待办模块所有监管查看权限   |
| SYS_NOTIFY_MONITOR  | 待办监管者   | 拥有待办监管查询和明细查看权限 |

### 5.2.2 业务权限

我的待办、我的已办、我的通知、我的关注查询：不设权

我的待办、我的已办、我的通知、我的关注读取：仅本人

待办处理：由源业务模块或流程模块决定；用户仅可处理分配给自己的待办

待办标记已读、关注、取消关注：仅本人

监管查询、监管读取：待办管理员 OR 待办监管者

监管操作：不开放；监管页面仅查看，不可代办、不可改状态、不可删除

## 5.3 业务

待办生成：各业务模块、流程模块在需要用户处理或需要用户知晓时，统一创建待办记录，并写入来源模块、来源单据ID、标题、待办类型、接收人、处理链接、创建时间等信息

我的待办：普通用户可查看分配给自己的未处理待办，并进入来源单据页面处理业务；待办是否可点击处理、是否可审批、是否可编辑，由来源业务模块最终鉴权

我的已办：用户完成处理后，待办自动从“未处理人”转入“已处理人”；已办保留处理结果、处理时间，用于个人追溯

我的通知：仅需知晓无需办理的消息写入通知接收人；用户可查看和标记已读，但不进入待办处理链路

我的关注：用户可对待办或通知进行关注，便于后续持续跟踪；关注仅影响个人视图，不改变业务处理权限

流程联动：流程审批到达节点时自动生成审批待办；审批通过、驳回、撤回后自动完成对应待办；流程中的抄送消息进入“我的通知”而非“我的待办”

监管查看：后台提供待办监管列表页面，仅待办管理员和待办监管者可访问；监管视图可按模块、单据、人员、状态、时间范围查询，但仅可查看，不可直接代替业务用户执行处理

# 8. 任务模块

## 8.1 表

| 权限名         | 中文名         | 说明 |

## 8.3 业务

项目创建 @task 类注解， ITask 接口类 和 SysTaskMain 实体类；

注解以任务表的主要字段作为填写参数；

````java
private SysTaskMain execute();
````

仅 '定时任务管理员' 可访问后台定时任务页面：

每次执行定时任务，先创建 sys_task_example 实例，通过实现类调用 execute 方法，再根据 SysTaskMain 创建 sys_task_execution_record 记录，并删除 sys_task_example 实例；任务发生异常时需保证 sys_task_example 能被清除，且 sys_task_execution_record 能被记录；

| SYS_I18N_ADMIN | 多语言管理员 | 多语言管理页面与全部维护接口     |

免鉴权：语言列表读取（登录页语言下拉使用）、前端语言包 `/locales/{code}.json`

登录即可：模块聚合列表、当前用户语言更新

## 9.3 业务

语言管理：多语言管理员维护语言清单（新增、编辑、启停用、删除、设默认）；系统初始化时保证 zh_CN（默认）与 en_US 两条语言；默认语言禁止删除与停用；删除语言时级联删除该语言全部翻译，已选该语言的用户语言登记改绑当前默认语言（不删行）

资源与翻译：资源 key 仅随 `resources/i18n/**` 资源文件扫描产生，不提供人工新增/删除入口；翻译按「模块 × 资源 key × 语言」矩阵维护，支持人工编辑、Excel 导入导出与重置

启动同步与部署（同规则，覆盖四分支）：

- 翻译缺失 → 新增
- 翻译为资源文件导入（人工编辑标记为空）→ 资源值覆盖
- 人工已编辑（标记非空）→ 跳过不覆盖
- 该语言无对应资源文件（或文件中无此 key）→ 删除人工编辑标记为空的记录

部署：管理员手动触发与启动同规则的「资源 → DB 同步」并刷新缓存；前端语言包经动态接口 `/locales/{code}.json` 输出启用语言的全量翻译，未启用或未知语言码返回错误

用户语言：登录请求可选携带语言码，登录成功后登记用户语言（存在更新、不存在插入；无效语言码忽略并回退默认语言，不报错）；登录后可更新个人语言；顶部栏切换仅改变当前页面语言，不落库

异常处理：重复语言码返回参数错误；默认语言删除/停用被拒；Excel 导入中未登记的资源 key、无效语言码列一律跳过且不插入资源项

# 10. 模块组开关模块

> v1.1 新增（接口开关机制）：按「模块组」粒度对一组接口做运行期整体启停，管理员不改代码、不重启即可关闭/恢复一个模块组；设计依据 [接口开关机制设计方案-修订稿](../v1_1-common/05-增加接口开关/接口开关机制设计方案-修订稿.md) 及其四份设计分册。

## 10.1 表

```
模块组状态表 common_module_group （配置型表，V1_01_043__common_module_group_schema.sql 建表；
    field_key 全局唯一 uk_module_key；无创建人/创建时间/更新人，field_update_time 由数据库 ON UPDATE 维护）
```

## 10.2 权限

| 权限名           | 中文名       | 说明                                   |
| ---------------- | ------------ | -------------------------------------- |
| SYS_MODULE_ADMIN | 模块组管理员 | 维护模块组开关状态（系统管理-模块管理） |

模块组列表读取：登录即可，无角色要求——模块组列表暴露系统拓扑，定为登录即可、免登录不可访问

模块组启停：模块组管理员；系统管理员（SYS_ADMIN）经 BaseResolver 自动放行，但**不穿透模块开关**（关闭模块组下系统管理员同样被拦）

## 10.3 业务

开关语义：接口开关的单位是「模块组」，key 为全局唯一命名空间、统一 kebab-case（如 `calendar`、`org-group`）；归属声明为 Controller 类或方法上的 `@ModuleGroup(moduleGroupKey = "...")` 注解（方法级覆盖类级），**无注解 = 不受开关控制（放行）**——登录、`/init`、`/initID`、`setting/load`、SSE 订阅、swagger 等公共入口均不打注解，不受开关影响。开关判定位于业务鉴权之前（`ModuleGroupInterceptor` 先于 Controller `authorize`），属「功能门禁」（模块能不能用），与「谁能用」的 `ACTION_* + resolver` 鉴权正交。

行为语义总表：

| # | 场景 | 行为 |
| --- | --- | --- |
| 1 | 请求命中无注解的 Controller | 放行，进入既有鉴权链路 |
| 2 | 已登录 + 命中开启模块组的注解 | 放行，进入既有鉴权链路 |
| 3 | 已登录 + 命中关闭模块组的注解 | 返回 `MODULE_DISABLED`（"该模块未开启"），不进入 Controller 与 resolver |
| 4 | 未登录 + 命中关闭模块组的注解 | 放行给后续最终鉴权，返回 `UNAUTHORIZED`（匿名策略 D2：不向匿名暴露模块开关状态） |
| 5 | 注解 key 在 `common_module_group` 中不存在 | 启动期校验告警（WARN）；运行期按「开启」放行（fail-open），不因误配置扩大故障面 |
| 6 | 模块组从 yml 中移除 | 库中记录保留（关闭历史可追溯），不做自动清理（D3） |
| 7 | Redis 不可用 | 进程内缓存 + TTL 兜底（默认 30 秒），开关功能不受影响（D1） |

纳入原则与首批清单：面向最终用户的功能模块才可纳入开关范围；登录认证、组织架构主干、权限、字典、日志、公共配置、定时任务、i18n 等基础设施与系统管理类模块**不纳入**（关闭它们会破坏系统自举能力）。首批仅以下模块组（D5：`third-party` 仅设计占位，不建 yml、不标注 Controller）：

| 模块组 key | 名称 | 覆盖范围（Controller） | 说明 |
| --- | --- | --- | --- |
| `calendar` | 日程 | `SysCalendarMainController`（sys/calendar 全部接口） | 现有模块，作为机制验证 |
| `org-group` | 组织架构-群组 | `SysOrgGroupController` | v1.1 群组功能的灰度入口 |
| `third-party` | 第三方 | （预留，暂无 Controller） | 设计占位，第三方账号接入模块落地时启用 |

后续追加模块组只需「moduleGroup.yml 加条目 + Controller 加注解」，机制本身无需改动。

模块组数据来源与幂等同步：各模块在 `resources/properties/{common|sys}/{模块}/moduleGroup.yml` 的 `module-group` 段声明（`name`/`remark` 必填，缺失时同步任务告警并跳过该条目）；启动同步作为第 10 个启动任务追加到 `SysStartupTask#run`（不另建 ApplicationRunner），幂等三边界：

1. 不存在 → 插入，`field_enable` 默认开启；
2. 已存在 → 只回写元信息（`name`/`remark` 变更时更新），`field_enable` **一律不动**——否则管理员关闭后重启即被 yml 重置，机制失效；
3. yml 中移除 → 库中记录保留，不删除、不改状态、不加下线标记，可人工清理。

状态缓存与多实例一致性：进程内 TTL 缓存为主（默认 30 秒，常量定义于 `CommonModuleProperties`）；切换成功后更新 DB → 本实例立即刷新缓存 → 尝试 Redis pub/sub 广播失效通知其他实例（best-effort，失败仅记日志、依赖 TTL 收敛）；DB 异常时有缓存沿用缓存、无缓存放行并告警（fail-open），不在 DB 故障时放大为全站拒绝。

异常处理：

- 模块关闭（`MODULE_DISABLED`）：已登录请求命中已关闭模块组的注解时，拦截器抛 `ModuleDisabledException`，返回 `BaseResponse.failure("MODULE_DISABLED", "该模块未开启，请联系管理员")`（HTTP 200 + code 体系，全工程惯例）；请求**不进入** Controller 与 resolver；
- 匿名请求策略（D2）：未登录请求命中关闭模块组的注解时**放行给最终鉴权**，返回 `UNAUTHORIZED`（登录已过期，请重新登录）；不返回 `MODULE_DISABLED`，避免向匿名暴露模块开关状态；
- fail-open 语义：注解 key 未登记（启动期 WARN、运行期放行）、DB 异常且缓存不可用（放行并告警）、DB 异常但有缓存（沿用缓存并告警）、前端 store 模块状态缺失（菜单不过滤、页面不拦空态）——一律按「开启」放行，不放大故障面。

用户侧感知：模块关闭后前端菜单隐藏（菜单按「权限 auth + 模块可用性」双重过滤）、目标页面渲染「模块未开启」空态（不重定向首页）；模块恢复开启后自动恢复可见（页面与交互详见 [系统模块UI设计文档](系统模块UI设计文档.md) 4.9 节）。
