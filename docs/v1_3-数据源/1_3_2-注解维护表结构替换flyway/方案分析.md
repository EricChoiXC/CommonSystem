## 1. 总体结论

1. **方向有价值**：针对「版本号冲突、脚本过多」两个痛点，注解化表结构维护确有收益，且与本工程「作为其他项目功能基底」的定位吻合。
2. **当前文档不充分**：改造说明只给出了 7 个注解的属性草案，未覆盖同步语义、存量接驳、生产门禁、并发控制、审计追溯等决定方案成立与否的硬问题。
3. **与已落地事实重叠**：方案中 `@DataSourceField` 与已实现的 `@DatasourceField`（A8）几乎逐属性重复（label/type/ops/literalAllowed/sortable/order），应直接复用，不另起炉灶。
4. **流程要求**：按仓库开发顺序（需求 → UI → API → 数据库 → 代码与迁移脚本），本改造属框架级能力，须先补设计文档并评审，不得以当前草图直接进入实现。

## 2. 痛点核实（与仓库事实对照）

| 痛点 | 核实结果 | 注解方案是否解决 |
| --- | --- | --- |
| 版本号冲突 | 真实存在。ERP 合并部署共享序号空间，`docs/v1_3-数据源/数据源开发任务清单.md` R03 已登记「V1_01_046 须确认不与 ERP 侧序号冲突」；`db/migration/` 目录存在 ERP 侧脚本导致的缺号 | ✅ 消灭版本号概念，真正解决 |
| 脚本过多 | 真实存在。现存 20+ 迁移脚本，每改一次字段即新增一个脚本；且刚发生 DEF-1 事故——迁移脚本注释中 `${CURRENT_USER_ID}` 触发 Flyway 占位符解析失败，已在 `application.properties:24` 落地 `spring.flyway.placeholder-replacement=false` 规避 | ✅ 改字段不再产生新脚本 |
| 作为其他项目基底 | 双刃。对新部署的衍生项目，注解直出 DDL 更方便；但 ERP 合并部署契约目前写在 `docs/迁移说明.md`（ERP 侧执行自己的脚本，如 V1_01_020），改方案等于变更跨工程交付契约 | ⚠️ 须重新定义合并部署边界，否则「基底」接入成本反而上升 |

## 3. 注解设计本身的问题

| # | 问题 | 依据 | 建议 |
| --- | --- | --- | --- |
| 1 | 字符串魔法值过多：`fieldType`/`type`/`indexType`/`linkType` 均为 `String` | A8 扫描器先例是运行期 fail-fast（`SysDatasourceFieldScanner`），但拼写错误只能启动期暴露 | DDL 层改用枚举（`FieldType`、`IndexType` 等），编译期拦截 |
| 2 | `ColumnField.sourceName()` 注释写「中文名，数据源名」，一个属性两种语义 | 改造说明 §字段注解 | 拆分为 `comment`（列 COMMENT，数据库设计文档同步依赖它）与独立的数据源归属表达；现有脚本大量使用 COMMENT（如 `V1_01_046`） |
| 3 | `defaultValue() default ""` 歧义：无法区分「无默认值」与「默认空串」 | 改造说明 §字段注解 | 增加哨兵值或 `hasDefault` 开关 |
| 4 | `ObjectField.PkKey()` 属性名违反 Java 命名（大写开头），语义错位（注释为「是否创建外键」）；且与全工程「不建物理外键」惯例冲突 | `V1_01_046__sys_datasource_schema.sql:10` 明文「关联由应用层保证，不建物理外键（全工程惯例）」 | 见第 4 节裁剪建议：整体砍掉 |
| 5 | `@ListObjectField` 未定义中间表自身 DDL 归属（独立 `@TableSource` 类还是隐式生成） | 改造说明 §字段注解 | 同上，随联表能力一并裁剪 |
| 6 | 类型集不够：`STRING/NUMBER/DATE/DATETIME` 覆盖不了既有事实——`sys_datasource.field_conditions`/`field_fields` 是 JSON 列、`field_enable` 是 BIT(1)、`@Index` 无唯一键表达（先例 `uk_datasource_code`） | `V1_01_046__sys_datasource_schema.sql:20-30` | 类型枚举补 JSON/BIT 等；`@Index` 增 `unique` 属性 |
| 7 | 公共字段规则未定义：BaseModel/MainModel 的 `field_creator_id` 等公共列如何进 DDL | A8 已有「fieldId 内建补齐固定最前」先例（`SysDatasourceFieldScanner.java:89`） | DDL 引擎定义对应的公共列内建模板，文档须写明 |
| 8 | 命名冲突：仓库中「数据源」已被 `sys_datasource`（取数配置）占用，再引入 JDBC 语义的 `@DataSource` 造成三义混淆；与 `java.sql.DataSource`、Spring 动态数据源注解同名 | 已落地模块 `com.eric.base.sys.datasource` | 裁决保留草稿原名并收敛到独立包 `com.eric.base.common.source`；与 `java.sql.DataSource` 的同名单 import 冲突由设计文档评估（见 §7） |
| 9 | 注解元信息缺失：`@Retention`/`@Target` 未声明 | A8 先例 `@Retention(RUNTIME)`/`@Target(FIELD)`（`DatasourceField.java:18-19`） | 设计文档补齐 |
| 10 | `fieldMaxLength() default 200` 一刀切：现有表字段长度差异大（VARCHAR(32)/(100)/(200)/(500)），默认 200 会让存量 adopt 比对产生长期漂移告警 | 各建表脚本（如 `V1_01_046`） | 长度必填显式声明，不设默认值 |
| 11 | `defaultValue` 无函数式默认值出口：`DEFAULT CURRENT_TIMESTAMP`、`ON UPDATE CURRENT_TIMESTAMP`（`field_update_time` 全工程统一写法）无法表达 | 各建表脚本 | 公共列走内建模板；业务时间列默认值表达式单列设计 |
| 12 | `@TableSource` 缺表级属性：`ENGINE=InnoDB`、`CHARSET=utf8mb4`、表 COMMENT（现有脚本全部显式声明） | 各建表脚本 | 引擎内建统一默认值 + 补 COMMENT 属性，设计文档定稿 |
| 13 | `primaryKey` 标志与惯例冲突：全工程统一 `field_id VARCHAR(32)` 主键（`IDUtil.initID()`），开放标注引入偏离口子 | 建表脚本 + `IDUtil` | 同 A8 模式内建主键列，不开放 `primaryKey` 标注 |

## 5. 建议与路线

### 5.1 裁剪建议

- **砍掉** `@ObjectField` / `@ListObjectField`：联表查询属数据源查询引擎范畴，v1.8 方案 §9 已裁决「跨数据源 join 不做」，此处属范围蔓延；
- **取消** `@DataSource`：数据源归属改由配置表达；
- **保留** `@TableSource` / `@ColumnField` / `@Index` 三件套，可覆盖绝大多数现实需求；
- **复用** 已实现的 `@DatasourceField` + `SysDatasourceFieldScanner` 模式（fail-fast、order、进程内缓存），不重复造注解。

> **裁决修订（2026-11-16）**：`@DataSource` 不取消，作为类级数据源归属声明保留（草稿原名）；注解族全部收敛到新包 `com.eric.base.common.source`；已实现的 A8 `@DatasourceField` 迁入该包替换为 `@DataSourceField`（属性不变），Scanner/Service/各模块 Query/Vo 引用点同批迁移、功能等价。详见 §7。

### 5.2 推荐路线（已裁决：纯替换）

1. 引擎只管「注解标注的表」，不触碰未标注表；
2. 存量 21 张表用反向生成工具导入注解后 adopt（比对告警，不重建）；
3. **纯替换 Flyway**（裁决推翻原「冻结 baseline + SQL 通道」的混合模式建议）：移除 `spring.flyway` 配置与 Flyway 依赖，`flyway_schema_history` 保留为历史档案不再读写；
4. 数据回填走 **Java 编码迁移通道（DataMigration SPI）**：版本化、只增不改日志表、启动期按序执行，替代 SQL 数据脚本；
5. 生产环境 validate-only（`CS_DS_SYNC_MODE` 三段式门禁）。

### 5.3 POC 与立项评估

- **POC 验证三件事**：模型 → DDL 生成正确性（MySQL 8.4 + Connector 8.4.0）、基于 `information_schema` 的 diff 准确性、锁与门禁机制；
- **工作量评估**：属内部 mini-hbm2ddl，按框架标准评估（约 1~2 周起步 + 长期维护成本），需与痛点强度匹配后再决定是否投入。
